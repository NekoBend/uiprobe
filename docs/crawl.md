# Crawling an app

`uiprobe crawl PACKAGE` shows what a crawl of the app `PACKAGE` would press on the screen that is showing now, and for every clickable element it would not press, why not. The preview is the default: it presses nothing. The older form `uiprobe crawl PACKAGE --dry-run` still works and always means the preview. `uiprobe crawl PACKAGE --press --out DIR` crawls for real: see [Pressing crawl](#pressing-crawl---press). A crawl presses when `--press` is given, or when the settings file says `press = true` and `--dry-run` is not given; `--dry-run` always previews. Every pressing run, by `--press` or by `press = true`, takes its run folder from `--out DIR` when given (counted from the current folder); else it makes a new folder inside the folder that the settings file's `runs_dir` names (see [Settings file](settings.md)); else it stops with a usage error (exit 2) before the adb server is contacted that asks for `--out`, in the style of the missing-settings-file message (with `--json` the lines are the one `message`, separated by newlines, and there are no `details`):

```
uiprobe: error: a pressing crawl needs a folder to record the run into, and none was given
give one now:      add --out DIR to the same command (DIR must not exist yet)
or set it once:    runs_dir = "uiprobe-runs" in uiprobe.toml (a real folder that exists, counted from the settings file's folder; each run gets a new folder inside it)
```

The file name in the `runs_dir` line, and in the first line when `press = true` comes from the file, is the settings file the run uses: the path given with `--config PATH`, or `uiprobe.toml`. `runs_dir` must name a real folder (not a link or junction) that already exists. When `press = true` comes from the file, the first line ends with `(the settings file uiprobe.toml says press = true)` and a fourth line follows: `or preview:        add --dry-run and remove press-only options such as --depth (a preview presses nothing)`; `--dry-run` alone is refused when press-only options are given.

`--press` together with `--dry-run` is a usage error (`--press and --dry-run cannot be combined`). The preview needs the settings file (see [Settings file](settings.md)): its words, rules, screen-edge sizes and smallest visible size are the defaults of the run. It reads `./uiprobe.toml` in the current folder, or the file named by `--config PATH`; no other folder is searched. Without a file the command stops with a usage error (exit 2) before the adb server is contacted:

```console
$ uiprobe crawl com.example.app
uiprobe: error: crawl needs a settings file and none was found (looked for ./uiprobe.toml)
create it with:    uiprobe init
or name one with:  uiprobe crawl com.example.app --config PATH
```

The last line keeps a `--dry-run` that was given (`uiprobe crawl com.example.app --dry-run --config PATH`), so that following it works with a file that says `press = true`; with `--press`, or with an option that only a pressing run takes (such as `--out`), it says `add --config PATH to the same command` instead, because a pressing run has more options than the line could repeat. With `--json` the three lines are the `message` of the `uiprobe.error/1` object, and `details` holds `looked_for`, `create` and `name_one`. When the missing file was named with `--config PATH`, the `create` line is `uiprobe init PATH` with the given path filled in (only when it needs no shell quoting; otherwise the word `PATH` stays a placeholder), so that it creates the file that was looked for. A file that is given with `--config` but missing, or that is invalid, is a usage error that names the file and, for an invalid entry, the key. A `--config` path that ends with a path separator or `/.` (`rules.toml/`, `rules.toml/.`) is the folder form of a path: it is a usage error that names the file to give instead (`to use the file, give --config rules.toml`), and `rules.toml` is not read. Any other path is opened as given, never tidied first. Warnings about the file (an entry that has no effect) go to stderr.

```console
$ uiprobe crawl com.example.app
$ uiprobe crawl com.example.app --deny "gift card" --deny "coupon"
$ uiprobe crawl com.example.app --config ci/uiprobe.toml
$ uiprobe crawl com.example.app --tap-unlabeled
$ uiprobe crawl com.example.app --json
$ uiprobe crawl com.example.app --dry-run
```

Example output (abbreviated; it is not a recording of a real screen):

```console
$ uiprobe crawl com.example.shop
preview for com.example.shop on screen s-23512491bbaf; nothing was pressed
settings: uiprobe.toml
foreground: com.example.shop, keyboard: hidden
would press (1):
  e2 TextView "Browse" id=browse [tap] center=160,125
would not press (2):
  e3 TextView "Delete account" [tap] center=160,185: deny_word ("delete" in text)
  e6 TextView [tap] center=160,305: unlabeled
nothing was pressed: this was a preview (the default)
to press this time: add --press --out DIR to the same command
to always press: set press = true in uiprobe.toml, and runs_dir (the folder that gets the run folders) or --out DIR on each run
```

The line `nothing was pressed` says `(--dry-run)` instead of `(the default)` when `--dry-run` was given. The two lines after it say how to switch to a pressing run, for this run or for every run. The first says what to add to the command you just ran, so that its other options (`-s`, `--deny`, `--config` and the rest) stay as they were; after `--dry-run` it reads `to press this time: remove --dry-run and add --press --out DIR to the same command`. When the settings file has `runs_dir`, it names only `--press` (`add --press to the same command`), since the run folder then comes from the file. The second says that every run then also needs `runs_dir` or `--out DIR`. When the device does not answer that it is an emulator (also when the check cannot be read), a third line follows: `on a real device also add --allow-real-device`. When the settings file says `press = true` and `--dry-run` kept the run from pressing, the output ends with `nothing was pressed: this was a preview (--dry-run)` and none of these lines follow: the switch is to remove `--dry-run`, and to add `--out DIR` unless the file has `runs_dir`. The JSON output has none of these lines.

| Option | Meaning |
| --- | --- |
| `--dry-run` | Force the preview (the default): judge the screen showing now; press nothing. Wins over `press = true` in the file. Cannot be combined with `--press`. |
| `--press` | Crawl for real (see [Pressing crawl](#pressing-crawl---press)). Needs `--out DIR`, or `runs_dir` in the settings file. Cannot be combined with `--dry-run`. `press = true` in the settings file does the same without it. |
| `--deny WORD` | Also never press an element that contains `WORD`, for this run only. May be given many times. |
| `--config PATH` | The settings file to use (default `./uiprobe.toml`). It must exist. |
| `--tap-unlabeled` | Allow pressing elements that have no text, description or hint, for this run, whatever the file says. This also allows icon-only buttons that deny words cannot see, such as a trash can. |

`--deny-file` no longer exists: the settings file replaces it, so giving it is a usage error. Put the words in the file's `[deny] words`. The [common options](commands.md#options) (`-s`, `--adb`, `--adb-server`, `--no-start-server`, `--json`) work as for the other commands.

What the preview does:

- It makes one dump of the screen showing now, then reads which app is in front, then whether the soft keyboard is shown; for the text output (not with `--json`) it then reads whether the device is an emulator (`getprop ro.kernel.qemu`), for the closing lines, unless the file says `press = true`. Apart from the temporary dump file that every dump writes on the device and tries to remove afterwards, on a best-effort basis (see [Network and privacy](network.md)), nothing that changes the device is sent: no input, no app launch. It creates no file or folder on this computer, also when it is interrupted (exit 130). Because it presses nothing, uiprobe does not refuse a real device; the [Safety](safety.md) advice about test devices still applies.
- It does not start the app or bring it to the front. If another app is in front, or the foreground cannot be read, every element is skipped as `outside_target_app`, except on a screen over the element limit, where every candidate gets only `screen_too_large` (see the table below). Open the app yourself first.
- Only clickable elements appear, under `would press` or `would not press` (`press` or `skip` in JSON); other elements are not listed. A candidate without a visible part of at least `[rules] min_visible_px` pixels (default 8) in width and height has no `center`; the fixed 8 pixels apply only to the center shown on a `screen_too_large` screen (see the table below). Two rules apply here and to no other command (`tap`, `find` and the rest are not affected): the crawl does not press an element whose label is only a number (`number_only`), and does not press a switch, checkbox, radio button or a row that holds one (`toggle`). Both only add refusals. An element that may be pressed is listed under `would press`; every other one is listed under `would not press` with all its reasons, in the fixed order below. For `deny_word`, `irreversible_screen` and `confirm_button` the line also says which word or phrase was found and where: `("delete" in text)` when the element itself holds it, `("delete" in text of e12)` when it was found in another element that shares the press point or belongs to the element's scope (for `confirm_button` and `irreversible_screen`, any element on the screen).
- The command exits with 0 whenever the preview was made, also when nothing may be pressed or another app is in front. Device errors exit as for `find`, and Ctrl+C exits with 130.

The reasons, in the order they are listed:

| Reason | Meaning |
| --- | --- |
| `screen_too_large` | The screen has more than 5000 elements. It is not judged, and every candidate gets only this reason. In the preview, the center shown for such a candidate is the middle of its visible part as `Screen.visible_bounds` gives it, which always uses 8 pixels, even when `[rules] min_visible_px` is larger (the element is still not pressed). |
| `outside_target_app` | The foreground is not `PACKAGE` (or is unknown), or the screen belongs to another package, or any element whose part on the display holds the press point belongs to another package, whether it is drawn on top of the candidate or behind it. |
| `permission_screen` | The press point belongs to a system permission dialog. |
| `not_visible` | No part of the element is on the display, or the part on the display is narrower or lower than `[rules] min_visible_px` pixels (default 8). |
| `covered` | The topmost meaningful element at the press point (clickable, or with a text, description or hint; the last in document order) is neither the element nor one of its descendants. The detail names that element (`element_id`). A candidate is always clickable, so it is always meaningful and is the topmost meaningful element at its own press point at the latest; a press target is therefore never missing for a candidate (the `no_target` refusal of `tap` cannot happen in a crawl). |
| `disabled` | The element is disabled. |
| `text_input` | Pressing the point would focus a text field and raise the keyboard. |
| `password_field` | The element or an element that holds its press point (an ancestor or something on top) is a password field, or the element or a clickable such element contains one. |
| `unlabeled` | The element and its descendants have no text, content description or hint (unless `--tap-unlabeled`). |
| `number_only` | The label is only a number: it has a numeral and otherwise only whitespace, punctuation and symbols (`200`, `$5`, `1,000`, `12:30`, `+1`; not `Page 2`, `8:30 AM`, `2 items`). A numeral is a digit of any script, a fraction such as `½` or a Roman numeral such as `Ⅳ`; the last two are refused on purpose. The label is the element's own text, else its description, else its hint, else the first non-empty text or description of a descendant. Such a tile is often a price (spending in-game coins) or a keypad digit. Over-blocks page number buttons, keypads and rating stars labelled `4.5`. |
| `toggle` | The element or a descendant is checkable (a switch, checkbox, radio button or toggle button), because pressing it changes an app setting. The detail names the checkable element. Over-blocks a Settings row whose main press opens a sub-screen but which also holds a switch. |
| `two_target_row` | The element's descendants hold an element whose resource id ends with `:id/two_target_divider` (unless `[rules] skip_two_target_rows` is `false`). AOSP Settings draws that divider between the main area of a two-target row and its second button: pressing the "T-Mobile" row of the Internet screen switches the active network, while the gear next to it opens the details. Only the row is refused; the gear and the other elements inside it are judged on their own. The detail names the divider (`element_id`). Expected not to fire on vendor Settings apps such as Samsung's One UI (not confirmed: only its home page was recorded); use `row_with_button` there. |
| `row_with_button` | The element has a clickable descendant (only with `[rules] skip_rows_with_buttons = true`; off by default). It catches two-target rows without the divider id, and also refuses list rows of ordinary apps that hold their own button (a mail row with a star, a song row with a menu). The detail names the first clickable descendant. When `two_target_row` applies too, only `two_target_row` is given. |
| `navigate_up` | The element is the up button of a toolbar, the arrow at its top left (unless `[rules] skip_navigate_up` is `false`). It is found by its structure: an image button (class ending in `ImageButton` or `ImageView`) that is the first clickable child of a toolbar, which is a parent whose class ends with `Toolbar` or whose resource id ends with `:id/action_bar` (the dump reports a Toolbar as `android.view.ViewGroup`, and AOSP Settings gives it that id); or by a resource id ending with `:id/home` or `:id/up` (the older action bar). An element whose content description, or whose label as for `number_only`, is exactly `Navigate up` is refused too; that is text the app chooses, and an app that sets it only makes uiprobe refuse more. The detail's `note` says which sign matched. Over-blocks the first image button of a toolbar on a top-level screen (a drawer button). |
| `slider` | The element or one of its descendants is an adjustable control: its class ends with `SeekBar` (also `AbsSeekBar`, `AppCompatSeekBar`), `RatingBar` or `Slider` (the Material `Slider` and `RangeSlider`); or the element's press point lies on such a control anywhere on the screen (unless `[rules] skip_sliders` is `false`). A tap on a slider moves it to the tapped place and so changes a value. The detail names the slider (`element_id`) and says `subtree` or `press point` (`note`). A `ProgressBar` is not refused. |
| `deny_word` | A deny word is found in the element's scope: its own fields and its descendants, the descendants of every clickable ancestor, and every element that holds its press point (an ancestor or something on top): its own fields and the descendants of its clickable ancestors, and, when it is clickable, all its descendants. The scope also includes the joined text and descriptions of the subtree of each clickable element in it, so a word split over children matches (separate children "Log" and "out" match `log out`); the JSON detail then has the field `joined`. |
| `irreversible_screen` | The screen warns that something cannot be taken back: the text, description or hint of any element on it holds an irreversibility phrase (see below). Every element of the screen gets this reason, whatever its own label is, so that neither the "Yes" nor the "Cancel" button of such a screen is pressed. The detail names the phrase (`word`, with curly apostrophes written as plain ones), the field and the element where it was found (`element_id`), the first one in document order. Hidden and off-screen elements count too. It is switched off by `[rules] refuse_irreversible_screens = false`. |
| `confirm_button` | The element, or a clickable element holding its press point, is labeled as a confirm button and a deny word is found somewhere on the screen (exception words never apply here). A label is a confirm label when it equals a confirm word ("OK", "Yes", "Allow", "はい", ...) or starts with one followed by a character that is not a letter ("Yes I'm sure!", "OK, delete", "Continue anyway"); "Okinawa", "Yesterday" and "Continued" are not. The check applies to full-screen layouts as well as dialogs. |
| `dialog_confirm_button` | The element is a confirm button on a dialog (unless `[rules] refuse_dialog_confirm` is `false`). |
| `screen_edge` | The press point lies in a screen-edge area where a press would pull the status bar, a gesture or the navigation bar. |

The crawl takes the first pressable element of a screen, and on a sub-page that is the up button. Pressing it returned to the parent screen at once, before any row of the sub-page was pressed; the crawl took that parent for a deeper screen, pressed BACK on the app's real first screen, left the app and relaunched it, about 6 actions per sub-page. With `navigate_up` the rows of a sub-page are pressed first, and the crawl goes back up with its own BACK, as before.

A tap on a slider changes a value. On a Samsung phone the crawl pressed the "Notification vibration" row of the Settings app at its centre; the centre lay on the row's SeekBar, so the tap set the vibration intensity from 5 to 2. Because the slider's description changed, the row then counted as a new element and was pressed again. uiprobe always presses the centre of the visible part of an element and does not move the press point aside, so a row that holds a slider, and any element whose centre lies on one, is refused.

Neither row rule catches a row that shows no structural sign, for example a saved Wi-Fi network row whose press reconnects to that network: it has no divider and no button inside, so it is still pressed.

Deny words are matched as substrings in the text, content description, hint and resource id (without its package part), ignoring case, width variants and separators, so `signUp`, `sign-up` and `SIGN UP` all match `sign up`. The built-in list holds Japanese and English words for buying, paying, sending, posting, deleting, disabling, force-stopping, signing in, signing out, adding to a cart, opening an account, starting over (`restart`, `undo`, `やり直`, `元に戻`), and the state-changing verbs of Settings pages (`forget`, `disconnect`, `unpair`, `turn off`, `revoke`, `eject`, `unmount`, `unlink`, `deactivate`, `切断`, `接続を解除`, `ペアリングを解除`, `オフにする`, `取り出`, `マウント解除`, `リンク解除`; added in defaults version 7, after a crawl pressed `Forget` on a saved Wi-Fi network) and similar actions. `restore`, `復元`, `取り消` and `stop` are not default words: `Backup & restore` rows only open a sub-page, `取り消し` often means Cancel, and `Stop` is too common.

Exception words are empty by default, so by default the deny words decide exactly as described above. You can list words under `[deny] except` in the settings file. A deny word found completely inside such a word, where it stands as one whole word of a text, content description or hint (also in the texts of an element's descendants read together), then no longer counts. For example, with `except = ["automatically"]`, `call` inside `Automatically` no longer refuses a Settings row whose summary reads `Wi-Fi doesn't turn back on automatically`. Only that occurrence is excused: an element whose only hit was there is then pressed, also by `crawl --press`, unless another reason refuses it or the limits below apply. `Automatically pay` is still refused by `pay`, and a label split across child elements may still be refused (see below), but `Bill my card automatically`, `Empty trash automatically` and `Redial automatically` hold no other hit and are pressed. Whoever adds an exception word takes that on. To see what the deny words matched, look at the elements that would not be pressed: each line of the preview names the word, the field and the element (`deny_word ("call" in text of e5)`), and `--json` has them under `details`; in a pressing run, `skipped.jsonl` has the reasons and, for `deny_word`, `irreversible_screen` and `confirm_button`, the same details (see [The run folder](run-folder.md)). It has one line per screen id, element fingerprint and reasons, not one per element: identical elements of one screen with the same reasons share a line (the details are those of the first one), and a screen with too many elements to judge gives one line for the whole screen (`screen_too_large`).

When an exception word excuses a hit, exactly: the hit lies completely inside an occurrence of the exception word; that occurrence is one whole word (a run of letters and digits, with the accent marks that belong to them, equal to the exception word apart from case and width variants) inside the text of one element field (its text, content description or hint); and it has real separators on both sides, that is a space, punctuation, or the start or end of that text. Where the texts of an element's descendants are read together, the start or end of one text counts as a separator only when the nearest visible character of the neighbouring text is not a letter, digit or combining mark (texts with only invisible characters are passed over). Every occurrence of a deny word is checked on its own, so `Recorder order` is still refused with `recorder` listed (the second `order` stands outside the word). Every clickable element in the subtree is judged this way, so an outer clickable container cannot hide the refusal of a button inside it.

When it does not excuse a hit (each of these refuses more, never less): a hit that only overlaps the occurrence or spans two texts; an exception word that appears only across two texts or touches a letter, digit or mark of the neighbouring text, so a label split across child elements may not be excused (`recorder` + `s`, also with `recorders` listed; `recorder` + U+0301; U+0332 + `recorder`; `削除済み` + `にする`; and `Turn on` + `automatically`, although a person reads two words there); and a word that is not the same once normalized: `Borders` is another word than `border`, a word that appears only once spaces are removed does not count (`Job order` still matches `order`, although `joborder` holds `border`), and an invisible character or a full-width or circled letter inside the word, an additional or different combining mark (an accent) inside it or right after it, a boundary that exists only after width folding (`Ŀrecorder` is one word, although folding turns `Ŀ` into `L` and a middle dot) and an invisible character next to it that hides a longer word (`recorder` + zero-width space + `s` reads `recorders`; `recorder` + zero-width space alone, or followed by a space, keeps the exception) all make it another word. In these cases any deny hit that is still present after normalization counts. A hit that normalization removes was never a hit, with or without exceptions: the single text `recorder` + U+0301 holds no `order` once width folding composes `ŕ`. An exception word written with a mark (`r` + U+0308 + `ecorder`) matches the text with the same mark, unless width folding (NFKC) composes the mark with its letter into one character (`e` + U+0301 becomes `é`): then the exception does not match and the hit counts.

An entry must be one word of letters and digits without invisible characters (a zero-width space or a variation selector such as U+FE0F is refused) and must not equal a deny word; such a pair is an error that says to remove the deny word instead. An exception word excuses every deny word, the built-in ones and the ones added in the file or with `--deny`; a word given with `--deny` that equals an exception word blocks as given, because the exception is dropped for that run. Resource ids, the irreversibility phrases and the screen-wide search behind `confirm_button` never use exception words, so `Debit $50 automatically?` on a screen still refuses its `Continue` button.

Limits of exception words: the rules above are what uiprobe checks, and they lean towards refusing. Combinations of text an app crafts with exception words you write can still get through in these known ways, which are accepted limits, not checked: a compatibility character that width folding turns into a letter, at the start of the next text, is not seen as continuing the word (with `recorder` listed, the texts `recorder` + `ⓢ` are pressed, while the single text `recorderⓢ` is refused); a combining mark at the start of a text, after punctuation at the end of the text before it, is passed over (with `recorder` listed, `!` + U+0332 + `recorder` in two texts is pressed); case folding can create the hit that the exception then excuses (with `reassigning` listed, `reaßigning` is pressed, because folding `ß` gives `ss` and so `sign in`, which without the exception refuses it). The other way round, a whole exception word can still be refused, so a button holding it is not always pressed: when a neighbouring text changes under width folding, uiprobe cannot trace the joined text back to the texts and counts every hit in it (with `recorder` listed, the texts `Cafe` + U+0301 + `. ` and `Recorder` are refused for `order`, while `Café. ` written with the precomposed `é` and `Recorder` are pressed). An exception word you add means that a button containing that word, where it stands whole, is pressed when no other deny word matches it.

Irreversibility phrases are matched like deny words: as substrings, ignoring case, width variants, separators and invisible characters, and a curly apostrophe counts as a plain one. Each of the text, description and hint of every element is matched alone; the resource id is not read, and a phrase split over two elements is not found. Because spaces and separators are ignored, `cannot be undone` also matches `can not be undone`. The built-in list is `can't undo`, `cannot undo`, `cannot be undone`, `can't be undone`, `cannot be reversed`, `can't be reversed`, `cannot be recovered`, `can't be recovered`, `irreversible`, `irreversibly`, `permanently`, `this action is permanent`, `元に戻せません`, `取り消せません`, `元に戻すことはできません`, `元に戻すことができません`, `取り消すことはできません`, `取り消すことができません`, `復元できません` and `完全に削除`. Only these phrases (and the ones you add) are recognized, not every way of saying that something cannot be undone. The list is in the settings file (`[irreversible] phrases`), so you can remove a phrase there. In the order of the reasons, `irreversible_screen` comes right after `deny_word` and before `confirm_button`.

The screen-edge areas come from the settings file; the generated file holds the sizes measured on an API 36 emulator (24 px at the top, 32 px at the bottom, 30 px at each side), the same for every device. They are pixels, not scaled to the device's density. The smallest visible size (`min_visible_px`, 8 in the generated file) applies to the rules of the crawl preview only: `tap`, `find` and the Python `Screen` keep the fixed 8 pixels.

Limits that are known and accepted:

- Substrings over-block: `Posture` contains `post` and `Recorder` contains `order`, so both are not pressed. A miss is worse than an over-block. An exception word in the settings file can let such a word through, with the risk described above.
- The sign-in, disable and force-stop words over-block too: `sign in` matches `Designing`, `Signing out` and `Design info`, `log in` matches `Dialog input` and `Catalog in stock` (any word ending in `log` or `sign` before a word starting with `in`), `disable` matches a `Disabled` status text, and `無効` matches a status text such as `Wi-Fi 無効` in a Settings row. The cart and account words over-block too: `account` matches `Accounts` and `Accounting`, `cart` matches `Cartoon`, `Descartes` and, across a space, `Music artists`. Exception words do not help where the hit spans two words, as in `Dialog input`, `Catalog in stock` and `Music artists`.
- The state-changing words over-block too, and are accepted over-blocks: `forget`, `disconnect`, `unpair`, `revoke` and `eject` also match labels that only open a page, such as `Unpaired devices`, `Disconnection history`, `Revoked certificates`, `切断履歴`, `Rejected calls` and `Reject` (`eject`), and the status text `Disconnected` (a row whose summary says so is not pressed). `turn off` also matches `Return office` and `Turn offline maps`, because words are compared without spaces too. A `[deny] except` word helps only where the deny word lies completely inside one whole word of the label, so listing `Disconnected`, `Disconnection`, `Unpaired`, `Revoked` or `Rejected` as exception words lets those labels through (and every other label with such a word, including a button that does what the word says); it cannot help when the match spans words, as in `Return office` (`turn off` over `Return` and `office`). There, and wherever you prefer to drop the word altogether, use `[deny] remove`. For those, take the deny word out with `[deny] remove`. A refused row frees action budget, so with a small `--actions` limit a run can reach other rows than before; this is expected.
- An exception word lets through every label in which it stands whole and no other deny word matches, including labels that name an action: with `automatically` listed, `Bill my card automatically`, `Dial automatically` and `Forward automatically` are pressed; with `recorder`, `Email recorder audio`. The deny list has no words such as `dial`, `charge` or `renew` that would catch these.
- A non-clickable container whose resource id or description holds a deny word (for example a list called `order_history_list`) blocks every element under it.
- A deny label that is a sibling of a clickable icon in a row that itself is not clickable is not part of the icon's scope.
- A password field below a non-clickable container that holds the press point does not stop an element from being pressed.
- The start-over words over-block: an `Undo` button that only reverts the last edit, or a `Restart` button of a media player, is refused too, and so are `Restarted`, `Undone`, `Undoubtedly` and `Undock`. The lists prefer refusing too much.
- A confirm word at the start of a label needs a non-letter after it, so `Yes I'm sure!` counts and `Yesterday` does not. A word that ends in a letter of the Japanese script (hiragana, katakana including the long-vowel mark `ー` and the iteration marks, kanji including `々`) needs no boundary, because Japanese is written without spaces: `はい、削除します` and `はい削除します` both count, a custom word `オーケー` matches `オーケーです`, and so do `はいる`, `確認画面` and the negative `許可しない` (over-blocks). Words in every other script keep the boundary, and a confirm word in Latin letters is not matched when Japanese follows it (`OKです`). A label split over several text elements is read joined by a space and, where one text ends and the next starts with a Japanese letter, also joined without one (`確` + `認してください`).
- The irreversibility phrases over-block: `permanently` matches `Permanently moved` and a settings text such as `Permanently allowed`, and a screen with one such text is refused as a whole, even its harmless buttons. The reverse is also true: a warning worded in another way (`This is final`, `No going back`) is not recognised.
- Katakana `ハイ` (or half-width `ﾊｲ`) is not a confirm word; only hiragana `はい` is.
- The preview judges one screen as it is. It cannot see what a press would lead to, and it does not look at the pixels, only at what `uiautomator` reports.
- When `dumpsys window` shows several displays (a foldable with a cover screen) or an unusual focused-display line, the foreground is read only while display 0 is the focused display, from the resumed activity that `dumpsys activity activities` prints once for the whole device (seen on one capture only: SM-F776B, Android 17, phone open); while the cover screen has the focus, the foreground is unknown and every element is skipped as `outside_target_app` (see [Python API](python.md)). The focus reading there is best effort against forged window titles, so the pressing crawl needs the tap window check on such a device: with `--no-tap-window-check` it sends no tap or BACK (`focus_unknown`, cause `several_displays_need_tap_window_check`). That check guards taps only; a BACK relies on the focus reading, so a forged title that makes uiprobe misread the focus could make a BACK go to whichever window really has the focus.

The output with `--json` is a `uiprobe.crawl_preview/1` object (see [Output formats](output.md)).

## Pressing crawl (`--press`)

`uiprobe crawl PACKAGE --press --out DIR` presses for real on the selected device, and so does `uiprobe crawl PACKAGE --out DIR` when the settings file says `press = true` (without `--dry-run`). With `runs_dir` in the settings file, `--out DIR` can be left out: the run then gets a new folder `PACKAGE-YYYYMMDD-HHMMSS` (local time) inside the folder `runs_dir` names. It force-stops the app and starts its launcher activity (unless `--no-restart` is given), judges every screen with the same rules as the preview, taps what they allow, presses BACK, and restarts the app when it is stuck or another app comes to the front. Every step is recorded in the new folder `DIR` (see [Run folder](run-folder.md)). It is the command form of `crawl_run()` (see [Crawling from Python](python.md#crawling-from-python-alpha)), which describes each check it makes before a tap.

```console
$ uiprobe crawl com.example.app --press --out runs/first
$ uiprobe crawl com.example.app --press --out runs/long --actions 200 --minutes 20
$ uiprobe crawl com.example.app --press --out runs/real --allow-real-device
$ uiprobe crawl com.example.app --out runs/second    # with press = true in uiprobe.toml
$ uiprobe crawl com.example.app --press    # with runs_dir in uiprobe.toml
```

With `runs_dir` and no `--out`, the run folder is chosen before anything is sent: the folder `runs_dir` names (relative to the settings file's folder) must exist and be a folder, not itself a link or junction (only its last part is checked so; links and junctions in the parts above it are followed, as for `--out`), and the run folder is `PACKAGE-YYYYMMDD-HHMMSS` in it, or `-2` to `-99` added when that name is taken by anything (a file, a folder or a link); when all are taken the run stops. Each of these stops is a `run_folder_error` (exit 1) before the adb server is contacted; the message for a missing folder says to create it or add `--out DIR`. The plan names the chosen folder. Only the run folder is made, by the same create-only step as for `--out`, nothing is reused or overwritten, and a folder that another program makes under that name between the choice and that step ends the run with `run_folder_error` (`already exists`) before any action, without writing into it and without naming it as the run's folder. Before the device is touched, the chosen folder (from `--out` or `runs_dir`) is checked, and the command stops with `run_folder_error` and no device request on what that check can see: something already at that path (also a broken link); a folder to put it in that does not exist or is not a folder (trailing separators of the path are ignored for this); on Windows, a path that depends on a drive's own working folder; or a path that cannot be inspected at all (access denied, for example). The run checks again and makes the folder create-only as before, and that step can still fail for reasons the early check cannot see, such as a folder that can be read but not written to, or a full disk. Accepted limit: another program running as the same user can replace the `runs_dir` folder, or the new run folder, with a link between uiprobe's check and its use, so the records can land somewhere else; the same holds for `--out` today. Making the folder and writing its files through an open handle of the folder (`dir_fd`) would close that gap and is a possible later change.

Safe defaults:

- It presses only on an emulator. A device that is not an emulator, or whose emulator check (`getprop ro.kernel.qemu`) cannot be read, is refused with exit 17 (`not_emulator`, `details.reason` `not_emulator` or `unreadable`) before the run folder is made or anything changes on the device; the identity read through the pin must say emulator too. Known point: the device is pinned first, which reads its identity (`ro.serialno`, the build fingerprint and the boot id, with `ro.kernel.qemu`, in one command), and only then is the emulator check made, so a real device refused without `--allow-real-device` gets those reads before the refusal. This is how `--press` has always worked; `press = true` in the settings file is a new way into the same run; the message says to add `--allow-real-device`, which presses on that device.
- It stops the app first: the first action force-stops the app (`am force-stop`), then asks Android to start its launcher activity (`am start -W`). Which screen the app then shows is up to the app: for example, Settings on API 36 and 37 emulators brought back another package's search screen after a force-stop (see `other_activity` under [Launching an app](commands.md#launching-an-app) for the API 36 case), which the crawl treats as a screen of another app. What the app had not saved is lost. The force-stop and the start are one action of kind `launch` (counted once toward `--actions`), and the force-stop passes the same checks as a relaunch's: the time limit and the device pin are checked before it, and again before the start. The launcher activity is read before the force-stop as well, and when it cannot be read nothing is sent. When the time limit passes between the two, the start is not sent: the launch gets the `not_sent` end line `start_not_sent` and the summary has a note that the app was force-stopped at the start of the run but not started. `--no-restart` starts from the screen the app shows now, with no force-stop, as earlier versions did. `uiprobe launch` keeps its own default, which is the opposite: it stops the app only with `--restart` (see [Launching an app](commands.md#launching-an-app)).
- It stops at the settings file's `[limits]`: after `actions` sent actions (the launch, taps, BACK and restarts each count; an action the checks held back does not) or `minutes` minutes, 300 and 30 in the file that `uiprobe init` writes, unless `--actions` or `--minutes` say otherwise for the run. `--depth` (else `[limits] depth`, 5 in the generated file) limits how deep it taps on one path: on a screen that deep it presses BACK and goes on with another path, so the depth does not end the run (when the current path is a single screen it sends no navigation BACK, only a BACK that closes a shown keyboard: with `--depth 1`, once the first screen is judged with nothing deeper allowed, the run ends `exhausted`, unless another stop reason such as `keyboard_stuck` or `max_actions` comes first). The time limit is measured from the start of the run, set once: an action is not sent once it has passed, the launch and restarts included, as it is checked by uiprobe's own clock on the request's own connection right before the request is written. Reads are not cut off: a read in progress (a dump, for example) can run until it finishes after the limit, and the run then ends at the next step. Each limit is the option when it was given, else the file's value; every valid settings file holds all three (since defaults version 1). If no file value applied, the values that `uiprobe init` writes would be used (5, 300, 30); the plan calls such a limit `(default)`.
- It sends nothing to a screen of another app, unless the app is listed under `[rules] also_target` in the settings file (see [Listing more apps](safety.md#listing-more-apps-also_target)): it restarts the target app instead (`am force-stop`, then `am start -W`), which can lose unsaved state in that app. `[rules] back_on_other_screens = true` in the settings file (false in the file `uiprobe init` writes) or `--back-on-other-screens` makes it press BACK there instead; that BACK reaches whichever app has the focus. `--back-on-other-screens` turns it on for one run and `--no-back-on-other-screens` turns it off for one run, whatever the file says; both together are a usage error. The plan line names the source: `BACK on screens of other apps: yes (settings file)`, `yes (--back-on-other-screens)`, `no (--no-back-on-other-screens)` or, by default, `no (restart the app)`; with `--json` the plan has `back_on_other_screens_source` (`"file"`, `"option"` or `"default"`). A system permission dialog counts as a screen of another app, so it gets that BACK too. When 3 restarts in a row still end on screens of other apps (an app that opens a screen of another package inside its own task, for example Settings with its search screen) and a fourth would be needed, the run ends with `relaunch_limit`, unless another limit ended it first; the result then adds a note that names the app in front at the end and points to `--back-on-other-screens` (or `back_on_other_screens = true` under `[rules]` in the settings file); it is not shown when BACK was already on. With BACK on the crawl presses BACK on such a screen up to twice before it restarts the app, and that BACK reaches whichever window has the input focus, not the app being crawled. When the app itself was in front at the end but a window of `com.android.systemui` had the input focus (the lock screen, a screen that is off, or the notification shade), the note says to turn the screen on and unlock it when it is off or locked, or to close the notification shade or the other System UI window, then run again; uiprobe does not wake, unlock or close anything itself.
- It does not scroll unless you ask. `[rules] scroll_lists = true` in the settings file (false in the file `uiprobe init` writes) or `--scroll` for one run turns on the scrolling of lists with a mouse wheel turn, and `--no-scroll` turns it off for one run; both together are a usage error. When it is on, and the device's own `input` usage lists the wheel scroll, a screen with nothing left to press (or at the depth limit, where it is scrolled and never pressed) whose largest scrollable element is a `ListView`, `ScrollView`, `RecyclerView` or `NestedScrollView` gets one turn of the wheel, `input mouse scroll X Y --axis VSCROLL,-N`, at a point where only plain layouts and labels lie (N is `[limits] scroll_amount`, 3 in the generated file; at most `[limits] scrolls_per_screen`, 10, turns per screen; after `[limits] scroll_incidents`, 2, turns that changed a value or opened another screen, none at all). The screen is read again and its new rows are tried like any other. It is a different kind of input from a tap, so read [A wheel scroll from the crawl](safety.md#a-wheel-scroll-from-the-crawl) first: an app's own view of an allowed class can react to the wheel, and the dump cannot show it. With it off the run reads no `input` usage and sends no wheel input. The plan line says what the run does, for example `scroll lists with the mouse wheel: yes (--scroll), at most 10 per screen, wheel amount 3; an app's own view can react to the wheel (see docs/safety.md)`, `scroll lists with the mouse wheel: no (this device's input does not list the wheel scroll)` or `scroll lists with the mouse wheel: no`.
- After a relaunch it goes back down. When a relaunch ended a path (a tap landed on another app's screen), the crawl takes the deepest screen of that path that still had rows to try as its goal, and presses the rows that it pressed before to get back down to it: on the top page, then on each screen it passed. This **replay presses rows that were pressed before**, so a row on the way down is pressed once more for each replay. Every replay tap goes through the same checks as any tap (the element must be pressable now, and is judged and re-checked again; nothing that is refused now is pressed). Replay presses only (a) rows of the recorded route, each verified step by step from the root, or (b) untried rows that may be pressed; if (a) cannot be verified, the route is given up and the crawl falls back to (b). A route is used only when its first tap was pressed on the top page and every screen of it was reached by a recorded tap from the one before; a step is pressed only when exactly one pressable row has the recorded fingerprint, at the recorded place. A replay stops at the first difference (another screen than the route expects, the row missing, refused now, or a tap that lands elsewhere), the crawl then goes on from the screen it is on, and a goal whose replay failed twice is dropped (a relaunch that cuts a replay short counts as one failure). Replay taps count as actions and take time like any tap, the depth limit holds, and the limit of relaunches in a row is unchanged. A replay tap's `transition_start` line has `replay: true` (see [The run folder](run-folder.md)). The crawl also counts a row seen with and without a badge (an element whose resource id contains `badge`, in any case, and what is below it) as one row: a row pressed while a badge was shown is not pressed again when the badge is gone. The badge is left out of the row too, so two rows that differ only by a badge inside them count as one row, and one of them may not be pressed. A screen that is too large to be judged has no such counting. A screen whose id changes on its own (for example a list that is still scanning, as Settings' Internet page does while it searches for networks) breaks a route: when such a screen is on the way down, the step to it is not verified and the replay is given up. `[rules] replay_path = false` in the settings file turns this off: it returns both the path replay and the "do not press the same row twice when only a badge changed" behaviour to the earlier behaviour. The default is on, for every file, old ones included.
- It starts the app with `am start -W` of its launcher activity, which it reads with `cmd package resolve-activity` right before each start (the first launch and every relaunch, after the force-stop; no component is kept between starts). By default the first launch reads the launcher activity before the force-stop too, so an app whose launcher activity cannot be read is not force-stopped, and reads it again after the force-stop, as a relaunch does; the start uses that second read. With `--no-restart` it reads it and starts the app without a force-stop. The time limit is checked again after that read, so a read that ends past the limit sends no start. The previous version started apps with `monkey`, which turned auto-rotate on (seen on API 24 and API 36 emulators and a Samsung API 36 phone); `am start` does not change it (see [Launching an app](commands.md#launching-an-app)). When the launcher activity cannot be read, the start is not sent and the crawl ends with exit 15 (`launch_failed`, `launcher_unreadable`; when the read before the first launch's force-stop fails, nothing is sent and the launch gets a `not_sent` end line, and when a read after a force-stop fails, of the first launch or a relaunch, it gets `start_not_sent`). The time limit counts from right after the app's uid is read, so the launcher read is inside it. A start whose reply names an activity of another app is waited on like any start: when the app comes to the front within the launch timeout the crawl goes on with it; otherwise that other app counts as in front (the crawl goes on, and relaunches). A start whose reply does not come in time ends the crawl (exit 15, `start_timeout`): whether the app started is unknown, so nothing more is sent.
- Right before each tap it reads which window takes a touch at the tap's point and sends the tap only when that window belongs to the app. `--no-tap-window-check` turns this off; then an overlay of another app over the point gets the tap.
- With `also_target` listing packages, a screen of a listed package counts as the app's own (the dump and the foreground app must both name that package): its rows are judged and pressed under every guard, its depth continues the path, its rows are tried once like the app's, and its screens are saved in `screens/` and drawn in the tree under the row that opened them. At a tap on such a screen the window at the point must belong to the listed package's uid (read once at the start with the same `dumpsys package` read as the app's, so only while the window check is on; a listed package whose uid cannot be read, for example one that is not installed, is refused when the run starts); a window of a listed package over a tap point of the app itself is still refused. A listed package is never started or stopped: a relaunch always starts the app being crawled, and a screen of a package that is not listed is handled as above. Before anything is sent, the run refuses `com.android.systemui`, the home app and the app itself with exit 2 and the reason; the home app is read once, at the start, with the read-only command `cmd package resolve-activity --brief -a android.intent.action.MAIN -c android.intent.category.HOME` (the package before the slash of its one component line), only when the list is not empty; a read that fails or does not name exactly one valid `PACKAGE/CLASS` refuses the run (`also_target: could not read this device's home app, which also_target needs in order to refuse it; nothing was pressed`), and a home app that changes during the run is not noticed. With the list empty nothing is read or sent for it and the crawl behaves exactly as without the setting.
- The time limit is checked one last time by uiprobe's own clock right before a tap, BACK, force-stop or start is written, so slow checks cannot carry it past the limit. From Python (`crawl_run()`), nothing you pass runs between the last check and such a request; a `stop` that turns true while the checks before a tap or BACK read the screen takes effect after that one press (an accepted limit), as `stop` is asked again when the next observation begins.
- The device is pinned when the run starts: every request goes to that device, and a renumbered connection to the same device is followed (when its boot id can be read) or ends the run. Without a readable boot id, a renumbered connection and any failed adb exchange with the device, even on the same connection, end the run, since the device can then not be told apart from another emulator of the same image.

Before the first action it prints what it will do (to stderr with `--json`, so that stdout holds only the JSON result), and the lines are written out before the app is started: the device and whether it is an emulator, the app, why it presses (`pressing because: --press`, or `pressing because: press = true in FILE` naming the settings file), the limits with where each came from (`(--depth)`, `(--actions)` or `(--minutes)` for an option, `(settings file)` for the file's `[limits]`), the run folder with where it came from (`(--out)`, or `(runs_dir in FILE)`), the two choices about other apps' screens and the tap window above, whether the app is stopped first, and whether lists are scrolled with the mouse wheel (the source, `--scroll` or `settings file`, and the limits when it does; `no` when it does not). At the end it prints why it stopped (`exhausted`, `max_actions`, `max_duration`, `relaunch_limit`, `keyboard_stuck`, `dump_failed_repeatedly`, and the other stop reasons of [Run folder](run-folder.md)), the number of actions started (those not sent included, so it can be larger than `--actions`) and of screens, the actions that were not sent, by reason (for example `covered_by_other`, `cover_unknown`, `device_reconnected`), the number of transport moves, and the run folder:

```console
$ uiprobe crawl com.example.shop --press --out runs/first
pressing on emulator-5554 (emulator): com.example.shop
pressing because: --press
limits: depth 5 (settings file), actions 300 (settings file), minutes 30 (settings file)
run folder: runs/first (--out)
BACK on screens of other apps: no (restart the app)
check the window at each tap point: yes
start: the app is stopped first (am force-stop), then its launcher activity is started; what it had not saved is lost (--no-restart starts from the screen it shows now)
scroll lists with the mouse wheel: no
stopped: exhausted
actions: 31 (started; those not sent included)
screens: 7
not sent: covered_by_other 1
transport moves: 0
run folder: runs/first
```

While it presses, the command writes progress lines to stderr, so that a long run does not look stuck: one line after a sent action, at most one every 5 seconds, counted from the end of the last write, and normally one after the first action (the launch; it is missing when the run stops before the first screen is read, and so is any line when the run ends first). None is written once the run has stopped, and the result below is not changed by them. The line has the time since the start (of the time limit), the actions sent so far (of the action limit), the distinct screens of the app seen so far, and the depth of the path the crawl was on at its last decision (of the depth limit; at least 1):

```console
progress: 2m 14s of 30m, 37 of 300 actions, 12 screens, depth 3 of 5
```

Progress lines are written to stderr also with `--json` (as the plan is), so stdout holds exactly the JSON result. They name no text of the device. When stderr cannot be written to (closed, a broken pipe), the lines are switched off for the rest of the run and the crawl goes on; the result is not affected. `--quiet` turns them off; it is used only when the crawl presses and is a usage error for a preview, as the other options below. The lines are built from what the run already keeps and cost no request to the device. From Python, see `on_progress` in [Crawling from Python](python.md#crawling-from-python-alpha).

Lines starting with `note:` follow when one of these happened:

- A tap was refused because the window at its point could not be read (`cover_unknown`): the note names what could not be read and the option that turns the check off, with its risk. When the window list reader refused it, the note also names its rule and suggests `uiprobe diagnose tap-window` (see [Diagnosing the tap window check](commands.md#diagnosing-the-tap-window-check)); a refusal made before the list was read (the gate's own dump rotated, the app's uid) has no rule and no such suggestion. With the check on (the default), a rotated display prevents every tap; when another check fails as well (for example the keyboard came up), that reason may be the one recorded.
- The device's boot id could not be read: a renumbered connection then ends the run instead of being followed, and so does any failed adb exchange with the device, even on the same connection.
- The run stopped with `dump_failed_repeatedly`: `uiautomator dump` fails on a screen that never settles (a value that changes every second, an animation). The note names the app in front and the last screen that was read, so you can avoid that screen.

| Option | Meaning |
| --- | --- |
| `--out DIR` | The new run folder, counted from the current folder; it must not exist. Required when the crawl presses (with `--press` or `press = true`) and the settings file has no `runs_dir`; given, it wins over `runs_dir`. |
| `--actions N` | The most sent actions, 1 to 10000 (default: `[limits] actions` of the settings file; `uiprobe init` writes 300). |
| `--depth N` | How deep it taps on one path, 1 to 50 (default: `[limits] depth`; `uiprobe init` writes 5); it does not end the run. |
| `--minutes N` | The longest run in minutes, 1 to 1440 (default: `[limits] minutes`; `uiprobe init` writes 30). |
| `--settle SEC` | The pause after a tap or BACK, 0 to 60 seconds (default 1). |
| `--screenshots` | Also save a screenshot of each new screen in the run folder. |
| `--allow-real-device` | Also press on a device that is not an emulator. |
| `--back-on-other-screens` | Press BACK on a screen of another app instead of restarting the app, for this run, whatever `back_on_other_screens` in the settings file says. |
| `--no-back-on-other-screens` | Restart the app on a screen of another app, for this run, even when the settings file says `back_on_other_screens = true`. Not together with `--back-on-other-screens`. |
| `--scroll` | Turn a mouse wheel over lists to reach the rows below the fold, for this run, whatever `scroll_lists` in the settings file says (off by default; see [A wheel scroll from the crawl](safety.md#a-wheel-scroll-from-the-crawl)). |
| `--no-scroll` | Send no wheel input, for this run, even when the settings file says `scroll_lists = true`. Not together with `--scroll`. |
| `--no-tap-window-check` | Do not read which window takes a tap at its point. |
| `--no-record-text` | Keep the texts of the screens out of the run folder for this run (the setting `record_text = false` does it for every run): `text`, `content_desc` and `hint` are written as empty strings with `hidden` naming them, `summary.txt` shows `[text not recorded]`, the window title of a `covered_by_other` line is blanked, and `run-start.json` has `"record_text": false`. The plan says `texts of the screens will not be recorded (password fields are never recorded); the run folder holds no screen text`. The crawl itself does not change. Error messages of the run do not repeat text the device sent (a reply to a request, a window title): it reads `(device text not shown: record_text = false)` instead. Cannot be combined with `--screenshots`. |
| `--quiet` | Print no progress lines (see below). The plan, the `note:` lines, the warnings and the result are printed as before. |
| `--no-restart` | Do not force-stop the app before the first start: the crawl starts from the screen the app shows now. The plan line then reads `start: the app is not stopped first; the crawl starts from the screen the app shows now`. |

`--deny`, `--tap-unlabeled` and `--config` work as for the preview. The options above are used only when the crawl presses (with `--press`, or with `press = true` in the settings file and no `--dry-run`); given to a preview, each is a usage error: `--out is used only when the crawl presses: add --press, or set press = true in the settings file uiprobe.toml`, or with `--dry-run`, `--out is used only when the crawl presses, and --dry-run never presses` (checked before the file is read). With `--screenshots` and the default recording, hiding applies to the text in the records only: a screenshot holds pixels, so an app that shows a password field's characters on screen has them in the PNG; `--no-record-text` refuses `--screenshots` for that reason. `--screenshots` together with `--no-record-text`, or with `record_text = false` in the settings file, is a usage error before the device is contacted: `--screenshots cannot be used with --no-record-text: a screenshot shows the text of the screen, so the run would record it after all (nothing was pressed or written)`. Every value of `--actions`, `--depth`, `--minutes` and `--settle` is checked as it is read, so a wrong value is a usage error even when the option is given again later with a good one.

Exit codes: 0 when the run ended by one of its stop reasons, also when nothing could be pressed; 130 on Ctrl+C, after the run folder's `run.json` was written with the stop reason `interrupted` when that was still possible (the message names the folder only when this run made it and wrote its `run-start.json`; a second Ctrl+C while `run.json` is written can leave the folder without it); 17 for a refused device; the other errors as for the other commands, with `details.out` naming the run folder when this run created it and wrote its `run-start.json` (a folder found at that name, or one this run made but could not write into, is not named). With `--json` the result is a `uiprobe.crawl_run/1` object on stdout (see [Output formats](output.md)), which holds the plan as well, with `press_source` and `limits_source`; the plan lines go to stderr then. If stdout (or, with `--json`, stderr) is closed when the command starts, it stops with a usage error before anything is sent. A plan written to a non-blocking pipe that is full can be lost without an error (Python does not report it); the run starts anyway.

## Seeing the result as a tree

`uiprobe tree RUN_DIR` shows a finished (or interrupted) run folder as a tree of screens: every row of each screen with its name, which rows were pressed and where they led, and which rows were not pressed (marked with ` ·`, or with a kind such as `[toggle]`, `[back]`, `[slider]` or `[disabled]` when the skip reason is one of those; nothing below them was looked at). It reads only the run folder, so it can be run again at any time, without a device. `--why` adds the reason each unpressed row was skipped, `--ids` adds screen ids and activities, and `--json` gives the same graph as data. See [Showing a crawl run as a tree](commands.md#showing-a-crawl-run-as-a-tree).

```console
$ uiprobe tree runs/first
$ uiprobe tree runs/first --why
$ uiprobe tree runs/first --json
```
