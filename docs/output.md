# Output formats

## JSON documents

Every JSON document has a `schema` field. Its number changes only with an incompatible change, such as a removed or renamed field or a field whose meaning changes. A new field does not change it, so a reader should ignore fields it does not know.

- `uiprobe.screen/1`: a dumped screen with `captured_at`, `device` (`serial`, and `api_level` when known), `app` (`package`, and `activity`, which is left out when the focused activity cannot be read reliably or belongs to another app; it is read from Android's text diagnostics on a best-effort basis, so treat it as a hint, not as a security signal), `screen_id`, `display` (`width`, `height`; the device's current logical display size, from `wm size` rotated to the current orientation, falling back to the extent of the dumped windows when that cannot be read), and a flat list of `elements`. Each element has an `id` (`e1`, `e2`, ...), the `id` of its `parent` (absent for top-level elements), `class`, `bounds` as `[left, top, right, bottom]`, and, when present, `text`, `resource_id`, `content_desc`, `hint`, and `flags`. `screen_id` is a short hash of the package, activity, and the classes and resource ids of the elements; it does not change when only text or positions change, but it does change when the number of elements changes.
- `uiprobe.screenshot/1`: the result of `uiprobe screenshot -o PATH --json`, with `captured_at` (as in `uiprobe.screen/1`), `device` (`serial`), `path` (as given with `-o`), `bytes` (the size of the file), `width` and `height` (of the image, in pixels) and `display` (`width`, `height`: the display size that `uiprobe.screen/1` reports and that tap coordinates use, from `wm size`, turned to the orientation of the image; left out when it cannot be read). On newer Android a screen that forbids screenshots can give a mostly black image, which is still a valid PNG and is saved.
- `uiprobe.find/1`: the result of `uiprobe find --json`, with `screen_id`, `criteria` (the given ones, by the element's key names: `text`, `resource_id`, `content_desc`), `total` (how many elements matched), and `elements` (the matches, at most 20, possibly empty). Each element has the same form as in `uiprobe.screen/1` plus `center`, `[x, y]` (left out when the element cannot be pressed: covered, or no press target).
- `uiprobe.action/1`: the result of `uiprobe tap`, `swipe`, `key`, `type` and `launch` with `--json`. `action` is `tap`, `long_tap`, `swipe`, `key`, `type` or `launch`. A tap has `point` (`[x, y]`, the point that was pressed) and, when an element was selected, `element` (the same form as in `uiprobe.find/1`, with `center`; without an element, `--xy`, the key is absent). A swipe has `from` and `to` (`[x, y]`), `duration_ms`, `direction` (only with `--direction`) and `element` (only when one was selected with `--direction`). A key has `key`, the key code name that was sent. A type has `length` (the number of characters of the given text, all sent with exit status 0), `device` (`serial`) and `captured_at` (as in `uiprobe.screen/1`); the text is never written. A launch has `package`, `device` (`serial`), `restart` (`true` or `false`, always written) and `captured_at` (as in `uiprobe.screen/1`, taken after the app came to the front).
- `uiprobe.crawl_preview/1`: the result of `uiprobe crawl PACKAGE --dry-run --json`, and of `uiprobe crawl PACKAGE --json` when the settings file does not say `press = true` (when it does, `uiprobe crawl PACKAGE --out DIR --json` presses and gives `uiprobe.crawl_run/1`, and so does `uiprobe crawl PACKAGE --json` when the file also has `runs_dir`; with neither the command is a usage error), with `package`, `screen_id`, `captured_at` (as in `uiprobe.screen/1`), `settings` (the path of the settings file that was used), `pressed` (`false`, because nothing is pressed) and `mode` (`"preview"`), which this version always writes and which `uiprobe.crawl_preview/1` documents from earlier versions may omit, `foreground` (the package in front; left out when unknown), `keyboard_shown` (`true` or `false`; left out when unknown), `press` and `skip`. Both arrays are always written, in the order of the screen, and may be empty. `press` holds the elements a crawl would press, in the form of `uiprobe.find/1` elements with `center` (the point the judgement chose; a pressable element is never covered, so it always has one). `skip` holds the others in the same form (`center` is left out when the element has no visible part of at least `[rules] min_visible_px` pixels (default 8) in width and height, reason `not_visible`, or is covered; on a `screen_too_large` screen the center is the middle of the visible part with a fixed 8 pixels, and the cover is not computed) plus `reasons` (the reasons, in the order of the table in [Crawling an app](crawl.md)) and `details`, a list with one object per detail: `reason` and, when not empty, `word`, `field`, `element_id` (the element where the word or the cause was found) and `note`.
- `uiprobe.crawl_run/1`: the result of a pressing `uiprobe crawl PACKAGE --json` (with `--press`, or with `press = true` in the settings file), with the plan: `package`, `device` (`serial`, and `emulator`: `true`, `false`, or `null` when the check could not be read and `--allow-real-device` was given), `press_source` (why the run presses: `"option"` for `--press`, `"file"` for `press = true` in the settings file), `limits` (`depth`, `actions`, `minutes`), `limits_source` (for each of `depth`, `actions` and `minutes`, where its value came from: `"option"` for `--depth`, `--actions` or `--minutes`, `"file"` for the settings file's `[limits]`, `"default"` for the value `uiprobe init` writes, used only when neither gives one), `back_on_other_screens`, `check_tap_window`, `screenshots` and `restart` (`true` or `false`; `restart` is `true` unless `--no-restart` was given: the first action force-stops the app before it starts it; written by this version, absent from earlier output); `press_source`, `limits_source` and `out_source` are new in this version too and keep the schema number, as a new field does; and the result: `out` (the run folder), `out_source` (where the run folder came from: `"option"` for `--out`, `"file"` for a new folder inside the settings file's `runs_dir`), `stop_reason` (as in `uiprobe.run/1` of the [Run folder](run-folder.md)), `actions` (actions started, those not sent included), `screens`, `not_sent` (an object from each reason to how many actions were closed as not sent for it; empty when none), `repins` (how many times the pinned transport was followed during the run, as `run.json` counts them; a move during the command's own device check before the run is not counted), `repin` (`false` when the boot id could not be read, so a renumbered connection ends the run) and `notes` (the advice lines the text output shows as `note:`, possibly empty). Errors are `uiprobe.error/1` objects; when this run created the run folder and wrote its `run-start.json`, `details.out` names it (for uiprobe's own errors; an internal error does not; a folder that was already there, or that another process made while the run had not made its own, is not named).
- `uiprobe.diagnose_tap_window/1`: the result of `uiprobe diagnose tap-window --json`, with `notice` (the sentence that the report holds no device serial, app or window names, coordinates, accounts or network values; with `--show-device-text` instead the sentence that it includes text and numbers from the device, where window names and app text can appear, possibly a serial or personal data), `show_device_text` (`true` or `false`), `command` (`"dumpsys input"`, the command whose output the report describes and, without `--package`, the one command it read; with `--package` the `dumpsys package` read of the app's uid comes before it and is not named), `readable` (`true` or `false`), `reason` and `rule` (why the crawl's tap window check would refuse, see [Diagnosing the tap window check](commands.md#diagnosing-the-tap-window-check); `null` when readable; without `--package` the command knows no app, so a valid `samsungFlags=0x1` row reached in display 0's list gives `line_format` and `samsung_flags` also where the crawl accepts it on the app's own window; with `--package PKG` the crawl's test for `PKG` accepts it on `PKG`'s own window; in another display's list that value gives `samsung_fields`, as in the crawl), `note` (present only when `rule` is `samsung_flags` or the uid of `--package` could not be read, absent otherwise: one sentence; for `samsung_flags` without `--package` it is `"a crawl accepts samsungFlags=0x1 on the target app's own window; diagnose is not told an app (add --package PKG to test that app's windows)"`, with `--package` it says that the window is not the given app's own window, or that the app's uid could not be read; for any other result with a uid of `--package` that could not be read it is `"the given app's uid could not be read (dumpsys package); no window counted as its own"`; it holds no device text and never the package; new in this version, keeping the schema number, as a new field does), `part` (`"dispatcher"`, `"input_reader"` or `"output"`, the whole output, used without exactly one dispatcher header or after the dispatcher's part) and `line` (the line it refused at, from 1 in that part; both `null` when no one line is to blame), `windows_read` (how many window lines the reader read into a window in the display's list), `display_list` (the list the reader took as display 0's, `null` when none: `per_display`, `false` for the one list of every display; `reached`, whether the reader got to it; `read`; and `failed`, `true` when the check refused in it) and `lines` (the failing line and the lines around it, or the reader's headings: `number`, `failing`, `kind` (`window_row`, `transform`, `matrix_row`, `heading`, `viewport`, `other` or `blank`, as the reader classified the line) and `length`). `windows_read`, `read` and `length` are at most 9999 in JSON (9999 stands for 9999 or more; the Python object keeps the exact numbers). Nothing else of the device's output is in it. With `--show-device-text` each line also has `indent` and `tokens` (a list of strings holding device text), and the object has `lists` (every list the reader found: `position`, `per_display`, `asked`, `reached`, `read`, `failed`) and `forms` (rows that look alike: `position`, `rows`, `recognised`, `quoted`, `transform` and `fields`); see the command's page.
- `uiprobe.init/1`: the result of `uiprobe init --json`, `{"schema": ..., "path": ...}`, the path of the settings file that was created.
- `uiprobe.devices/1`: `{"schema": ..., "devices": [...]}` with `serial` and `state` for each device, and `model`, `api_level`, and `emulator` when known.
- `uiprobe.error/1`: `{"schema": ..., "error": {"code": ..., "message": ..., "details": ...}}`, where `details` is present only when there are any. Without `--json` the message is printed on stderr instead. For `uiprobe diagnose` the message is a fixed sentence that names only the code, and `details` is left out (an `internal_error` keeps `details.type`, the name of the exception class), because the error's own message can name the device; a usage error of `diagnose` shows none of the arguments, only the valid form (or `--serial may be given only once`).

- `uiprobe.crawl_tree/1`: the result of `uiprobe tree RUN_DIR --json` (see [Showing a crawl run as a tree](commands.md#showing-a-crawl-run-as-a-tree)), built from the files of a run folder only. It has `run` (`package`, `label` (`null`; the app's label is not recorded in the run folder yet), `started_at`, `ended_at` and `stop_reason` (`null` when `run.json` is missing), `actions`, `finished` (`true` when `run.json` was read) and `record_text` (`false` when `run-start.json` says so)), `root` (the screen the first launch led to; `null` when it is unknown or has no file), `screens`, `unreached` and `warnings` (strings). `screens` is a flat map from screen id to `package`, `activity` (`null` when unknown), `elements`, `unmatched` and, when the crawl did not judge the screen (`screen_too_large`), `screen_reasons`. A screen reached twice is one entry; a reader follows `to.screen_id`. `unreached` lists the screens of the app that no recorded tap led to and that are not the root (screens only they lead to are in `screens` too, but not listed). `elements` are in document order. Each has `element_id` (`e1`, ...), `kind` (`row`, a clickable element, or `heading`, a text outside any clickable element), `class`, `name` (the first text of the row; else its content description in quotes; else `[icon: CLASS]`), `texts` (all texts of the row in document order, the name first when it is a text) and, only when the name is hidden, `hidden` (`true`: the run recorded no texts, or the element is a password field, whose name is `[password field]` and whose `texts` are empty). A `row` also has `pressed` (`true` when a tap on it was sent), `action_id` (the tap's action id, or `null` when no tap was recorded), `to` (only when a tap was recorded: one of `{"screen_id": ID}`, `{"same_screen": true}`, `{"other_app": PACKAGE or null}`, `{"not_read": true}`, `{"unknown": true}` (a start line with no end line) and `{"not_sent": REASON}`; a tap that was not sent, or whose delivery is unknown, has `pressed` `false`) and `reasons` (the reasons from `skipped.jsonl`, matched by the element's fingerprint; empty when none). `unmatched` lists the entries of `skipped.jsonl` for this screen that match no row, each with `fingerprint` and `reasons`.

The files of a crawl run folder (`uiprobe.run_start/1`, `uiprobe.transition_start/1`, `uiprobe.transition_end/1`, `uiprobe.skip/1`, `uiprobe.run/1`) are described in [The run folder](run-folder.md). This version adds `restart` to `uiprobe.run_start/1` (`true` or `false`) and to the first `uiprobe.transition_start/1` line (`true` when that launch includes a force-stop, absent otherwise; it records what the launch is, written before anything is sent: whether the force-stop went out is in the end line: a `not_sent` end line with any reason but `start_not_sent` means nothing was sent; `start_not_sent` means the force-stop went out and the start did not; a `failed` end line (`outcome: "unknown"`) means the force-stop or the start may have reached the device; any other end line means both were sent), without a new schema number.

## Exit codes

| Code | `error.code` | Meaning |
| --- | --- | --- |
| 0 | | Success. This includes a crawl preview that found nothing to press, and a pressing crawl that ended by one of its stop reasons (also `not_sent`). |
| 1 | `internal_error`, `file_error`, `run_folder_error` | Unexpected error. `run_folder_error` is `uiprobe crawl --press` failing to make its run folder or to complete one of its files (`details.path` names it). `file_error` is `uiprobe screenshot` failing to create its file (`details.created` is `false`) or to finish writing it (`true`; the partial file stays and `details.path` names it). |
| 2 | `usage_error` | Bad command line or argument. |
| 3 | `adb_server_unavailable` | The adb server cannot be reached or started. |
| 4 | `device_not_found`, `multiple_devices` | No device matches, or several are ready and none was chosen. |
| 5 | `device_offline`, `device_unauthorized` | The device is connected but not usable. |
| 10 | `adb_error` | The adb server refused a request or the protocol broke. |
| 11 | `dump_failed` | `uiautomator dump` failed, timed out while running, or produced unusable XML. |
| 12 | `element_not_found`, `element_not_visible` | `find_one`, `uiprobe tap` or `uiprobe swipe --direction` found nothing (`uiprobe find` exits with 0 instead), or the element to press has no visible part, shows under 8 x 8 pixels (also when it is the only match), is covered by another element, or has no press target (`uiprobe tap` with a selector, and the library). |
| 13 | `multiple_elements` | `find_one`, `uiprobe tap` or `uiprobe swipe --direction` found several elements (a match under 8 x 8 pixels counts). |
| 14 | `input_failed` | The device did not report success for a tap, long press, swipe, key or a piece of `type`. This does not prove that nothing was pressed or moved. |
| 15 | `launch_failed` | `uiprobe launch` could not start the app or could not see it in front: `details.reason` is `launcher_unreadable`, `stop_failed`, `start_failed`, `other_activity`, `unexpected_output`, `start_timeout` or `not_in_front` (see [Launching an app](commands.md#launching-an-app)). With `start_failed`, `other_activity`, `unexpected_output`, `start_timeout` and `not_in_front` the app may still have started. |
| 16 | `screenshot_failed` | The device gave no usable screenshot: empty output (a screen that forbids screenshots can give this on older Android), a cut-off image or data that fails the PNG checks listed in [Taking a screenshot](commands.md#taking-a-screenshot). No file is made. `uiprobe dump` can still return the structure of that screen. |
| 17 | `not_emulator` | `uiprobe crawl --press` (without `--allow-real-device`) or the Python function `crawl_run()` refused to press on a device that is not an emulator, or whose emulator check could not be read (`details.reason` is `not_emulator` or `unreadable`). Nothing was written and no input was sent. `--allow-real-device` (`allow_real_device=True`) skips the check. |
| 130 | `interrupted` | Interrupted with Ctrl+C (also during `crawl`). When `uiprobe screenshot` is interrupted while it writes its file, `details.path` names it and `details.created` is `true`; the file stays and may be incomplete. A Ctrl+C at another instant (inside the creation itself, or after the file is complete while the result is printed) may only say "interrupted" and can leave a partial or a complete file. |
