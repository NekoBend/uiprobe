# Python API

```python
from uiprobe import Device

device = Device()  # or Device("emulator-5554")
screen = device.dump()

print(screen.package, screen.activity)
login = screen.find_one(resource_id="login")  # exactly one match, or an error
print(login.text, screen.tap_point(login))  # the point to tap; raises when covered

buttons = screen.find(text="ログイン")  # a list, possibly empty
print(screen.to_json(indent=2))

point = device.tap(login)  # press it; returns the point pressed
# device.tap(screen.tap_point(login), long=True)  # instead of the tap above: the same point, held 800 ms
```

Note: writing uiprobe's JSON (`Screen.to_json` and the `uiprobe._json.dumps` the commands use) for user-supplied text that is not valid UTF-8 (a lone surrogate, as POSIX makes of undecodable command-line bytes) to a strict stream can raise `UnicodeEncodeError`; the command line escapes it (its output streams use `backslashreplace`).

`uiprobe.cli` is now a package: code that replaces an internal name on `uiprobe.cli` (for example `uiprobe.cli.Device` or `uiprobe.cli.crawl_run`, with monkeypatch) no longer reaches the modules inside it, while the documented entry points (the `uiprobe` command, `uiprobe.cli.main` and `uiprobe.cli.run`) are unchanged.

`uiprobe.device` is now a package, and `Device` is assembled from mixin classes: code that replaces an internal name on `uiprobe.device` (for example `uiprobe.device.time`, `uiprobe.device._monotonic` or `uiprobe.device.DUMP_TIMEOUT`, with monkeypatch) no longer reaches the modules inside it. The documented names (`Device`, `devices`, `select_device`, `device_details`, `uiprobe.device.KEY_ALIASES` and the others a former `from uiprobe.device import ...` could name) are unchanged.

`Device(serial=None, *, adb_server=None, adb=None, start_server=True, pin=False)` chooses the device when it is created. `pin=True` also pins it right then (see [Crawling from Python](#crawling-from-python-alpha)); use it for `crawl_run()`. `uiprobe.devices()` lists devices. `Screen.find` selects visible elements (8 x 8 pixels or more) and `Screen.find_one` selects one element, both with the matching rules of `uiprobe find`: `text`, `resource_id` and `desc` are given together and must all match (AND). `text` is equal after surrounding whitespace is removed on both sides, `resource_id` is equal to the full id or the part after `:id/`, and `desc` is equal. `Screen.visible_bounds(element)` returns the visible part of an element, or `None` when nothing of it is on the display or the part is narrower or lower than `uiprobe.model.MIN_VISIBLE_PX` (8) pixels. `Screen.require_visible(element)` returns the visible part or raises `ElementNotVisibleError` (`no_visible_part` or `too_small`); `Element.is_meaningful` is true for an element that is clickable or has a non-empty text, content description or hint. `Screen.hit_target((x, y))` returns the topmost meaningful element (clickable, or with a non-empty text, content description or hint; the last in document order) whose part on the display holds the point, or `None`; any meaningful element on top counts, whatever its size (the 8-pixel minimum applies to the element being pressed), the right and bottom edges are exclusive and an empty part never holds a point. `Screen.find_one` counts the matches over every element with a non-empty part on the display, whatever its size, so a 100 x 100 element and a 100 x 7 one with the same text are two matches (`MultipleElementsError`); a single match under 8 x 8 pixels raises `ElementNotVisibleError` (`too_small`), not `ElementNotFoundError`. When `find_one` raises `ElementNotFoundError` or `MultipleElementsError`, the `details` of the error hold `criteria`, `total` and `candidates`: for `multiple_elements` the matches, for `element_not_found` the visible elements whose text, resource id or description contains a given value (compared after Unicode NFKC normalization and case folding), or, if there are none, the clickable ones that are not disabled. The `criteria` in `details` use the JSON names (`text`, `resource_id`, `content_desc`), as in `uiprobe find --json`, although the Python parameter is `desc`. There are at most 20 candidates, and `total` is their full number. A candidate has the JSON form of an element plus `center`, `[x, y]`, which is left out when the element cannot be pressed (no visible part, too small, covered, or no press target). `Device(...)` and `devices(...)` raise `TypeError` for an argument of the wrong type and `ValueError` for a malformed address or adb path, before contacting the adb server. `find` and `find_one` raise `ValueError` when no criterion is given. `Screen.tap_point(element)` returns the center of the visible part, rounded down, as `(x, y)`; `find` reports the same point as `center`. It raises `ElementNotVisibleError` (`element_not_visible`, with `element`, `bounds` and `reason` in `details`) when the element has no visible part (`no_visible_part`), shows under 8 x 8 pixels (`too_small`, plus `visible_size`) or is covered (`covered`, plus `covered_by` and `point`) or has no press target (`no_target`, plus `point`): `hit_target` at the point must be the element or one of its descendants, so an element that is not meaningful (no text, description or hint, not clickable), for example one selected by its resource id inside a clickable row, is refused, naming the row; press the row instead. When `hit_target` is `None` (no meaningful element holds the point, possible only for an element that is not meaningful itself) the element is refused with `no_target`, because nothing at that point can receive a press.

`Device.dump(*, details=True)` captures the screen. With `details=False` it skips the reads of `dumpsys window` and `getprop`, so `Screen.activity` and `Screen.api_level` are `None` (the JSON form then leaves out `app.activity` and `device.api_level`) and `Screen.screen_id`, which includes the activity, can differ from the id of a full dump of the same screen; a `details` that is not a bool raises `TypeError` before anything is sent; the display size (`wm size`) and everything that `find_one`, `tap_point` and `tap` check are still read, so those checks give the same results. `uiprobe tap` and `uiprobe swipe` with a selector use `details=False`; `uiprobe dump` and `uiprobe find` keep the default.

`uiprobe.__version__` is the version string, such as `0.1.0a1.dev0`, that `uiprobe --version` prints.

`Device.tap(target, *, long=False, press_ms=10)` presses one point and returns it as `(x, y)`. By default the tap holds still for `press_ms` = 10 ms and is sent as `input swipe X Y X Y 10`, so the "Pointer location" developer option shows it (a plain `input tap` is barely visible there); the point does not move. `press_ms` is an int from 0 to 200 (a bool is not an int; `TypeError` for another type, `ValueError` outside the range): 0 sends the plain `input tap X Y`, and the bound stays below Android's usual default long-press time (about 400 to 500 ms, longer with accessibility settings), though an app may use its own shorter threshold. The 10 ms visibility was measured on one device only (a Galaxy S25 Ultra at 60 Hz: 10 ms visible, 6 ms not). `long=True` sends the fixed 800 ms press and cannot be combined with a `press_ms` other than 10 (`ValueError`). `Device.tap` validates `press_ms` before this call sends any adb request (creating `Device()` already contacts the server). `target` is an `Element` or a point, a tuple or list of two ints from 0 to 32767 (a bool is not an int here). A point of the wrong type, or a `long` that is not a bool, raises `TypeError`; a coordinate out of range raises `ValueError`; `Device.tap()` validates these arguments before it sends any adb request of its own. An element is accepted only when it is one of the elements of the `Screen` returned by the latest `device.dump()` of this same `Device` (the same object, not a copy; `Screen.find` and `Screen.find_one` return such objects). The point is then `screen.tap_point(element)`, so `Device.tap`, `uiprobe tap` and the `center` of `find` agree. An element from an older dump, from another `Device`, built by hand, or given before any dump raises `ValueError` before anything is sent: dump again, or pass `screen.tap_point(element)` as a point. An element with no visible part, a sliver under 8 x 8 pixels or a covered element raises `ElementNotVisibleError` and nothing is sent. A point given directly is pressed as given, with no such check, because the caller named it. The input is sent once and never retried or resent, not even after a connection error, which propagates unchanged. When the device does not report success, `Device.tap` raises `InputFailedError` (`input_failed`); success needs the line `uiprobe-exit:0` as the last line and no other line that is not empty (empty lines are ignored); its `details` hold `command` (`tap` for any `press_ms`, or `long_tap`), `point`, `reason` (`no_exit_status`, `exit_status` or `unexpected_output`), `exit_status` for the second reason, and `output` (at most 200 characters) when there is other text. `input_failed` does not prove that nothing was pressed, so do not repeat the tap blindly. The app in front is not checked.

`Device.swipe(start, end, *, duration_ms=300)` drags one finger and returns `(start, end)` as tuples of ints. Both points follow the rules of `tap` (a tuple or list of two ints from 0 to 32767, no bool); `duration_ms` is an int from 1 to 10000 (`TypeError` for another type, `ValueError` outside the range). A swipe whose start equals its end is a `ValueError`: it is a press, use `tap`. Everything is checked before the adb server is contacted. It sends `input swipe X1 Y1 X2 Y2 MS; echo uiprobe-exit:$?` once, with a read timeout of `duration_ms / 1000 + 10` seconds, and never resends it. `InputFailedError` has `command` `swipe`, `from`, `to` and `duration_ms` in its `details` instead of `point`, and does not prove that nothing moved.

`Device.scroll(direction, *, within=None, duration_ms=300)` swipes along the middle of an area of the screen of the latest `device.dump()` and returns the same pair as `swipe`. `direction` is the way the finger moves: `"up"`, `"down"`, `"left"` or `"right"` (a non-str raises `TypeError`, another string `ValueError`). Without a dump it raises `ValueError("dump the screen first")`. `within` must be an `Element` (`TypeError` for any other type) of that latest screen (an `Element` from another dump raises `ValueError`, as for `tap`) and its visible part is the area (`ElementNotVisibleError` when it has none, a sliver under 8 x 8 pixels included; a cover is not checked); without `within` the area is the whole display. The geometry is the one described under [Swiping and scrolling](commands.md#swiping-and-scrolling): the gesture runs from the first to the last pixel of the rectangle (right and bottom are exclusive, so the far ends are `right - 1` and `bottom - 1`, and both ends are inside the area); an area that is too small raises `ValueError("the area is too small to scroll")`, and so does a latest dump whose display size is unknown because `wm size` could not be read (`ValueError("the display size is unknown ...")`; use `swipe` with explicit points). All of this is checked before anything is sent; the swipe then follows the rules of `Device.swipe`.

`Device.scroll_display(direction, *, duration_ms=300)` is `scroll` over the whole display without a dump: it reads the current display size once with `dumpsys window displays` (the `cur=` size of display 0, already rotated), then sends one swipe with the same geometry and checks as `scroll` without `within`, and returns the same pair. It needs no earlier `dump()` and does not change the latest dump. A `direction` of the wrong type raises `TypeError`, another string `ValueError`; `duration_ms` is checked like in `swipe` (a wrong type raises `TypeError`, an unusable value `ValueError`), before the display size is read. When the size cannot be read it raises `ValueError("the display size is unknown ...")` (a `uiprobe.device.DisplaySizeUnknownError`, a subclass of `ValueError`) and sends nothing; it does not fall back to a dump by itself, so call `dump()` and then `scroll`, or use `swipe` with explicit points. A display too small to scroll raises `ValueError("the area is too small to scroll")`. All of this is checked before any input is sent.

A `Device` object can be reused for several actions: the device is chosen once, when the object is created, so later actions do not repeat the device lookup (`host:devices-l`).

`Device.key(name)` presses one key and returns the key code name it sent. `name` is a key of `uiprobe.device.KEY_ALIASES` (case-insensitive) or a full `KEYCODE_[A-Z0-9_]{1,40}` name; a non-str raises `TypeError`, and an empty name, a number, a `KEYCODE_` name made only of two or more digits (such as `KEYCODE_26`; `KEYCODE_0` to `KEYCODE_9` are accepted), a lower-case `KEYCODE_` name or anything else raises `ValueError`, before the adb server is contacted. It sends `input keyevent KEYCODE_...; echo uiprobe-exit:$?` once and never resends it; `InputFailedError` has `command` `key` and `key` in its `details`. `KEY_ALIASES` is the alias table in [Pressing keys](commands.md#pressing-keys), a `tuple` of `(alias, key code name)` pairs, so it cannot be changed. A key in `uiprobe.device.DEVICE_WIDE_KEYS` (a `frozenset` of names) or starting with one of `uiprobe.device.DEVICE_WIDE_KEY_PREFIXES` (a `tuple`) acts on the whole device and raises `ValueError`, before the adb server is contacted. `Device.key(name, *, refused=None)` takes the refused names from `refused`, a `uiprobe.device.RefusedKeys(keys, prefixes, source="the refused-keys list")` (a `frozenset` of exact `KEYCODE_` names and a `tuple` of name prefixes, each checked against `KEYCODE_[A-Z0-9_]{1,40}`; `source`, a `str`, only names the origin of the lists in the refusal message, which for an exact key says to remove it there and for a prefix names the prefix and says that changing it affects every key that starts with it), in place of those two built-in lists; `None` keeps them. The keys of `uiprobe.device.FIXED_DEVICE_KEYS` are refused whatever `refused` holds, and a `refused` of another type raises `TypeError`. The settings file's lists are `RefusedKeys(frozenset(settings.refused_keys), settings.refused_key_prefixes, str(settings.source))`. The app in front is not checked by `swipe`, `scroll` or `key`.

`Device.type_text(text)` types printable ASCII (0x20 to 0x7E) into the field that has focus and returns `None`. A non-str raises `TypeError`, and a str subclass is read once as a plain `str` with the same characters; empty text, a character outside ASCII, a newline, a tab or another control character raises `uiprobe.device.TextNotTypedError` (a `ValueError`) before the adb server is contacted, with `details` holding `character`, `escaped` and `position` for a refused character. It sends `input text` with the argument in single quotes and `; echo uiprobe-exit:$?`, once per piece, in pieces of at most `uiprobe.device.TYPE_PIECE_SIZE` (256) characters, and splits the text between `%` and `s` so that no piece contains `%s` (the device turns it into a space). Each piece must report exit status 0 and print nothing else (empty lines are ignored), or typing stops with `InputFailedError` (`details`: `command` `type`, `reason`, `piece`, `pieces` and `pieces_done`; no exit status, as the device prints it and a reply could repeat the text). A device error while sending is raised as a new error of the same class whose message and `details` hold only fixed words and the numbers `piece`, `pieces` and `pieces_done` (and `request` `shell:input text <text omitted>`), never the text or what the device answered, chained to no error that uiprobe caught. Typing is not checked afterwards. Typing that stops can leave the earlier pieces typed and the piece it stopped at typed in part or in full.

`Device.launch(package, *, restart=False, timeout=10.0)` starts an app and returns `None` once it is in front. `package` must be a `str` (`TypeError` otherwise; a subclass is used as a plain `str` with the same text) that follows the same rule as `preview` (`ValueError` otherwise), `restart` a bool, and `timeout` a number of seconds from 0 to 600 (a bool is not a number; the value checked and used is the one the base `int` or `float` type gives); all are checked before the adb server is contacted. The previous version started apps with `monkey -p PACKAGE -c android.intent.category.LAUNCHER 1`, which turned the device's auto-rotate setting on (`accelerometer_rotation` 0 to 1; seen on API 24 and API 36 emulators and a Samsung API 36 phone); `am start` does not change it (on an API 36 emulator no setting value changed across `launch`, `launch --restart` and a short crawl), and `monkey` is never sent. First, before every start, it reads the launcher activity with the same command as `Device.launcher_activity(package)`: `cmd package resolve-activity --brief -c android.intent.category.LAUNCHER PACKAGE; echo uiprobe-exit:$?`, a read. The output must be zero or more lines like `priority=0 preferredOrder=0 match=0x108000 specificIndex=-1 isDefault=true`, then exactly one line `PACKAGE/CLASS` of exactly that package (the class made of dot-separated parts of ASCII letters, digits, `_` and `$`; it may start with `.`, at most 255 characters), then `uiprobe-exit:0` last; anything else (`No activity found`, another exit status, output cut short, another package, more lines) raises `LaunchFailedError` with reason `launcher_unreadable`, and nothing that changes the device is sent. On a pinned device this read follows the rule of a request that changes the device: it goes out only while the device needs no new proof (else `DeviceNotFoundError` with `pin_not_proven`, nothing sent), and when anything happens to the pin during it (`pin_epoch` moves), nothing more is sent (`pin_not_proven`). `launcher_activity` alone is an ordinary read. With `restart=True` it then sends `am force-stop PACKAGE; echo uiprobe-exit:$?`, which stops the app so the next launch starts a fresh task (unsaved state in the app is lost); it must report exit status 0 and print nothing else (empty lines are ignored), or the start is not sent; it then reads the launcher activity again and starts that second read (the launcher can change while the app stops), and when the second read fails it sends no start and raises `LaunchFailedError` (`launcher_unreadable`) with `force_stopped` `True` (stopped, not started); any other error of that read (a device error such as a timeout) is raised with `force_stopped` `True` added to its `details`. It then sends `am start -W -a android.intent.action.MAIN -c android.intent.category.LAUNCHER -n PACKAGE/CLASS; echo uiprobe-exit:$?` once, never resent, and requires (after one CR at each line end is cut, empty lines ignored): no control character and no line starting with `Error` (API 24 prints its errors with exit status 0), `uiprobe-exit:0` last, exactly one `Starting: Intent { act=android.intent.action.MAIN cat=[android.intent.category.LAUNCHER] cmp=PACKAGE/CLASS }` naming the component sent (short or full spelling), exactly one `Status: ok`, exactly one `Activity: PACKAGE/CLASS` of the same package (the class may differ from the one started), and besides only, each at most once, one of the two captured `Warning:` lines, `LaunchState:`, `ThisTime:`, `TotalTime:`, `WaitTime:` and `Complete` in their captured shapes ([Launching an app](commands.md#launching-an-app) lists them). The reply of `-W` may stay silent for `timeout` seconds (at least `uiprobe.device.START_MIN_WAIT`, 1 second). Then it reads `device.foreground()` about every 0.5 seconds, at least once, until it equals `package`; no read starts after `timeout` seconds, which bounds when the last read may start, not the whole wait (a read that started in time still counts, and a pause can end late). A reply whose `Activity:` line names another app is waited on in the same way: the launch succeeds when the app comes to the front in time. On a device that is not pinned (as `uiprobe launch` uses), each request selects the device by its serial; no request of a launch starts an adb server (it uses only the server that is there; `AdbServerUnavailableError` with `start_skipped` `in_launch` when it is gone), and after its first request a request that fails (also one a read of the app in front swallows) ends the launch at once (`AdbError` with `reason` `launch_interrupted`), so nothing more is sent; on a pinned device this also counts an identity read that failed (a device error) or gave a reply that cannot be read while a wait proves a renumbered transport again (the wait itself goes on and may still prove the device; an identity that was read and differs ends the pin at once, as before), so such a launch fails even when the app came to the front, also when that read was its last (the reads of that wait were already sent; nothing that changes the device follows); accepted limit: if the device behind the serial is replaced between the launcher read and the start, the start uses the component read just before (it fails, or opens that component of the same package on the new device). A pinned device keeps its pin's rule. A launch that cannot be confirmed raises `LaunchFailedError` (`launch_failed`, exit code 15), whose `details` hold `package` and `reason`: `launcher_unreadable` (plus `output`, the first line that is not blank, stripped, cut to 200 characters and escaped; nothing was sent, or, with `force_stopped` `True`, the app was force-stopped and not started), `stop_failed` (plus `exit_status` or `output` when known; the start was not sent), `start_failed` (an `Error` line or a non-zero status, plus `output` and `exit_status` when not 0), `other_activity` (a reply that is a success in every other way names an activity of another app, or of the system owner `android` such as its chooser `android/com.android.internal.app.ResolverActivity`, and the app was still not in front after the wait; plus `output` and `activity`, escaped), `unexpected_output` (plus `output`, the line at fault or else the first line that is not blank, cut to 200 characters and escaped), `start_timeout` (the reply did not come; plus `timeout`, the silence allowed; whether the app started is unknown) or `not_in_front` (plus `foreground` and `timeout`); after `start_failed`, `other_activity`, `unexpected_output`, `start_timeout` and `not_in_front` the app may still have started. Other device errors propagate unchanged, apart from that `force_stopped` detail.

`Device.screenshot()` captures the screen with `screencap -p`, sent through the binary-safe `exec:` service, and returns the PNG bytes unchanged. On a device with more than one display (a foldable), `screencap` prints a text warning before the image; uiprobe then reads `dumpsys display` once and finds the physical id of the display that is on (its viewport has `isActive=true` and its logical display block `mIsEnabled=true`): display 0 when the phone is open, the outer screen when it is folded, which is the display the screen read (`dump`) uses. Exactly one display must be on, and the viewport line and the logical display section must name the same digits-only id; then it captures again with `screencap -p -d ID`. Otherwise (none on, several on, a flag missing, the two places disagree) `ScreenshotFailedError` has `reason` `multiple_displays_unresolved` and nothing more is sent. A device with one display sends only `screencap -p`. It writes nothing, on the device or on this computer, and does not change the latest dump. The bytes are checked in memory first, without decoding them, as [Taking a screenshot](commands.md#taking-a-screenshot) lists: the PNG signature, a well-formed `IHDR` chunk (13 bytes of data, width and height from 1 to 2**31 - 1, a bit depth that the color type allows, standard methods), chunks that fit in the data, the placement of `PLTE` and `IDAT`, and an empty `IEND` chunk at the end; checksums (except the fixed one of `IEND`) and pixels are not checked. Empty output, a cut-off image or other data raises `ScreenshotFailedError` (`screenshot_failed`, exit code 16), whose message says that the screen may forbid screenshots (for example a private browser tab) and that its structure can still be dumped; `details` hold `reason` (`empty` or `invalid`) and `bytes`. A screen that forbids screenshots gives empty output on older Android, but a mostly black image on newer Android; that is a valid PNG and is returned. `Device.display_for_image(width, height)` returns the display size that `dump` reports (from `wm size`), turned to the orientation of an image of that size, or `None` when `wm size` cannot be read. To save an image, open a new file in create-only mode (`open(path, "xb")`) so that nothing is overwritten; `uiprobe screenshot` does this and its checks are in [Taking a screenshot](commands.md#taking-a-screenshot).

```python
from uiprobe import Device, ScreenshotFailedError

device = Device()
try:
    png = device.screenshot()
except ScreenshotFailedError as error:
    print(error.message)  # the structure can still be dumped
else:
    with open("screen.png", "xb") as file:  # "xb" fails when the file exists
        file.write(png)
```

`uiprobe.preview(device, package, policy=None)` is the Python form of `uiprobe crawl PACKAGE`. It returns a `uiprobe.Preview` with `package`, `screen` (the `Screen` that was judged), `foreground` (the package in front, or `None` when unknown), `keyboard_shown` (`True`, `False` or `None` when unknown) and `judgement` (a `uiprobe.guards.Judgement`: `pressable` and `skipped` are tuples of decisions, each with `element`, `point`, `reasons` and `details`). `policy` is `None`, which means `uiprobe.Policy()`, or a `Policy`; `Policy(...).with_deny_words(words)` adds deny words (an exception word equal to an added word is dropped, so the word blocks as given), `Policy(skip_two_target_rows=...)` (default `True`) refuses a row whose descendants hold an element with a resource id ending in `:id/two_target_divider` (reason `two_target_row`; an Android Settings row with a second button, where pressing the row changes the setting) and `Policy(skip_rows_with_buttons=...)` (default `False`) refuses a row with a clickable descendant (reason `row_with_button`, given only when `two_target_row` is not; it also refuses ordinary list rows with their own button, and is meant for vendor Settings apps such as Samsung's One UI, where the divider rule is expected not to fire; not confirmed), the elements inside the row being judged on their own and a row with no structural sign (a saved Wi-Fi network row whose press reconnects) being caught by neither, `Policy(skip_navigate_up=...)` (default `True`) refuses the up button of a toolbar (reason `navigate_up`: an image button that is the first clickable child of a parent whose class ends with `Toolbar` or whose resource id ends with `:id/action_bar`, an element whose resource id ends with `:id/home` or `:id/up`, or one whose content description or label is exactly `Navigate up`), so that a crawl presses the rows of a sub-page before going back up with its own BACK, `Policy(skip_sliders=...)` (default `True`) refuses an element that is or holds an adjustable control (reason `slider`: a class ending in `SeekBar`, `RatingBar` or `Slider`) and an element whose press point lies on one anywhere on the screen, because a tap moves the control and changes a value, `Policy(replay_path=...)` (default `True`) is read by the pressing crawl only: after a relaunch the crawl presses again the rows that were pressed before to get back down to a screen that still has rows to try (a row on the way down is pressed once more for each replay), and counts a row seen with and without a badge as one row; `False` returns both to the earlier behaviour (the settings key is `[rules] replay_path`), `Policy(deny_exceptions=...)` sets the exception words (default `()`, `uiprobe.guards.DEFAULT_DENY_EXCEPTIONS`, so `Policy()` decides as substring matching alone; a deny word completely inside one of them, where it stands as a whole word inside one element's text, description or hint with real separators around it, does not count; only that occurrence is excused, so an element whose only hit was there is pressed, while a label split across child elements may still be refused (exact condition and limits under [Crawling an app](crawl.md)); an exception weakens every deny word, built-in or added; the screen-wide check behind `confirm_button` never uses them; an exception must be one word of letters and digits without invisible characters and must not equal a deny word, else `ValueError`; `uiprobe.guards.word_matches(value, word, exceptions=...)` and `deny_word_in(element, words, exceptions=...)` apply the same checks), and `Policy(tap_unlabeled=True)` allows unlabeled elements. `Policy(skip_number_only=False)` and `Policy(skip_toggles=False)` turn off the `number_only` and `toggle` rules (both default to `True`, meaning the rule applies). `Policy(refuse_dialog_confirm=False)` drops only the `dialog_confirm_button` reason, `Policy(skip_irreversible=False)` turns off the `irreversible_screen` reason (`Policy(irreversible_phrases=...)` sets its phrases), `Policy(edges=(top, bottom, left, right))` sets the screen-edge sizes in pixels (the default `None` keeps the API 36 sizes, and an explicit `avoid` wins) and `Policy(min_visible_px=N)` (default 8) sets the smallest visible size that the judging uses; `Screen.tap_point`, `Screen.find` and `Screen.visible_bounds` keep 8. `with_deny_words` keeps all of these. `uiprobe.settings.policy_from_settings(settings, *, extra_deny=(), tap_unlabeled=None)` builds the `Policy` that the settings describe, as `crawl` does: `settings` comes from `uiprobe.settings.load_settings(path)` (a `SettingsError`, a `ValueError`, when the file is unreadable or invalid), `extra_deny` adds words like `--deny`, and `tap_unlabeled=True` forces the rule for this policy like `--tap-unlabeled` (`None` keeps the file's value). Nothing is pressed or launched and no file is written on this computer (the dump writes its own temporary file on the device, tries to remove it afterwards, and if the removal fails the file can stay on the device). The function acts on whatever is showing now: it reads `device.dump()`, then `device.foreground()`, then `device.keyboard_shown()`, and judges the screen. A foreground other than `package`, or an unknown one, gives every candidate `outside_target_app`, except on a screen over the element limit, where every candidate gets only `screen_too_large`. `package` must be a `str` (`TypeError` otherwise) of two or more dot-separated segments, each an ASCII letter followed by ASCII letters, digits or underscores, at most 255 characters (`ValueError` otherwise); a `policy` of another type raises `TypeError`. Both are checked before the adb server is contacted. Device errors propagate unchanged.

`Device.foreground()` returns the package of the app in front and `Device.focused_window()` the window with input focus, with its owner (`None` when unknown); `preview`, `launch` and the crawl use them. On a device with one display, `foreground()` reads `mFocusedApp` in `dumpsys window` (and only when that says nothing, the resumed activity in `dumpsys activity activities`), and `focused_window()` reads `mCurrentFocus` in `dumpsys window` and the window's owner in `dumpsys window windows`. A `dumpsys window` output with more than one display header line (`Display:` then `mDisplayId`, in any spacing), or with any line holding `mTopFocusedDisplayId` that is not exactly `mTopFocusedDisplayId=0` (an unusual focused-display line), is read as one with several displays (a foldable with a cover screen), where each display has its own `mCurrentFocus` and `mFocusedApp`. Then every `mTopFocusedDisplayId` line, in any spacing, must be exactly `mTopFocusedDisplayId=0` (display 0 has the focus), else both are unknown. `foreground()` does not use `mFocusedApp`: it reads `dumpsys activity activities`, where every line naming `topResumedActivity`, `mResumedActivity` or `ResumedActivity` (in any spacing) must have the exact shape, both a `topResumedActivity` and a `ResumedActivity` line must be there, and all must name the same activity, else unknown. `focused_window()` accepts only the shape seen on a two-display phone: as many lines naming `mCurrentFocus` (in any spacing) as display header lines, all but one exactly `mCurrentFocus=null`, that one an exact `mCurrentFocus=Window{...}`, and that window's block in `dumpsys window windows` showing it on display 0 (`mDisplayId=0` on the line below its header); anything else, such as no focus, focus on both screens or focus on the cover screen only, is unknown. Each line may end with one CR. This reading is best effort against window titles: an app can put line breaks in a title and forge lines, and while no display has a focused window, a title that forges a display header and a focus line together is read as the focus. `focused_window()` decides between the two readings once, from its first `dumpsys window`, and gives `None` when a later read of the same call disagrees (the second full dump, or a `dumpsys window windows` that shows several displays). On several displays the lines of `dumpsys window windows` too lose at most one CR before each LF. So on several displays the crawl relies on the check of the window at the tap point: with `Policy(check_tap_window=False)` (`--no-tap-window-check`) it treats the focus as unknown and sends no tap or BACK once any `dumpsys window` read of its `Device` (full or `windows`, in an observation or a gate) has shown several displays, for the rest of the run (window blocks of `dumpsys window windows` on more than one display, by the `mDisplayId=` line below each block's header, count too; the note is cleared when a run starts, and checked once more by uiprobe itself after the caller's last clock call before the request; end line reason `focus_unknown` with `details` `{"cause": "several_displays_need_tap_window_check"}`, given before every other reason except `time_limit` and `device_reconnected`, which also refuse the request). Accepted limits of this reading, besides the forged pair above: if `dumpsys activity activities` has no genuine resumed line, a window title can supply agreeing `topResumedActivity` and `ResumedActivity` lines, and the foreground becomes that package (on one display the same holds when no genuine `mFocusedApp` line is there, as before); and a focused window whose title changes between the focus read and the owner read can have title text with line breaks taken as its owner lines, so the focus is given to another package and uid. While a foldable is being opened or closed, the foreground can be misread if the focus moves between the window read and the activity read; taps stay guarded by the tap-window check, the next read notices it, and the same gap is in the earlier commits of this change. Taps stay guarded by the uid check of the window at the tap point, which cannot be turned off on several displays; a BACK can still go to the window that really has the focus. Further accepted limits (L1, code you pass to the crawl): the note of several displays is cleared when a crawl starts, so a `clock`, `stop` or `sleep` of yours that starts another crawl on the same `Device` clears it; reads that your callbacks make (such as `device.foreground()` in your `clock`) count toward the note, and only those before the gate's last check of it are seen in time; `Device.diagnose_tap_window()` does not count toward it, so a `dumpsys input` that only it reads does not set the note. Window titles can also move the reading the other way: a line break in a title can split a window block's header from its `mDisplayId=` line (that window then counts on no display), and a title that imitates a second window block, or a second `Display:` section in `dumpsys input`, on a single display makes uiprobe take the device for one with several displays, which only refuses more. `dumpsys input` is read only for the tap window check, so its `Display:` sections count only while that check is on. That check guards taps only: a BACK relies on the focus reading, so on several displays a forged title that makes uiprobe misread the focus could make a BACK go to whichever window really has the focus. Limits: while another display has the focus (a closed foldable using its cover screen), both are unknown, so `launch` fails with `not_in_front` (its message then adds that another display, perhaps the cover screen, has the focus, when every `mTopFocusedDisplayId` line is exact and names the same display other than 0), the preview skips every element as `outside_target_app` (the preview's result does not say why) and the crawl presses nothing. That `topResumedActivity` and `ResumedActivity` are printed once for the whole device was seen on one capture only (SM-F776B, Android 17, phone open), where `mFocusedApp` appeared once per display. An output with no display header line, or one, and no `mTopFocusedDisplayId` line or only exact `mTopFocusedDisplayId=0` lines (as single-display emulators print: API 24 has no such line, API 37 has it) reads as before.

from uiprobe import Device, Policy, preview

result = preview(Device(), "com.example.app", Policy().with_deny_words(["coupon"]))
for decision in result.judgement.pressable:
    print(decision.element.id, decision.point)
for decision in result.judgement.skipped:

## Crawling from Python (alpha)

`uiprobe.crawl_run` (the function `crawl` of `uiprobe.crawl_driver`) runs a pressing crawl and records it in a new run folder. It is alpha; `uiprobe crawl PACKAGE --press --out DIR` runs it from the command line (see [Pressing crawl](crawl.md#pressing-crawl---press)). **It presses on the selected device**: it force-stops the app and starts it (unless `restart=False`), taps elements that the guards allow, presses BACK, and relaunches the app (`am force-stop`, then start), which can lose unsaved state. Read [Safety](safety.md) first.

```python
from uiprobe import Device, Policy, crawl_run
from uiprobe.crawl import Limits

result = crawl_run(
    Device(pin=True),
    "com.example.app",
    "runs/first",
    policy=Policy().with_deny_words(["coupon"]),
    limits=Limits(),
)
print(result.stop_reason, result.screens, result.actions, result.out)
```

`crawl_run(device, package, out, *, policy, limits, screenshots=False, allow_real_device=False, settle=1.0, stop=None, clock=time.monotonic, sleep=time.sleep, restart=True, record_text=True, on_progress=None)` returns `CrawlResult(out, stop_reason, screens, actions)`.

- `restart` (keyword-only, a `bool`; anything else raises `TypeError` before anything is sent): with `True`, the default, the first action force-stops the app (`am force-stop`) and then asks Android to start its launcher activity (which screen the app then shows is up to the app); what the app had not saved is lost. It is one action of kind `launch`, counted once toward `Limits.actions`, and its start line has `restart: true`. It goes through the same steps as a relaunch: the gate of the force-stop (`stop`, the time limit, the pin, a read of the launcher activity and the last comparison; when the launcher activity cannot be read, nothing is sent, as without `restart`), then, after the force-stop, `stop`, the time, the pin check, `stop`, the launcher read, the time and the last comparison before the start. A pin that moved before the force-stop sends nothing (`device_reconnected`, the run ends with `not_sent`); one that moved after it holds back the start (`start_not_sent`, the run ends with `not_sent`). When `stop` or the time limit ends the run between the force-stop and the start, the start is not sent: the end line has the reason `start_not_sent` and `summary.txt` says the app was force-stopped at the start of the run but not started. With `False` only the start is sent, so the crawl begins on the screen the app shows now. `run-start.json` records the choice as `restart`. Changed from earlier versions: they never force-stopped the app at the start, so existing callers that pass nothing now get the force-stop; pass `restart=False` to keep the earlier behaviour.

- `on_progress` (keyword-only, `None` or a callable `(Progress) -> None`; anything else raises `TypeError` before anything is written or sent): called after each sent action, once its end line is written and the screen after it was read (the first launch included), and never for an action that was not sent or once the run has stopped. The library prints nothing by default; `uiprobe crawl --press` passes a function that prints a line to stderr at most every 5 seconds. `Progress` (also `uiprobe.Progress`) is a frozen dataclass with `elapsed` (seconds since the run's start by the run's `clock`), `actions` (counted toward the limit), `action_limit`, `screens` (distinct screens of the app seen), `depth` (the length of the path at the engine's last decision, at least 1), `depth_limit` and `minutes` (the time limit); each is a value the run already keeps, so the callback costs no request to the device. It runs in the crawl's thread, between two actions and never between the gate's last comparison and the input (the send rule: it is caller code like `stop` and `clock`, and tests/test_send_rule.py checks it with them), so it should return quickly: the run waits for it. It is not called while a transition is open, nor when `stop` has already said yes, a wait was ended or the time limit has passed, and it reads no clock and does not call `stop`, so having it never changes what the run sends. An exception it raises is not swallowed: the run ends as for any other error of the loop, `run.json` gets `"stop_reason": "error"` (it has no field for the code) and `summary.txt` gets the note `error: internal_error` (the `Note:` line after `Actions:`), and the exception is raised again unchanged; a `KeyboardInterrupt` in it is handled like Ctrl+C (see `stop`: `interrupted`, raised again unless `stop` returns True).
- `record_text` (keyword-only, a `bool`; anything else raises `TypeError`): with `False`, the run folder holds no text of any screen: every element's `text`, `content_desc` and `hint` is written as `""` and named under `hidden`, `summary.txt` shows `[text not recorded]`, the window title of a `covered_by_other` end line is blanked and `run-start.json` has `"record_text": false`. It is a keyword of the call and not a `Policy` field because it is about the records, not about judging: the engine, the screen ids, the fingerprints and the gate use the real texts, and only the writer hides them, so the run sends the same actions with either value. With `screenshots=True` it raises `ValueError` before anything is written or sent (a screenshot shows the text). A password field's text is hidden whatever `record_text` is; see [What is recorded of a screen's texts](run-folder.md#what-is-recorded-of-a-screens-texts). `uiprobe.settings.Settings.record_text` is the setting, and the command line passes it here.
- Order: the arguments are checked (`TypeError`, `ValueError`), then the device is pinned and checked, then the app's uid is read and the run's time starts, then the run folder is made, then the app is force-stopped (unless `restart=False`) and started. Nothing is written and no input is sent before the first two pass (the device check itself reads one system property). Every start (the first launch's and each relaunch's, after its force-stop) is preceded by a read of the app's launcher activity (the same read as `Device.launcher_activity`), then the clock, then a comparison of the pin, and the start uses that read with `am start -W`, never `monkey`; no code of the caller runs between the last pin comparison and the start, and a start whose read ended past the time limit is not sent (`time_limit`; after a force-stop `start_not_sent`). A launcher activity that cannot be read raises `LaunchFailedError` (`launcher_unreadable`) and ends the run with `error`; the start is not sent (when the read in the gate of a first launch fails, with or without `restart`, nothing is sent and the launch gets a `not_sent` end line with that reason; when the read after a force-stop fails, of the first launch or a relaunch, `start_not_sent`). Pinning (`Device.pin_transport`, done by `Device(..., pin=True)` right after the device is chosen, or else by `crawl_run()` itself) keeps every later request on the adb transport the device was chosen on (`host:transport-id:N`), and the emulator check already goes through it, so a device that later takes the same serial receives nothing: its requests fail and the run ends with `error`. The pin reads the device's identity through that transport (`ro.kernel.qemu`, `ro.serialno`, `ro.build.fingerprint` and the kernel's boot id from `/proc/sys/kernel/random/boot_id`, in one command; `Device.pinned_identity`) and keeps it. Before every action and every read of the screen the run checks that the adb server still lists the pinned transport with the same serial and that the identity through it is the same, boot id included (and, unless `allow_real_device=True`, still an emulator); a restarted adb server numbers its transports anew, so this is what catches another device behind the same number. If not, the run ends with `error` (`DeviceNotFoundError`, `details.reason` `device_changed`). A device changed in the instant between that check and the next request is not caught. A server that reports no transport id, or an identity without a build fingerprint, raises `AdbError` before anything is written.
- A renumbered transport: an adb server can give a device a new transport number after it was offline for a moment (seen with an emulator under load: offline, gone from the list, then back under a new number, within a second). When the pinned identity has a boot id (`Device.can_repin`), a request that finds the pinned number gone from the server's list, or still listed for the serial but offline, waits for the device instead of ending the run; any other change (the number lists another serial, or the device is unauthorized) ends it at once. The wait lasts until 10 seconds after it began: the list is read every 0.5 seconds until exactly one entry with the serial is ready (an old entry that is still offline does not count). The identity is then read through that number, passed to that one request (the pin itself does not point there before it is proven), and must equal the pinned one, boot id included; the time limit (and a `stop` that already returned `True`) are looked at once more, and only then does the pin move (`Device.repins`). Two ready entries with the serial, another identity or boot id, no return within the 10 seconds, a 6th move to another number, or an 11th wait in one `Device` (`Device.reconnects`, coming back on the same number included) end the run with `device_changed`. A request that changes the device (an input, `am force-stop`, the start of the app) never waits and never moves the pin. It goes out only when the pinned number is listed and ready and nothing happened since the identity was last proven on that number: no request on the pin failed, no wait began, the pin did not move (`Device.pin_epoch` moves on each of these). Otherwise nothing is sent: when the device can be proven again (the cases below), the request fails with `DeviceNotFoundError` whose `details.reason` is `pin_not_proven` and the pin is kept, so the next read proves the device first; the crawl closes such an action like the gate does (`device_reconnected`). In any other case it fails with `device_changed`, and the pin fails. A read after such an event proves the device again before it goes out, by the wait above (also when the number is listed and ready again); that needs a pinned boot id. A read may write and remove a temporary file on the device (`uiautomator dump`), and these requests follow the renumbered transport like the other reads, after the identity was proven. A request that fails in the middle (the device went offline while it ran) is not repeated: when its error reaches the crawl, the run ends with `error`, as before; when a reader swallows it, the device is proven again before the next request (without a pinned boot id the next request fails the pin instead). While it waits (at most 10 seconds), the run does not call `stop`: `stop` may read the device, and a request during a wait fails the pin. Only the time limit and a `stop` that already returned `True` before the wait are looked at; when either says so, the run ends with `max_duration` or `interrupted`, and an action that was still in the gate gets a `not_sent` end line. `stop` is called again after the wait, and Ctrl+C works during it. The check before the run (the emulator check) asks nothing while it waits; a watch set with `Device.set_pin_watch` before the call is put back afterwards. Once the pin has failed (`device_changed`, or a wait that was stopped), the `Device` refuses every later request with the same error, even when the device comes back, so no request goes out after the pin was given up, also when a reader swallowed the first error. A `pin_transport()` that fails is kept the same way (an interrupt during it included): such a `Device` sends nothing afterwards, not even by serial. Once pinned, the `Device` no longer starts an adb server by itself: a server that restarted would number its transports anew, so when the server stops during a crawl, the crawl ends (the failed requests move `Device.pin_epoch`, and proving the device again fails) instead of going on with a new server. A server that replaces the first one between two requests (already listening, or started by someone else before the next request) causes no failure when no request falls into the outage, so that switch itself is not noticed; a list or an identity that changed with it still is. A check of the server's list before a request that does not succeed counts as a failed request, and so does a request that ends in any other way than success (any error, an interrupt), and an input, `am force-stop` or app start whose answer does not report success (it may have been cut off). An interrupt (Ctrl+C) that leaves a request on the pin also fails the pin: a `Device` that was interrupted is not used again; make a new one. Only the message and the details of the failure are kept. Each move is a `Note:` line in `summary.txt` and is counted as `repins` in `run.json` (moves made during this run only); `run-start.json` has `repin`, whether moves were allowed in this run. When the boot id cannot be read when the device is pinned (an empty or malformed answer), moves are not allowed: a renumbered transport ends the run with `device_changed`, as it always did, and the three other fields are compared even if a boot id becomes readable later. Such a device is also never proven again: after any event that moves `Device.pin_epoch` (a failed request, a wait), the next request, a read or an input, fails the pin with `device_changed` and the run ends, because another emulator of the same image that took the same serial and number in the meantime would read exactly the same. A boot id that was read at the pin and can no longer be read counts as a change.
  - When anything happened to the pin (`Device.pin_epoch` moved: a failed request, a wait, a move) after the observation an action was chosen on, the gate does not send that action (`device_reconnected`): what was read before may be stale. When it happened during the gate's own reads, a refused tap's screen is read again from scratch. An observation that an event crossed is read again before anything is chosen on it, so such an event costs an action only when it falls between the observation and the input. When it happens between a relaunch's force-stop and its start, the start is not sent; when the device is successfully proven again, the action gets `start_not_sent` (and `summary.txt` says `device_reconnected`) and the run ends with `not_sent`, while without a pinned boot id the pin fails and the run ends with `error`. Nothing was sent and nothing about the screen is known, so, when the device can still be proven again (it has a pinned boot id; without one the next request fails the pin and the run ends with `error`), the engine takes such an action back (`CrawlEngine.withdraw`: its whole state goes back to before it chose the action, so nothing is counted, recorded or marked tried) and decides again from a fresh read; a tap's element can therefore still be pressed. Exceptions: when the force-stop of a relaunch was sent and its start was not (`start_not_sent`), and when the first launch was not sent, the run ends with `not_sent`. Every such refusal comes from an event that makes the device be proven again, so the wait limit of the `Device` (10) and the time limit bound how often it can happen.
- What is sent: only the first launch, taps at the points the engine chose, mouse wheel turns (scrolls) with `Policy.scroll_lists` (see the next item), BACK and relaunches. Never text, long presses, swipes or other keys. By default BACK is sent only while a screen of the target app is in front (see the next item). Each action is written to `transitions.jsonl` before it is sent and is sent once, never retried. By default the first launch force-stops the app and then asks Android to start its launcher activity; the depth limit counts from the screen the app shows after that start, which is up to the app (see `other_activity` below). With `restart=False` the first launch does not force-stop the app, so it continues an existing task: if the app already has screens in its back stack, the depth limit counts from the screen that is showing, not from the bottom of the stack. A launch after which the app is not in front (a permission dialog or a splash screen of another package holds the focus), or whose reply names an activity of another app (`other_activity`: on an API 36 emulator, Settings' search screen of another package came back after a force-stop), does not end the crawl: it is noted in `summary.txt` as `... was not in front after launch (PACKAGE)` and the engine goes on from what it sees (off target: no tap, a relaunch; so such a run can end with `relaunch_limit`). A start whose reply did not come in time (`start_timeout`) ends the crawl with `error`: whether the app started is unknown, so nothing more is sent or read; `summary.txt` says that the reply did not come. A start that `am start` reports as failed (`start_failed`, `unexpected_output`) ends the crawl with `error` too. A launch or relaunch that fails and ends the crawl gets an end line with `failed`, its `reason` and `outcome: "unknown"`. An app that is not installed or has no launcher activity is found by the first launch's launcher read, which comes after the run folder was made (with `restart` in the gate of the force-stop, without it in the gate of the start): nothing is sent, the launch gets a `not_sent` end line with the reason `launcher_unreadable`, and the run ends with `error` (`LaunchFailedError`). An error of the device or of adb in that read (a lost adb connection, for example) also closes the launch as not sent, with the error's word (`adb_error` for a lost connection, `device_changed` for a changed device), before the error is raised. When the force-stop went out and an error or Ctrl+C comes before the start (up to and including the last comparison of the pin before it), the launch (or relaunch) is closed as `start_not_sent` and `summary.txt` says the app was force-stopped but not started, with the error's word or `interrupted`. The error is then raised again; Ctrl+C ends the run as described under Ending: `crawl_run()` returns with `interrupted` when `stop` is given and returns `True` at that moment and `run.json` was written, and otherwise raises the interrupt again. The record format is in [The run folder](run-folder.md).
- Scrolling, an opt-in that is off unless you ask: `Policy(scroll_lists=...)` (default `uiprobe.guards.DEFAULT_SCROLL_LISTS`, `False`; anything but a `bool` raises `TypeError`) and `Limits(scrolls_per_screen=..., scroll_amount=..., scroll_incidents=...)` (defaults 10, 3 and 2; at least 1, `scroll_amount` at most 10) let the engine hand out a `Scroll(screen_id, point, amount)`: a mouse wheel turn at one point, `amount` steps, content further down (there is no direction, duration or swipe; a bad point or amount raises). It is handed out only on a screen of the app that has no untried row left that may be pressed or is at the depth limit, has a vertically scrollable element, is not a dialog or judged irreversible, has a container (the innermost scrollable list container of the largest scrollable element) of an allowed class and a point `uiprobe.guards.scroll_target` accepts (every element whose rectangle holds the point must be the container, inside it (a plain class, or a list class that does not scroll; nothing scrollable) or above it (a list class, scrollable or not, or a plain class that does not scroll); the allow lists are `uiprobe.guards.SCROLL_CONTAINER_CLASSES` and `SCROLL_POINT_CLASSES`, exact class names, fixed constants and not settings; see [Pressing crawl](crawl.md#pressing-crawl---press)), has had fewer than `scrolls_per_screen` scrolls sent on its container (counted under `uiprobe.guards.container_key`) and on its family of screen ids, on its set of lists and in its activity (a refused proposal does not count either; the activity count is shared by all pages of one activity), was not marked by a scroll that changed something, and the run has had fewer than `scroll_incidents` such scrolls. The driver gates it like a tap, `CrawlEngine.recheck` takes a `Tap` or a `Scroll` (for a scroll the whole screen must be identical to the planned one, the display size and every element's id, parent, class, package, text, description, hint, flags, `editable` and bounds, and a screen of a permission package is never scrolled; any change is `changed_before_press`), `CrawlEngine.scroll_sent` reports it (only the very instance `recheck` allowed) and `CrawlEngine.scroll_effect(screen, foreground)` says what it did beyond scrolling (`changed`, `navigation` or None; a package of `also_target` in front is the target's own, another page of the same activity with none of the scrolled list is `navigation`), which the driver writes as `scroll_effect` in the end line. It is sent with the private `Device._wheel_scroll(point, amount, _send_by=..., _epoch=...)`, checked on the request's own connection like a tap's; `Device.scroll` and `Device.swipe` are not changed. `crawl_run` reads whether the device's `input` usage lists the `mouse` source and a `scroll <x> <y>` line with `VSCROLL` as a word of its `[--axis ...]` list (`Device._wheel_supported()`) itself when the run starts, once, if `scroll_lists` is on; there is no argument to claim support (`uiprobe crawl --press` is told the driver's own answer through a private callback and prints its plan from it, so the plan and the run use one read), and with `scroll_lists=False` nothing is read. A device that does not list them makes the run scroll-less and `run-start.json` says `scroll_input: false`. `CrawlEngine.scroll_effect` also takes the incident when it is first asked, before `next`, so a `next` taken back with `withdraw` does not lose it. A wheel event goes to the window under the pointer, not to the focused window, so the window check reads the window at the one point. It is counted as an action, recorded as a transition of kind `scroll` (`Transition.amount`, `Transition.scroll_effect`) and a scroll that only scrolls never pushes the engine's path. `uiprobe.settings.Settings` holds the settings, and the command line passes them here.
- The window at a tap's point: a tap goes to a point of the display, and the window that takes a touch there need not be the focused one: a window of another app can take touches without taking the focus (an overlay drawn over other apps, a floating button, the keyboard). Right before each tap, as the gate's last read, the crawl reads which window takes a touch at the tap's point (`Device.window_at(point, owned=...)`: the topmost window of display 0 in the list `dumpsys input` prints that takes touches and whose touchable region holds the point; `owned`, the crawl's owner uid and title test, says which windows may print `samsungFlags=0x1`, see the limits below; the crawl always passes `owned=`, so a subclass of `Device` that overrides `window_at` must accept the keyword `owned` and forward it: an override that does not accept it raises `TypeError` on the first guarded tap, and one that accepts it but does not forward it makes the app's own windows with `samsungFlags=0x1` refuse every tap (`cover_unknown`, rule `samsung_flags`)) and sends the tap only when that window belongs to the app. What this guarantees is exactly that: the topmost window that takes touches at the tap's point belongs to the app. Windows that only watch touches (such as the system's gesture monitors, which are spy windows) and copies of a touch sent to the wallpaper are not checked. The window belongs to the app when its owner uid equals the app's uid, read at the start with `Device.package_uid` from the package's own stanza in the `Packages:` section of `dumpsys package` (`userId=` on API 24 to 33, `appId=` on API 34 to 36, both read). No uid is read when there is not exactly one such stanza (headed at the stanza indent), when its number is 100000 or more (a uid of another user), when its lines claim two different numbers, when a `sharedUser=` line is not of the form `SharedUserSetting{<hash> <name>/<the same number>}` at the stanza's field indent, when the `Shared users:` section lists a shared user with the package's number while the stanza has no `sharedUser=` line, when it holds two different numbers, when it has no `User 0: ... installed=true` line (the package is not installed for user 0), or when the output ends inside the stanza (`dumpsys` can stop part way). The uid is read again right before each tap's window read (one more `dumpsys package` request per tap); when it cannot be read or differs from the first reading (the app was installed again), the tap is refused (`cover_unknown`, `target_uid`). The focused window must also belong to user 0 (`u0` in its record and an owner uid below 100000 in its block, both times the gate reads it), and its owner uid (`mOwnerUid=` in its block; on the emulators checked, API 24, 30 and 33 to 36, the app's own window has the app's uid there) must be the app's uid, or the tap is refused (`target_uid`); otherwise the tap is refused before the window is read (`cover_unknown`, `target_user`). That number is the uid of the app's windows for Android user 0 only: when the app runs for another user (a work profile, a second user), its windows have another uid and every tap is refused (`covered_by_other`). When the package shares its uid with other packages (`sharedUser=` in its stanza, `android:sharedUserId`) or has a uid below 10000 (a system uid such as Settings' 1000, which system windows have too), the window's title must also name the app: be the package, or begin with the package and `/` (as an activity's window does); a window of the app with another title (a popup, for example) is refused, and a window of another package with the same uid is refused unless its title names the app (see the limits below). A window of another app there refuses the tap (`covered_by_other`, with `details` naming the window and its owner uid). Anything that cannot be told refuses it too (`cover_unknown`, with `details.unreadable` saying which and, when the window list or the `Viewport` lines refused, `details.rule` naming the check, as listed in [Diagnosing the tap window check](commands.md#diagnosing-the-tap-window-check); `CrawlResult.cover_rule` holds that of the first `cover_unknown`; `uiprobe diagnose tap-window` and `Device.diagnose_tap_window()` tell it for a device without printing device values; pass `Device.diagnose_tap_window(owned=...)` the same kind of test as `window_at`'s `owned`, as `uiprobe diagnose tap-window --package PKG` passes the crawl's own, to have `samsungFlags=0x1` read on the app's own windows): `no_list` (no window list of display 0, or more than one that could be it), `line_format` (a line in the list of no known form, a field twice in a line, a field whose value is followed by more text before the next field, a flag name that is not known in a row of display 0 (rows of another display's list may name unknown `inputConfig=` flags; see the limits below), rows that do not run 0, 1, 2, ..., a missing `portalToDisplayId` on API 29 to 32, a list that does not end at a line it is known to end at, or a line outside the list that holds `ownerUid=`: a window name can hold line breaks and so fake a row and the end of the list, and then the real rest of its line lands outside the list), `region_format` (a touchable region that is not one rectangle or empty, or is reversed), `rotation` (the display is rotated or scaled, or its orientation cannot be read, see below), `no_window` (no window takes a touch there), `portal` (the window there forwards touches to another display, API 29 to 32), `target_uid` (the app's uid could not be read, at the start or right before the window, or it changed: then the window is not read) or `target_user` (the focused window belongs to another Android user than user 0). On API 24 to 32 a visible touchable window with neither `NOT_FOCUSABLE` nor `NOT_TOUCH_MODAL` takes a touch anywhere on the display, as the dispatcher of those versions does, so it holds every point. On a rotated display every tap is refused (`cover_unknown`, `rotation`), so an app in landscape cannot be crawled yet. Two sources say the display is rotated, and either one refuses: the `rotation` attribute of the gate's own `uiautomator dump` (other than 0, read with no extra request), and the orientation in the input reader's `Viewport` lines of display 0 in the same `dumpsys input`, which must all be of a known form, say 0 and have a logical frame equal to the physical frame (a display that is not scaled or moved); a display whose orientation cannot be read is treated as rotated (those lines were seen on emulators at API 24 to 36; where they are missing every tap is refused). A number with more digits than Python converts (4300 by default) is never taken as 0 or as a match: a rotation or orientation the check reads in a window list (another display's included), or a `Viewport` line's display number, refuses the tap (`rotation`), and such a number in the `Shared users:` section of `dumpsys package` makes the app's uid unreadable (`target_uid`). A window that covers only part of the screen (a floating button, a notification at the top) refuses only taps inside it. `Policy(check_tap_window=False)` turns this check off: then the tap goes out without that read, and a window of another app over the point gets it; `run-start.json` records the choice (`check_tap_window`). This adds one `dumpsys package` request to every tap whose app uid could be read at the start, and one `dumpsys input` request when the uid read right before it is the same.
- Screens of other apps: `Policy(back_on_other_screens=True)` makes the crawl press BACK while a screen of another app is in front, and that BACK, when the gate sends it, reaches the owner of the focused window, whichever app that is. A system permission dialog counts as a screen of another app, so it gets that BACK too. By default (`False`) the crawl sends nothing to such a screen: when the screen or the foreground app is not the target app (a permission dialog, the launcher after a BACK left the app, another app that came forward, an unknown foreground), the engine decides to relaunch the target app (`am force-stop`, then `am start -W` of the launcher activity), and the relaunch passes the gate like any other action (when the gate refuses it, nothing is force-stopped and the run ends with `not_sent`, or with `interrupted` or `max_duration` when `stop` or the time limit held it back). The engine relaunches at most 3 times in a row without a sent tap: when it would need a 4th, the run ends with `relaunch_limit` and the 4th is never sent; an app that shows another app's dialog at every start therefore ends that way, unless another stop reason comes first. With `True` the crawl presses BACK up to 2 times in a row there, then relaunches, as before this choice existed. The BACK that hides the keyboard and the BACK that goes up the path are decided on screens of the target app in both cases, and are sent only while the app owns the focused window (see the gate). Each BACK or relaunch decided on a screen of another app has `off_target` in its start line (the package of that screen, the app in front and the owner of the focused window, which is where a BACK goes), and `run-start.json` records the choice (see [The run folder](run-folder.md)). The settings file has it too (`[rules] back_on_other_screens`, read by `policy_from_settings()`, so a `Policy` built from a file that says `true` has it on); the command line options override it for one run.
- More apps as the target: `Policy(also_target=("com.example.helper",))` (a tuple of package names, empty by default; `uiprobe crawl` fills it from `[rules] also_target`) makes the crawl and `judge` treat a screen of a listed package, when the dump and the foreground app both name it, as the target app's own, with every guard (see [Listing more apps](safety.md#listing-more-apps-also_target)). `Policy` refuses a listed system UI, fixed home app, bad name, duplicate and over-long name when it is built, `CrawlEngine` the target itself, and `preview()` also reads the home app (the fail-closed read below) before it reads a screen; `crawl_run()` checks the list before it contacts the device (a name that is not a package name, a duplicate, the target itself, `com.android.systemui` and the fixed home apps raise `uiprobe.also_target.AlsoTargetError`, a `ValueError`), then, when the list is not empty, reads the device's home app once (`Device.home_package()`, a read-only `cmd package resolve-activity ... -c android.intent.category.HOME`; the same error if a listed package is that app, and `AlsoTargetError` when it cannot be read or does not name exactly one component: it fails closed; a home app changed during the run is not noticed) and, with `check_tap_window`, the uid of each listed package (the same error when one is not installed), all before the run folder is made. With an empty list nothing extra is read or sent. A listed package is never started or stopped, and permission packages never count as the target.
- Exception phrases: `Policy(except_phrases=("Quick Share",))` (a tuple of phrases, empty by default; `uiprobe crawl` fills it from `[deny] except_phrases`; each phrase is 1 to 80 characters with a letter and no control or invisible character, and two equal after `uiprobe.guards.normalize` raise `ValueError`) lets `judge` pass a plain clickable element whose only reason is `deny_word`: it is not long-clickable, checkable, scrollable, editable or a text or password field, nothing inside it is clickable or any of those, it has at most 500 elements, no clickable element contains it, its tap point is held by it or by something inside it, and it has only its name as text (exactly one element inside it has any text, description or hint, and its description and hint say the same as its text), the name has some area on the display with its middle inside the row, the last element drawn at the tap point and at the name's middle is the row or inside it (Samsung's empty `round_corner` view, whose package part is `android` or a valid package name, is passed over, nothing else; the name's middle is that of its full bounds and must be on the display), no other interactive element is drawn over the row there, and the name equals a phrase after normalization, and the deny words found in the row are exactly those found in the name text alone. `judge` then judges the same screen once more with only that name text replaced by a neutral label, and lets the element through when it has no reason left (an over-refusal is possible where neighbouring text forms a deny word with the name out). With more than 8 structurally eligible rows on a screen (counted before the reasons are looked at, the scan stopping at the ninth) no phrase applies. The `Decision` then has `except_phrase` (the phrase as written; `""` for every other decision, always with no phrases; it is a public field, so `dataclasses.asdict(decision)` has `except_phrase=""` for every decision, phrases or not), and the element's id is in `Judgement.unsafe`, so the wheel never turns over it. The crawl's re-check compares the fresh `except_phrase` with the planned one. `Policy.with_deny_words` drops a phrase that holds an added word. `crawl()` writes `deny_except_phrases` to `run-start.json` when there are phrases, and `except_phrase` into the start line of a tap on such an element (see [The run folder](run-folder.md)). `uiprobe.crawl.Tap` is unchanged.
  - The cost of the default: a relaunch force-stops the app and asks for its launcher activity again, which leaves the path the crawl was on (which screen the app then shows is up to the app), and the crawl never presses the same element of the same screen twice (an element is known by its screen id and its fingerprint), so when a tap opens another app's dialog, the rest of the screen that tap was on can stay unpressed when the way back to it goes through elements already pressed. With `True` a BACK may close the dialog, and then that screen is tried further.
- Every action passes one gate right after its start line is written and right before it is sent. The gate first asks `stop` and the clock, then checks the pin (above), then reads the device again, and does not send when something it needs cannot be read or has changed: then the start line gets an end line with `not_sent: true` and a `reason`, and nothing is sent. After its decision nothing else runs (no call of `stop`, no other read) before the input is sent.
  - Any action: not when `stop` returns `True` (`stopped`; once it has returned `True` it counts as `True` for the rest of the run) or the time limit has passed (`time_limit`). Any action but the first launch: not when the device was away after the observation it was chosen on (`device_reconnected`, see above).
  - A tap: the focused window is read, the screen is dumped again, then the foreground app, the focused window and the keyboard are read, and last the window at the tap's point (`dumpsys input`, unless `check_tap_window=False`; not read when the app's uid could not be read), so the reads nearest the press come last. The engine re-checks the tap on that dump (`changed_before_press`); the soft keyboard must be known to be hidden (`keyboard_unknown`, `keyboard_shown`); the window that has input focus must be owned by the app both before and after the dump (`focus_unknown`, `focus_other`: the notification shade, a system dialog or another app's window holds the focus) and must be the same window both times (`focus_changed`), so that the dump shows that window (uiautomator dumps the focused window: seen with the notification shade on API 24, 30 and 36; not checked with an app's own dialog). The owner is the `package=` that the system writes in the window's block of `dumpsys window windows`, not the window title, which an app chooses; this form was captured on emulators at API 24, 30 and 36 and is assumed for the other versions. Where it cannot be read, the crawl does not tap.
  - BACK and relaunch: the foreground app and the focused window (owner and title; and for BACK the keyboard) must be readable (`foreground_unknown`, `focus_unknown`, `keyboard_unknown`) and the same as when the action was chosen (`changed_before_send`). A BACK decided on a screen of the app (the keyboard BACK, a navigation BACK) goes to the window with input focus, so that window must also be owned by the app (`focus_other`), as for a tap, and also be of Android user 0 with the app's uid, as for a tap (the end line's `details` say `target_user` or `target_uid`; the uid is compared only with `check_tap_window` on, the user always); a BACK decided on a screen of another app (only with `back_on_other_screens=True`) is not held to that, because sending it there is what the setting allows. The engine has already counted a BACK or relaunch it returned, so when the gate does not send one for any other reason than `device_reconnected` (which the engine takes back, see above), the run ends with the stop reason `not_sent` (or `interrupted` or `max_duration` when that is why) and `summary.txt` says which check refused it. A device whose readings are not steady can therefore end runs early.
  - A relaunch, and the first launch with `restart=True` (the default), sends `am force-stop` and then the launch, with `stop` and the time limit asked again in between; when they end the run there, only the force-stop was sent, the end line has the reason `start_not_sent` and `summary.txt` says so.
  - A tap or a scroll is reported to the engine as sent only after it was sent without an error; one that was refused, or whose sending failed, is never reported.
  - When `stop` or the time limit holds an action back, the run ends right there, without another read of the device. The same holds when `stop` returns `True` during the pause after an input: the run ends without reading what the input did, so that action's start line has no end line. Between a relaunch's force-stop and its start, the device's identity is checked again too.

Which checks each action passes in the gate, after `stop`, the time limit and the pin (same transport, serial and identity; a renumbered transport followed as described above), which every action passes:

| Action | Reads | Must hold |
| --- | --- | --- |
| First launch | the launcher activity | readable (with `restart=True`, the default, this is the gate of its force-stop; the start comes after the checks below) |
| Tap | focused window, dump, foreground, focused window, keyboard, the window at the point (`dumpsys input`, unless `check_tap_window=False`) | the device not away since the observation; the engine's re-check on the new dump; keyboard known to be hidden; the focused window owned by the app and the same before and after the dump; the window that takes a touch at the point owned by the app |
| BACK decided on a screen of the app | the app's uid (`dumpsys package`, unless `check_tap_window=False`), foreground, keyboard, focused window (last) | the device not away since the observation; all readable and the same as when chosen; the focused window owned by the app, in Android user 0, with the app's uid as for a tap (`focus_other`; its end line's `details` say `target_user` or `target_uid`; they appear only for this refusal: a BACK held back as `changed_before_send` because the focus moved has no `target_*` details) |
| BACK decided on a screen of another app (only with `back_on_other_screens=True`) | foreground, focused window, keyboard | the device not away since the observation; all readable and the same as when chosen |
| Scroll | focused window, dump, foreground, focused window, keyboard, the window at the one point (`dumpsys input`, unless `check_tap_window=False`; a wheel event goes to the window under the pointer, not to the focused window) | the device not away since the observation; the engine's re-check on the new dump (the same screen, no keyboard, the same planned container and point, the whole screen as planned, parents included; for a scroll the window at the point must also be the focused window that supplied the dump, told by its title); keyboard known to be hidden; the focused window owned by the app and the same before and after the dump; the window that takes a touch at the point owned by the app. Refusal reasons are a tap's (`changed_before_press` when the re-check refuses); a refused scroll is released like a tap and the crawl goes on |
| Relaunch | foreground, focused window, keyboard (not used) | the device not away since the observation; foreground and focused window readable and the same as when chosen |

After the gate, a relaunch, and the first launch with `restart=True`, sends the force-stop, then asks `stop` and the time limit and checks the pin and the identity again, reads the launcher activity, and only then sends the start.

What the checks cover, and what they cannot: right before an action is sent, the gate has, in this order, (1) asked `stop` and taken the time once, (2) checked through the pinned transport that the device's identity is unchanged, (3) read the focused window, dumped the screen (tap only), read the foreground app, the focused window and the keyboard, and, for a tap, read the window at the tap's point from `dumpsys input` (unless `check_tap_window=False` or the app's uid could not be read), and (4) decided; nothing runs between the decision and the input. In addition, while the transport is pinned, every request to the device is preceded by a request to the adb server that checks the pinned transport still lists the same serial. adb cannot check and send in one step, so the following remain:

- The crawl's tap is a 10 ms swipe from the point to itself (`input swipe X Y X Y 10`). If Android sends a move event during it and the window at the point is marked `SLIPPERY`, a window of another app that appears at the point during those 10 ms can receive the rest of the press. Like the instant described in the next item, this falls after the last check.
- The device, the screen or the focus can change in the instant between the last check or read and the request that follows it (another device behind a restarted server, a dialog, the notification shade). Nothing can be done about that instant from outside the device.
- The window at a tap's point is read from the list `dumpsys input` prints; its four forms were seen on emulators at API 24 to 36 (API 24 to 30, 31 and 32, 33 and 34, 35 and 36), not on real devices. A device that prints it another way gets `cover_unknown` on every tap (see `check_tap_window`). In a list per display, an `inputConfig=` name that is not known (the forms of API 33 on) refuses only in a row of display 0; in another display's list it is let through when it is one upper-case word, and every other part of those rows is still checked as strictly as display 0's. Rows of the `flags=` forms (API 24 to 32) are checked as before in every list. A two-display Samsung foldable (Android 17) printed its cover screen's list (`Display: 1`, off while the phone is open) above display 0's with `SKIP_UNTRUSTED_TOUCH_TOAST`, which uiprobe does not know. This relies on an assumption that was not checked on a device: that a touch sent to display 0 is delivered only to display 0's windows (recalled Android behaviour). On the Samsung form (`samsungFlags=`, `pTouchableRegion=`, `1HXY=`), `samsungFlags=0x1` was printed by two Samsung phones on the app's own window only (Settings, with its own uid); what it means is not known, so it is accepted only on a window that passes the same owner uid and title test as the window at the point. Any other window of display 0's list with it, at the point or not, taking touches or not, refuses every tap (`cover_unknown`, `line_format`, rule `samsung_flags`); other values not seen (`FORCE_TRUSTED_OVERLAY | 0x400000`, `0x40000`) refuse as before (`samsung_fields`). A heads-up notification was not seen in that list on a real device or an emulator; a floating button and the keyboard were.
- What the check trusts and what it does not: it trusts that the output of `dumpsys` arrives as the Android system wrote it. It does not trust text an app can set (window names, `applicationInfo.name`): such text can hold line breaks and field-like words, and the parts of the output it could fake are checked against each other. One case remains: if a window of another app is the lowest in the list, no window above it takes the point, and its name fakes a complete window line, the check cannot tell; the tap then goes where it would go without the check. Output of the system that is damaged in ways that contradict themselves is an accepted limit; a contradiction the check notices makes it refuse.
- The check guarantees only that the topmost window that takes touches at the tap's point belongs to the app. Windows that only watch touches (such as the system's gesture monitors, which are spy windows) and copies of a touch sent to the wallpaper are not checked: such a window still sees the touch.
- An app that runs with a system uid (such as Settings, uid 1000), or that shares its uid with other packages, cannot be told apart from the other windows with that uid by the uid alone; for it the window's title must also name the app's package. The title is chosen by whoever made the window, so windows of another package sharing the app's uid (a package of the same developer, signed with the same key, or a system package) are told apart only by their name: one that names the app's package in that way is not told apart.
- Text an app sets can make the check refuse taps it would allow, never the reverse: a window name or `applicationInfo.name` holding a line break or a field-like word (`Preview flags=draft`, `Inspector ownerUid=pending`, `displayOrientation=1`) makes the whole list unreadable or the display look rotated, so every tap on that screen is refused (`cover_unknown` with `unreadable` `line_format` or `rotation`). Some other app texts refuse too: a focused window title longer than 512 characters makes the focused window unreadable (`focus_unknown`); a `versionName` with a line break whose next line is not indented, or a second line that reads like a `sharedUser=` field, makes the app's uid unreadable or makes the app look as if it shared its uid, so taps on windows whose title does not name the package are refused (`cover_unknown` `target_uid`, or `covered_by_other`); `applicationInfo.name` holding `ownerUid=` makes the list unreadable. The refusals are recorded in `transitions.jsonl` with those reasons. Text inside the app's package entry (a `versionName` such as `Release (appId=7)`, a requested permission named `sharedUser.demo.permission.SYNC`), braces in a window title (`Order {7}`, or another window titled `Window{...}`) and an apostrophe in a quoted window name (`Today's Orders`, API 24 to 34) are read as text and do not make the check refuse.
- Only Android user 0 is supported: on another user (a work profile, a second user) the app's windows have another uid, and a focused window of another user refuses the tap (`target_user`), so every tap is refused. On a rotated display every tap is refused (`rotation`: the gate's dump says the hierarchy is rotated, or the `Viewport` lines of `dumpsys input` are not those of an unrotated, unscaled display), so an app in landscape cannot be crawled yet.
- With `Device(..., pin=True)` the identity is read right after the device is chosen. A `Device` made without it is pinned by `crawl_run()`: if the adb server restarts in between and another emulator comes up with the same serial and transport number, that emulator becomes the one checked (it must still be an emulator, unless `allow_real_device=True`).
- Emulators made from the same image have the same serial number and build (on the emulators checked, `ro.serialno` was the same for all of them, and `ro.build.fingerprint` differed only between versions); the boot id tells them apart, and tells one emulator before and after a restart apart. A device whose boot id cannot be read is told apart only by those three, so another emulator of the same image with the same serial behind the same transport number cannot be told apart, and a renumbered transport or a failed request on the pin ends the run.
- A renumbered transport is followed only for reads and checks, and a read that fails in the middle is not repeated, so a device that goes offline while a request runs still ends the run. A device that was away makes the gate refuse the next action, which the engine then decides again (see above).
- `crawl_run()` turns `package`, `settle` and the numbers of `limits` into plain values once, at the start, and `Device` does the same with `serial`; the gate evaluates all its conditions before its last comparison, and no caller code runs after it. Objects the caller passes that cannot be turned into plain values (the `policy` with its words, `stop`, `clock`, `sleep`) run when they are called; such an object that reads the device from inside is not caught. A watch (`Device.set_pin_watch`) is the exception: a request it makes while the device is being proven fails the pin.
- An interrupt can arrive at any instant; the checks above cannot cover every one of them. `crawl_run()` ends the run when it is interrupted; a `Device` that was interrupted is to be made anew, not used again.
- A `Device` used by `crawl_run()` must not be used from another thread while the crawl runs: a request from another thread can move or fail the pin between the gate's last check and the input.
- Likewise a `Device` must not be used from another thread while its `launch()` runs (accepted limit, the caller's usage): a request from the other thread can start the adb server again or fail a request between the launch's steps, and the stop and the start can then reach a device that replaced the first one under the same serial. The launch's rule against going on after a failure covers only its own requests. The previous version's `launch(restart=True)` (`am force-stop`, then `monkey`, two requests on an unpinned `Device`) had the same exposure, also without a second thread: a server started again between its two requests received the `monkey` start.
- The pin proves the device only through the checks above. `Device(..., pin=True)` used on its own (outside `crawl_run()`) checks the server's list before each request but does not read the identity again while nothing happened to the pin (after a failed request or a renumbered transport it does, or, without a pinned boot id, fails the pin), so a device that took over the serial and the number between two requests is not caught there. After a move, the request that waited goes to the new number without reading the list again. Two devices are assumed never to show the same boot id; a copy of a whole guest state (a snapshot loaded twice) could break that.
- No code the caller supplied runs between the crawl's last comparison of the pin and the request that changes the device (with uiprobe's own `Device`; a subclass that overrides `stop_app`, `tap`, `key` or `_launch_component` runs its override there, see L1 below): not `clock`, not `stop`, not `sleep`, and no write of the run folder (a table-driven test checks this for every request the crawl sends: tap, BACK, force-stop, the first launch and the start of a relaunch). `stop` is asked only before the gate's last reads: the gate asks `stop` and the clock first, checks the pin, asks `stop` again (the pin check can wait for the device), reads, asks the clock again (as in the previous version: reads can take long), and compares the pin last (accepted limit L1: a `clock` that changes the screen after the reads is not caught by them, see [Safety](safety.md); also part of L1: the Policy is copied when the crawl starts, and changes to it during the run are not seen; and the crawl calls methods of the `Device` object you pass, its reads and, for the requests that change the device, `stop_app`, `tap`, `key` and the internal start `_launch_component`, handing each the pin epoch it approved and the time limit, which the device checks right before the request is written, so a `Device` subclass that overrides these methods and drops those arguments can send after the checks, as in the previous version for taps, BACK and relaunches); the first launch and the start of a relaunch (after its force-stop) ask `stop` after their pin check, read the launcher activity, ask the clock (the read can take long), then compare the pin, and the start uses that read (also part of L1: a `clock` that changes or removes the launcher activity after that read is not caught, and the start uses the component read just before). The run's end by uiprobe's own clock (`time.monotonic`) is set once when the run starts. With the default `clock`, which is that clock, it is read once per check. With a clock of the caller's, uiprobe's clock is read once before the caller's first value and again right before each later one, and the remaining time the caller's clock reports, counted from that moment, can only bring the end earlier, never later. The device checks that end, and the pin epoch the crawl approved at its last comparison (not a value read later), on the request's own connection: after the adb server selected the transport and right before a tap, BACK, force-stop or start is written. Past it that request is not sent (`time_limit`, the run ends with `max_duration`; for the start of a relaunch, `start_not_sent`), so reads that take long cannot carry a request that changes the device past the limit. What remains is the instant between that check and the request reaching the device. Reads are not cut off: `stop` and the time limit are looked at when an observation and a gate begin and before each request that changes the device, so a read in progress (a dump, the reads after a start, a wait for a renumbered device) can run until it finishes after the end, and the run ends at the next of those points. A start that went out and was answered stays recorded as sent, whatever happens after it. A stop that arrives during the gate's last reads takes effect after the one request that follows them (an accepted limit, see [Safety](safety.md)). Every value the caller passes is copied into plain data at the start (the policy, its words and the limits) and every clock value is turned into a built-in float when it is received, so no method, accessor or finalizer of a caller's object runs while the crawl decides; code the caller supplies that runs earlier (and a `Device` subclass) is an accepted limit.
- Another app that covers the screen only while a screenshot is taken is not caught (see `screenshots`).
- `clock` must give seconds of at least 0 and below `2**40`, such as `time.monotonic`. A value outside that range raises `ValueError`: before the run folder is made for the first value, and as an `error` run later. A screen whose element ids are not unique is recorded as a failed dump.
- `settle` is the pause in seconds after a tap or BACK; it ends early at the time limit and when `stop` returns `True` (checked every 0.1 seconds). `clock` and `sleep` replace the clock and the pause of the crawl only; the wait for the app to come to the front inside `Device.launch` (up to 10 seconds) uses the device's own clock. `screenshots=True` also saves a screenshot of each new screen; one that cannot be taken, or after which the app is not in front, is noted in `summary.txt` and the crawl goes on. Another app that covers the screen only while the image is taken and is gone again when the foreground is read afterwards is not caught.
- `stop` is called between actions, in the gate and during the pause (not while the device is waited for, see above); when it returns `True` the crawl ends with the stop reason `interrupted`, and an action already written is closed as not sent.
- Ending: the engine's stop reason (`exhausted`, `max_actions`, `max_duration`, `relaunch_limit`, `keyboard_stuck`, `dump_failed_repeatedly`) or `not_sent` (see the gate) is returned. For an error of uiprobe, adb or the device that prevents going on, `run.json` is written with `error` (the error code is in `summary.txt`) and the error is raised again. An exception that is not a uiprobe error is recorded the same way with the code `internal_error`. `CrawlResult.screens` counts the target screens observed, `CrawlResult.actions` the start lines that are complete on disk (counted by the writer, in the same marked block as the write), including those closed as not sent; the last one may not have reached the device if the run ended right then. When a write of the run folder itself fails (`RunFolderError`), the writer refuses further writes, so `run.json` is not written and the error is raised. For Ctrl+C (`KeyboardInterrupt`), `run.json` is written with `interrupted`; if `stop` is given and returns `True` at that moment and `run.json` was written, `crawl_run()` returns with `interrupted`, otherwise the interrupt is raised again (for example when the interrupt broke a write, so that `run.json` cannot be written). The library never swallows an interrupt that nobody asked to end the crawl.
