# The run folder

A crawl run is recorded in one new folder. The library part that writes it is `uiprobe.runlog.RunWriter`. It does not talk to the device. The Python function `crawl_run()` and the command `uiprobe crawl PACKAGE --press --out DIR` write a run folder (see [Crawling from Python](python.md#crawling-from-python-alpha) and [Pressing crawl](crawl.md#pressing-crawl---press)).

## Rules

- The folder must not exist, and its parent folder must exist. Nothing is created silently and an existing folder is never reused. If the folder exists or the parent is missing, nothing is written and `RunFolderError` is raised. The path gets the same checks as the files of `uiprobe init` and `uiprobe screenshot` first: it must not be empty or hold a null character, nothing may be at it (a broken link included), and on Windows a colon after the drive (a stream of a file or folder, such as `existing.txt:x`, or the `\\?\GLOBALROOT\GLOBAL??\C:\...` form) is refused; give a path of the GLOBALROOT form with its drive letter instead. A path whose entry cannot be looked up (access denied on a folder above it, for example) is refused with `cannot check`. The path is checked in the form it was given, and a relative path again after it is joined to the working folder; the folder is made with exactly that text. A path that would pass only once normalized (such as a path made too long by repeated `./`) is refused. A relative path is fixed to the working folder when the run starts, so later changes of the working folder do not move the files. On Windows a path relative to a drive's own folder is refused: `C:run` (a drive without a separator after it) and `\run` (a separator without a drive); give a full path with its drive (`C:\runs\x`) or a path relative to the working folder (`runs\x`). On Linux or macOS a colon is an ordinary character and is not refused; an NTFS drive mounted there with its streams turned on (NTFS-3G with `streams_interface=windows`, for example) still reads it as a stream, so do not write to such a drive.
- The run folder and `screens` are made so that only their owner can open them, because the files hold screen text, which may include personal data. On Linux and macOS the mode is `0o700` (the umask can only narrow it). On Windows, Python 3.12.4 and later give the folder access control for its owner, the Administrators group and SYSTEM only; Python 3.12.0 to 3.12.3 ignore the mode, so the folder gets the usual permissions of its parent. To share a run folder, change its permissions yourself afterwards.
- Every file is created new. No file is overwritten, renamed, truncated or deleted, also not after an error.
- Text files are UTF-8 with LF line ends on every system. JSON is escaped like the other uiprobe JSON: inside strings, the control characters U+0000 to U+001F use the standard JSON escapes (`\b`, `\t`, `\n`, `\f`, `\r`, and `\u00XX` for the others), and DEL, the C1 controls (U+007F to U+009F), the line and paragraph separators (U+2028, U+2029) and the bidirectional formatting characters (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069) are written as `\uXXXX`. Other text, such as Japanese, stays readable. A JSON line therefore never holds a line break inside a string.
- JSON never holds `NaN` or an infinite number. Each record is serialized once, by an encoder that refuses them with `ValueError` before any file is opened, and nothing is written.
- File names are fixed names, or a screen id (`s-` and 12 lowercase hex digits, such as `s-0123456789ab`). Text that comes from the app never becomes part of a path.
- Every line or file is flushed and then synced to the disk (`fsync`) before the method returns. A line is therefore complete on disk when the writer returns, also if the program is killed right after.
- If a write fails, the file stays as far as it got, `RunFolderError` names it (`details.path`), and the writer refuses all later writes.
- An interrupt such as Ctrl+C that arrives during a write is not turned into `RunFolderError`: it propagates as `KeyboardInterrupt` itself (or `SystemExit` and the like), without `details.path`. The writer then refuses all later writes, as after a failed write. If closing the file also fails after the interrupt, `RunFolderError` (naming the file) may be raised instead of the interrupt; either way the writer refuses all later writes. Marking the writer on an interrupt is best effort (see [Interrupts](#interrupts)).
- At the end, the line files are closed first, then `summary.txt` is written, and `run.json` last. A folder whose `run.json` is missing or is not complete JSON did not end normally. This holds one way only: a `run.json` that looks complete does not prove a normal end, because `finish()` can still fail at the final sync after the bytes are in the file. Only a `finish()` that returned without an error proves it.
- A writer is made only with `RunWriter.create`, which makes the folder. Calling `RunWriter(...)` directly raises `TypeError`, so a writer can never write into a folder it did not make.

## Files

| File | Written | Content |
| --- | --- | --- |
| `run-start.json` | when the folder is made | The settings the run started with. |
| `transitions.jsonl` | one line per event | Each action that is about to be sent, and where it led. Made at the first line. |
| `skipped.jsonl` | one line per screen id, element fingerprint and reasons | Elements that were not pressed; identical elements of one screen with the same reasons share a line, and a screen too large to judge gives one line for the whole screen. Made at the first line. |
| `screens/<screen_id>.json` | the first time a screen id is seen | The screen, in the form of `uiprobe dump --json` (`uiprobe.screen/1`). |
| `screens/<screen_id>.png` | the first time a screenshot is given for a screen id | A PNG image. Anything that does not start with the PNG signature is refused and no file is made. |
| `summary.txt` | at the end | Per screen, the labels of its buttons. |
| `run.json` | at the very end | How the run ended. It is written last, after the line files are closed and `summary.txt` is written. |

The `screens` folder is made when the first screen file is written.

## JSON formats

`run-start.json` and `run.json` hold one JSON object (indented). The `.jsonl` files hold one compact JSON object per line. Times are ISO 8601 with a UTC offset (the local one unless the caller gives a time with its own), to the second, such as `2026-03-01T09:30:15+09:00`.

- `uiprobe.run_start/1`: `started_at`, `package`, `limits` (`depth`, `actions`, `minutes`), `deny` (the deny words in use, in the given order), `deny_except` (the exception words in use, in the given order; written by this version, absent from older run folders), `back_on_other_screens` (`true` when the crawl may press BACK on a screen of another app; written by this version, absent from older run folders), `device` (`serial`), from `crawl_run()` `check_tap_window` (`false` when the window at a tap's point was not checked), from `crawl_run()` `restart` (`true` when the first action force-stops the app before it starts it, `false` with `--no-restart` or `restart=False`; written by this version, absent from older run folders) and, from `crawl_run()`, `repin` (`true` when a renumbered transport may be followed in this run, because the device's boot id could be read).
- `uiprobe.transition_start/1`: `recorded_at`, `action_id` (counts from 1), `action` and, when known, `from_screen_id`. `action` has `kind` (for example `launch`, `tap`, `back`, `relaunch`) and, when given, `point` (`[x, y]`) and `element`. When the action was decided on a screen of another app, the line also has `off_target`: `package` (the package of that screen's dump) and, when known, `foreground` (the package in front) and `focus` (the owner of the window with input focus, where a BACK goes). With the default, such an action is a `relaunch`; a `back` there exists only with `back_on_other_screens`. These say where the action was decided; whether it was sent is in the end line. A `launch` that includes a force-stop before its start (the first action of a crawl, unless `--no-restart` or `restart=False`) also has `restart` (`true`); the key is absent on every other line, and on a launch without the force-stop (written by this version, absent from older run folders). It records what the launch is, not what was sent: whether the force-stop went out is in the end line: a `not_sent` end line with any reason but `start_not_sent` means nothing was sent; `start_not_sent` means the force-stop went out and the start did not; a `failed` end line (`outcome: "unknown"`) means the force-stop or the start may have reached the device; any other end line means both were sent. The line is written before the action is sent.
- `uiprobe.transition_end/1`: `recorded_at`, `action_id`, `dump_failed` (`true` when the screen after the action could not be read) and, only when `dump_failed` is `false`, `to_screen_id`. For an action whose start line was written but which was then not sent, the line instead has `not_sent` (`true`) and `reason` (a short word, such as `stopped` or `focus_other`), and neither `dump_failed` nor `to_screen_id`. For a launch or relaunch whose sending failed and ended the run, the line instead has `failed` (`true`), `reason` (the launch failure, such as `start_timeout` when the reply of `am start -W` did not come in time, or `start_failed`; or the error code) and `outcome` (`"unknown"`: the device may have acted on it), and neither `dump_failed` nor `to_screen_id`; readers of older folders see no such line (written by this version). For `covered_by_other` and `cover_unknown` it also has `details`: for `covered_by_other`, `window` (the title of the window that takes a touch at the tap's point) and `owner_uid` (its owner's uid; a window of the app itself is reported this way when it runs for another Android user than user 0, or when the app shares its uid and the title does not name it); for `cover_unknown`, `unreadable`, one of `no_list`, `line_format`, `region_format`, `rotation` (the gate's dump says the hierarchy is rotated, or the `Viewport` lines of `dumpsys input` say the display is rotated or scaled, or cannot be read: on a rotated display every tap gets it), `no_window`, `portal` (the window there forwards touches to another display), `target_uid` (the app's uid could not be read, at the start or right before the window, or it changed) or `target_user` (the focused window belongs to another Android user than user 0). When the window list or the display's orientation in `dumpsys input` refused (`no_list`, `line_format`, `region_format`, or `rotation` from the `Viewport` lines or the list), `details` also has `rule`, the check that refused (such as `unknown_flag` or `list_end`; the rules are listed in [Diagnosing the tap window check](commands.md#diagnosing-the-tap-window-check)); it is written by this version and absent from older run folders, and absent for `rotation` from the gate's own dump. See [Crawling from Python](python.md#crawling-from-python-alpha).
- `uiprobe.skip/1`: `recorded_at`, `screen_id`, `fingerprint`, `reasons` (the reasons in the order the caller gives them; the writer does not sort them), `details` (only when the element was refused for `deny_word`, `irreversible_screen` or `confirm_button`; written by this version, absent from older run folders) and `element`. In the lines a crawl writes, `details` is a list with one object per such reason, in the form `crawl --json` gives: `reason` and, when set, `word` (the deny word or phrase that matched), `field` (`text`, `content_desc`, `hint`, `resource_id` or `joined`), `element_id` (the element where it was found, or the root of the joined subtree) and `note` (for `confirm_button`, the confirm label). For example `{"reason": "deny_word", "word": "delete", "field": "text", "element_id": "e3"}`. For `deny_word`, a deny word that an exception word excused is not counted, so it is not named. The screen-wide check behind `confirm_button` never uses exception words, so its details can name such a word, with the id of the element that holds it. The text in it comes from the device and is written like the element's text (escaped as described above). `RunWriter.write_skip(..., details)` called directly takes `details` as optional: each object must have a `reason` that is one of `deny_word`, `irreversible_screen` and `confirm_button` and also one of the line's `reasons`, with only the keys above, all strings; the writer does not require one object per reason. One line is written for each different combination of `screen_id`, `fingerprint` and `reasons`; repeats are not written. (If recording the combination fails after its line was written, for example through `MemoryError` or an interrupt, a retry by a caller that catches the error can write the line a second time; see [Interrupts](#interrupts).)
- `uiprobe.run/1`: `ended_at`, `stop_reason`, `screens` (how many screens were seen), `actions` (how many start lines were written, those closed as not sent included; an action that was taken back and chosen again has a start line, with its own action id, for each attempt) and, from `crawl_run()`, `repins` (how many times the pinned transport was followed to a new number; each one is also a `Note:` line in `summary.txt`).

`element` (in `uiprobe.transition_start/1` and `uiprobe.skip/1`) is written in the form the caller gives: an `Element` is written in its `uiprobe.screen/1` form, and a mapping is written as given. The writer does not check its fields.

## summary.txt

For each screen that was written, one heading line (package, activity and the screen id, as in the indented tree output of `uiprobe dump`) followed by one line for each clickable element that has a label (its text, or else its content description). After the counts at the top there can be `Note:` lines (quoted and escaped), which `crawl_run()` uses for an error code (`error: adb_error`), for a screen whose screenshot could not be taken, for a launch after which the app was not in front (`... was not in front after launch (PACKAGE)`, also when the start named an activity of another app), for a start whose reply did not come in time (`the reply of am start -W for PACKAGE did not come within 10.0 seconds; whether the app started is unknown, so the run ended`), for a force-stop whose start was not sent (`PACKAGE was force-stopped at the start of the run but not started (REASON)` for the first launch, `PACKAGE was force-stopped but not started again (REASON)` for a relaunch), and for each move of the pinned transport to a new number. Labels come from the app, so they are quoted and escaped the same way as in the indented tree output: control and bidirectional characters appear as `\uXXXX`.

## Interrupts

`RunWriter.critical()` is a context manager that marks the time while a line or file is written; the read-only property `writing` is `True` inside it. Each write method keeps the write and the writer's record of it (for example that a screen or a skip was already written) inside one such block, so `writing` stays `True` until the write is recorded. A program that handles Ctrl+C can look at `writing` and postpone the interrupt until the write is complete. `RunWriter.create` writes `run-start.json` before it returns the writer, so a program that also wants that first write uninterrupted postpones Ctrl+C for the whole `create` call. The library installs no signal handler.

When an interrupt does reach a write, the writer marks itself as failed and refuses later writes, but only as far as it can: an asynchronous exception such as `KeyboardInterrupt` can arrive between any two steps, also after the point where the mark is made, so the mark is best effort and cannot be complete. The reliable way is the one above: a program that handles Ctrl+C postpones it while `writing` is `True`.

## What `crawl_run()` writes

`crawl_run()` writes only the screens of the target app to `screens/`: a screen of another app (a permission dialog, the launcher) gets no file: the transition lines name it by its screen id, and the start line of a BACK or relaunch decided on it also has `off_target` with its package. Each action has a start line before it is sent and an end line with the same `action_id`: after the first screen read afterwards, or, when the gate right before sending refused it, a `not_sent` line (the reasons are in [Crawling from Python](python.md#crawling-from-python-alpha)). The end line is written before a screenshot of that screen is taken, and a screenshot is kept only when the app is still in front after it was taken. A start line with no end line is an action whose result is not known (the run ended or failed while it was sent); the input may or may not have been delivered. The stop reason is one of the engine's (`exhausted`, `max_actions`, `max_duration`, `relaunch_limit`, `keyboard_stuck`, `dump_failed_repeatedly`), `not_sent` (a BACK, a relaunch or the first launch was not sent: refused by the gate, or met a device that had to be proven again), `interrupted` or `error`. A folder with no `run.json` did not end normally.

## Limits

Files and folders are only ever created new: an existing file is never opened. But if another program running with the same rights replaces the run folder or the `screens` folder with a link (or, on Windows, a junction) during a run, later new files can be created where that link points. uiprobe does not defend against such a program, which could just as well write there itself. That reasoning holds only when the other program has the same rights. If you run uiprobe with higher rights (as an administrator or root), choose a parent folder that only that account can open, on a path where no other user can rename or replace any folder (every folder above it must be protected too), not a shared folder such as a common temporary folder: a program with lower rights could otherwise move where uiprobe creates its new files. The run folder itself is made private (see Rules), but on Python 3.12.0 to 3.12.3 on Windows that does not apply.

The same holds for a program that appends to `transitions.jsonl` or `skipped.jsonl` during a run: the writer keeps its own position in the file, so its next line can overwrite what was appended. The writer assumes it is the only one writing into its run folder.

The offline file guard (`tests/test_offline_guard.py`) checks that each of the four file-creating calls appears once, in `runlog.py`. It does not stop another uiprobe module from importing runlog's private helpers that make those calls. The two open helpers (`_create_text`, `_create_binary`) and `_make_dir` can only create new files and folders (an existing file or folder is an error). `_put` writes to whatever handle it is given and does not check where the handle came from. Review covers who calls these helpers.
