# Safety

**`uiprobe crawl --press` presses the device for real, and so does `uiprobe crawl` when the settings file says `press = true`.** A settings file can therefore start a pressing run without `--press` (with `--out DIR`, or a `runs_dir` in the file); `--dry-run` always previews. Its limits are the settings file's `[limits]` (300 actions, depth 5, 30 minutes in the file `uiprobe init` writes) unless `--actions`, `--depth` or `--minutes` say otherwise, and the plan printed before the first action says why the run presses and where each limit came from. It presses on a real device only when `--allow-real-device` is given, on every run: the settings file cannot hold that permission. Without `--press` and without `press = true`, `crawl` only previews and presses nothing. A file written by an older `uiprobe init` says `press = false`, so it does not start pressing. A run folder that comes from `runs_dir` is created only inside an existing folder that the file names, under a new name; uiprobe never creates that folder itself, and refuses it when its last part is a link or junction (links and junctions in the parts above it are followed, as for `--out`); nothing is reused or overwritten. Accepted limit: another program running as the same user can replace the `runs_dir` folder, or the new run folder, with a link between uiprobe's check and its use, so the records can land somewhere else; the same holds for `--out` today. Making the folder and writing its files through an open handle of the folder (`dir_fd`) would close that gap and is a possible later change.

uiprobe is alpha software, and `tap`, `swipe`, `key`, `type` and `crawl --press` send real input to a device. This page gathers the safety notes. Most notes below restate the other pages in short form; the links lead to the full rules.

## What is sent

- `tap`, `swipe` and `key` send real input to whatever screen is showing, in any app, and they press what you name, also a button called "Delete" or "Buy". `type` sends text to the focused field, whatever it is; it presses no button.
- They act on the screen showing now. The foreground app is not checked, and there is no deny-word guard. A swipe that starts at a screen edge can trigger a system gesture.
- With `tap --xy` and with `swipe --from ... --to ...` there is no dump and no check: the point is pressed, or the swipe sent, as given, because you named the points.
- Each press is sent once and never resent, not even after a lost connection, because a resend could press twice. Exit 14 (`input_failed`) does not prove that nothing was pressed: `input` may have acted before it failed. Look at the screen before you repeat the command.
- `type` sends the text to whatever field has focus, in any app; the text is not written to the output, and errors while it is typed hold only fixed words and numbers. Two exceptions: a refused character is named in the usage error (by code point and position), and an error that comes before any text is sent (no adb server, no device) is reported as for any other command. Device options (`-s`, `--adb`, `--adb-server`) go before `type` and are refused after it, so no word of the text is used as one. When the text is not quoted as one argument, part of it can still be read as arguments and appear in an error; uiprobe hides what it can (see [Typing text](commands.md#typing-text)), but quote the text, or use `Device.type_text` from Python. The text is visible in the process list and shell history of this computer, and may be visible in the device's process list while it is typed. A long text, or one with `%s`, goes out in several commands, so an error part way can leave part of it typed: look at the screen before you repeat the command.
- `launch` starts the app on whatever device is selected; `--restart` stops it first (`am force-stop`), which can lose unsaved state in that app; without it the app is not stopped. A pressing crawl does the opposite by default (see below).
- Apps are started with `am start -W` of the app's launcher activity, read with `cmd package resolve-activity` right before each start, never with `monkey`. The previous version started apps with `monkey -p PACKAGE -c android.intent.category.LAUNCHER 1`, which turned the device's auto-rotate setting on (`accelerometer_rotation` 0 to 1), seen on API 24 and API 36 emulators and a Samsung API 36 phone. `am start` does not change it: on an API 36 emulator no system, global or secure setting changed its value across `launch`, `launch --restart` and a short crawl. This holds for `launch` and for the first launch and every relaunch of `crawl --press`. When the launcher activity cannot be read in the expected shape, with its exit status 0, nothing is started (exit 15, `launcher_unreadable`; a crawl stops before its run folder is made). A crawl whose start gets no reply in time stops at once (`start_timeout`), because whether the app started is unknown. See [Launching an app](commands.md#launching-an-app).
- Between the crawl's last check and a request that changes the device (a tap, BACK, force-stop or start), no code you passed to `crawl_run()` runs (not `clock`, `stop` or `sleep`; this holds for uiprobe's own `Device`: a subclass that overrides `stop_app`, `tap`, `key` or `_launch_component` runs its override there, see L1 below), and the time limit is checked once more by uiprobe's own clock on the request's connection, right before it is written. Accepted limit L1 (as in the previous version): before a tap, BACK or force-stop the crawl calls your `clock` once more after its reads of the screen and before its last check of the pin, so a `clock` that changes the device's screen there (opens a window, for example) is not caught by those reads; a change of the device itself is still caught by the pin check. The same holds before a start: the crawl calls your `clock` after its read of the launcher activity and before its last check of the pin, so a `clock` that changes or removes the launcher activity there is not caught, and the start uses the component read just before. The Policy is copied when the crawl starts; changes to it during the run are not seen. The crawl calls methods of the `Device` object you pass: its reads, and for the requests that change the device `stop_app`, `tap`, `key` and the internal start `_launch_component`, handing each the pin epoch the crawl approved and the time limit, which the device checks right before the request is written. Also part of L1: a `Device` subclass that overrides these methods and drops those arguments can send after the crawl's checks; this is the same as in the previous version for taps, BACK and relaunches. Accepted limit: a stop asked while the checks before a tap or BACK read the screen takes effect after that one request; `stop` and the time limit are asked again when the next observation begins, and a read in progress can run until it finishes after them.
- Accepted limit for `crawl_run()` from Python: the crawl copies the values you pass into plain data when it starts (the policy and its words, the limits) and turns every clock value into a built-in float at once, so a subclass or an object with hooks cannot run code while it decides. Code you supply that still runs earlier (your `clock`, `stop` and `sleep`, a method of the `Device` object you pass) can change the device; the crawl checks the pin and reads the screen again after them, but an object made to defeat those checks (a `Device` subclass, for example) is not caught.
- `uiprobe launch` selects the device by its serial for each request; it never starts an adb server, and once its first request went out, any failed request ends it at once, so it never goes on through a server that was started again. Accepted limit: if the device behind the serial is replaced between the launcher read and the start, the start uses the component read just before (it fails, or opens that component of the same package on the new device). Use `crawl --press`, which pins the device, where this matters. Limit: the `LaunchState:` values seen and accepted in the reply of `am start` are `COLD`, `WARM`, `HOT` and `UNKNOWN (0)`; with any other value the start is not taken as a success (the launch fails, and a crawl ends with `error`).
- From Python, do not use a `Device` from another thread while its `launch()` runs: a request from that thread can start the adb server again between the launch's steps, and the stop and start can then reach a replacement device (accepted limit). The previous version's monkey-based `launch(restart=True)` had the same exposure.
- Deny words are used by the crawl preview (what `crawl` does by default), which presses nothing, and by the pressing crawl (`crawl --press`, and `crawl_run()` from Python), which judges every screen with the same guards before it taps. Both also refuse every element of a screen that says it cannot be undone, buttons such as "Cancel" included. They recognize the configured irreversibility phrases (for example "You can't undo this" or 元に戻せません, see [Previewing a crawl](crawl.md)), not every possible wording: a warning phrased in another way is not caught, so the screen is then judged like any other.
- The pressing crawl, `uiprobe crawl PACKAGE --press --out DIR` (or `uiprobe crawl PACKAGE --out DIR` with `press = true` in the settings file) or `crawl_run()` from Python (alpha), presses on the selected device: it force-stops the app at its start, taps what the guards allow, presses BACK and relaunches the app. The force-stop at the start (`am force-stop`, then the start of the launcher activity; which screen the app then shows is up to the app) loses what the app had not saved; it goes through the same pin and time checks as a relaunch's force-stop, and `--no-restart` (`crawl_run(..., restart=False)`) turns it off, so the crawl starts from the screen the app shows now. By default it sends nothing to a screen of another app: it relaunches the target app instead (`am force-stop`, then `am start -W`), which can lose unsaved state. `--back-on-other-screens` (`Policy(back_on_other_screens=True)`) makes it press BACK there, and that BACK reaches the owner of the focused window, whichever app that is. Right before each tap it reads which window takes a touch at the tap's point and sends the tap only when the topmost window that takes touches there belongs to the app (its owner uid is the app's for Android user 0; for an app with a system uid or a uid shared with other packages, its title must also name the app); `--no-tap-window-check` (`Policy(check_tap_window=False)`) turns that off (text an app sets, such as an unusual window name, can make the check refuse taps on that app's screens; see the limits under [Crawling from Python](python.md#crawling-from-python-alpha)), and then an overlay of another app over the point gets the tap. Windows that only watch touches (such as the system's gesture monitors, which are spy windows) and copies of a touch sent to the wallpaper are not checked. When the window cannot be read, nothing is sent (`cover_unknown`); on a rotated display every tap is refused that way (`rotation`, when the gate's own screen dump or the display orientation in `dumpsys input` says it is rotated), so an app in landscape cannot be crawled yet, and so is every tap while the focused window belongs to another Android user than user 0 (`target_user`). The check trusts that the output of `dumpsys` arrives as the Android system wrote it, and does not trust text an app can set (window names, `applicationInfo.name`). If a window of another app is the lowest in the list, no window above it takes the point, and its name fakes a complete window line, the check cannot tell; the tap then goes where it would go without the check. Output of the system that is damaged in ways that contradict themselves is an accepted limit; a contradiction the check notices makes it refuse. Windows of another package that shares the app's uid (a package of the same developer, signed with the same key, or a system package) are told apart only by their name. The tap is a 10 ms swipe from the point to itself: if Android sends a move event during it and the window at the point is marked `SLIPPERY`, a window of another app that appears there during those 10 ms can receive the rest of the press. It refuses a device that is not an emulator unless `--allow-real-device` (`allow_real_device=True`) is given, keeps every request on the device it checked (and checks before every action and screen read that the device behind its connection is still the same one), and right before each action reads the device again and sends nothing when anything it needs cannot be read or has changed, ending the run when that happens to a BACK or relaunch; see [Pressing crawl](crawl.md#pressing-crawl---press) and [Crawling from Python](python.md#crawling-from-python-alpha). The command stops at the settings file's `[limits]` (after 300 sent actions or 30 minutes, and at most 5 screens deep on one path, in the file `uiprobe init` writes), unless `--actions`, `--minutes` or `--depth` say otherwise; `crawl_run()` takes its `limits` from the caller.

Details: [Commands](commands.md).

## Real devices and test accounts

- Use an emulator, or a test device with test accounts. Do not run uiprobe on a phone that holds your own accounts, payment methods or messages.
- uiprobe uses the device given with `-s`, else the one named in `ANDROID_SERIAL`, else the only ready device. Run `uiprobe devices` first.
- The guards have been checked only on Android emulators; real devices and other Android versions may behave differently.
- Known point: a pressing crawl, by `--press` or by `press = true` in the settings file, pins the device before it checks whether it is an emulator. The pin reads the device's identity (`ro.serialno`, the build fingerprint and the boot id), so a real device without `--allow-real-device` gets those reads before the refusal; nothing is written, started or pressed. This was so for `--press` before; `press = true` is a new way into it.
- When `dumpsys window` shows several displays (a foldable with a cover screen) or an unusual focused-display line, the foreground app and the focused window are read only while display 0 is the focused display: the foreground from the device-wide resumed activity, the focused window only when exactly one display has a focused window and that window is on display 0. Otherwise they are unknown, so `launch` fails with `not_in_front` and the crawl presses nothing. That the resumed activity is printed once for the whole device was seen on one capture only (SM-F776B, Android 17, phone open). The focus reading is best effort against forged window titles, so on such a device the tap window check is the guard and cannot be turned off: with `--no-tap-window-check` the pressing crawl sends no tap or BACK. Once any read in a run has shown several displays (also window blocks on more than one display), this holds for the rest of the run; a new run starts without it. Accepted limits, where an app's window title can mislead the focus reading: while no display has a focused window, a title that forges a display header and a focus line together is read as the focus; if `dumpsys activity activities` has no genuine resumed line, a title can supply agreeing resumed lines, and the foreground becomes that package (on one display, the same holds without a genuine `mFocusedApp` line, as before); and a focused window whose title changes between the focus read and the owner read can have its title text taken as owner lines, so the focus is given to another package and uid. While a foldable is being opened or closed, the foreground can be misread if the focus moves between the window read and the activity read; taps stay guarded by the tap-window check, the next read notices it, and the same gap is in the earlier commits of this change. Taps stay guarded by the uid check of the window at the tap point, which cannot be turned off on several displays; a BACK relies on the focus reading, so it can go to the window that really has the focus. Further accepted limits (L1, code you pass to the crawl): the note of several displays is cleared when a crawl starts, so a `clock`, `stop` or `sleep` of yours that starts another crawl on the same `Device` clears it; reads that your callbacks make (such as `device.foreground()` in your `clock`) count toward the note, and only those before the gate's last check of it are seen in time; `Device.diagnose_tap_window()` does not count toward it, so a `dumpsys input` that only it reads does not set the note. Window titles can also move the reading the other way: a line break in a title can split a window block's header from its `mDisplayId=` line (that window then counts on no display), and a title that imitates a second window block, or a second `Display:` section in `dumpsys input`, on a single display makes uiprobe take the device for one with several displays, which only refuses more. `dumpsys input` is read only for the tap window check, so its `Display:` sections count only while that check is on.

## What deny words cannot see

- Deny words see only the text, description, hint and resource id that uiautomator reports. An icon-only button without them (a trash can, a send arrow) has no words to match.
- `--tap-unlabeled` allows pressing elements that have no text, description or hint. This also allows icon-only buttons that deny words cannot see, such as a trash can.
- Deny words include the state-changing verbs of Settings pages (`forget`, `disconnect`, `unpair`, `turn off`, `eject` and others, see [Crawling an app](crawl.md)), so the `Forget` button of a saved network and the buttons next to it are not pressed. Substring matching also over-blocks (`Posture` contains `post`); a miss is worse than an over-block. The known limits are listed in [Crawling an app](crawl.md).
- There are no exception words by default. A word you list under `[deny] except` in the settings file stops a deny word found inside it from counting where the word stands whole inside one element's text with real separators around it, so an element whose only hit was there is pressed: with `automatically` listed, `Bill my card automatically` is pressed by `crawl --press`. You take that on when you add the word. A label split across child elements (`Turn on` + `automatically`) or text that normalization changes may still be refused; the exact condition and its limits are in [Crawling an app](crawl.md). Exception words never weaken the screen-wide check behind `confirm_button`.

## Device-wide keys are refused

`key` refuses device-wide keys with a usage error (exit 2) before the adb server is contacted, whether the key is given as an alias or as a name. Ten keys are refused whatever any file says: the power, sleep, lock and call keys (`KEYCODE_POWER`, `KEYCODE_SLEEP`, `KEYCODE_SOFT_SLEEP`, `KEYCODE_LOCK`, `KEYCODE_CALL`, `KEYCODE_ENDCALL`, `KEYCODE_HEADSETHOOK`, `KEYCODE_TV_POWER`, `KEYCODE_AVR_POWER`, `KEYCODE_STB_POWER`). The other groups (more power and wake keys, sound and media playback, brightness, screenshots, assistants, system UI and keys that open other apps) are defaults: without a settings file they are refused, and with one, the file's `[keys]` table decides. The file can remove any of them and can add keys to refuse, for example `KEYCODE_HOME`. Any key that no list refuses is sent, including `home` and `recents`, which can leave the current app. `key` uses `--config PATH` when given (the file must then exist), else `./uiprobe.toml` when that file exists, else the built-in lists. Like `tap` and `swipe`, `key` sends to whatever screen is showing, in any app. The groups are listed in [Pressing keys](commands.md#pressing-keys) and the file in [Settings file](settings.md).

## What the guards cannot see

- The preview judges one screen as it is. It cannot see what a press would lead to, and it does not look at the pixels, only at what `uiautomator` reports.
- The screen-edge areas use the sizes measured on an API 36 emulator for every device for now, in pixels, not scaled to the device's density.
- The foreground app is not checked by `tap`, `swipe` or `key`.

## Texts in run folders

A run folder holds screen text, which may be personal. Two protections exist; the rest is up to you.

- A field with the `password` flag is always written without its text (`"text": ""` and `"hidden": ["text"]`), and `summary.txt` shows `[password field]`. It applies to text in the records only: a screenshot (`--screenshots`) holds pixels, so a password field whose characters the app shows on screen has them in the PNG; `record_text` off refuses screenshots. Only the flag decides: an app that shows a code or password in a plain field (a one-time code, a PIN on a custom keypad) is not covered by this.
- `record_text = false` (or `--no-record-text`) keeps `text`, `content_desc` and `hint` of every element, and the title of a window that covers a tap, out of the records. Use it when screens may show a code in a plain field. It cannot be used with `--screenshots`, because a picture shows the text.
- Limit: fingerprints in `skipped.jsonl` and in the records are hashes over an element's texts. A short code (4 to 6 digits) could be recovered from its fingerprint by trying all values, with `record_text` off too. Do not share a run folder of a screen that showed such a code.
- `uiprobe dump` and the text a dry run prints are not run folders and keep the texts; the same care as for [dumps](#personal-data-in-dumps) applies.
- PIN and fingerprint prompts of the system are screens of another app; uiprobe does not write them, but it notes their ids and, for an action decided there, the package.

## Terms of service

Automating an app you do not own may break its terms of service. Read them first, and prefer your own builds and test environments.

## Personal data in dumps

- A dump holds the text on the screen, which may include personal data such as names, addresses and messages. Check saved screens before you share them, also in an issue.
- A screenshot (`uiprobe screenshot`, `Device.screenshot`) can contain personal data too, like a dump, and an image can show what no text names, so look at it before you share it.
- Android lets an app forbid screenshots of a screen (`FLAG_SECURE`), but `uiautomator` still returns that screen's structure and text. So a dump of such a screen, and any copy of it you save, contains that text, which may include personal data. For example, on Android emulators at API 24 and API 36, Chrome's Incognito tab had `FLAG_SECURE`: Android's screenshot command, `screencap`, gave empty output on API 24 and an almost entirely black image on API 36, while `uiautomator dump` and `uiprobe dump` returned the full tree with its text.

## Sharing a tap window diagnosis

- `uiprobe diagnose tap-window` sends one command to the device, `dumpsys input`, which only reads; it presses nothing and changes nothing on the device. With `--package PKG` it first reads `dumpsys package PKG` (the app's uid, as the crawl reads it), which only reads too.
- `dumpsys input` holds device values: window titles and app names, the uids and pids of apps, screen coordinates, display ids such as `uniqueId=local:...`, the names of input devices, and on some devices more. uiprobe reads it in memory and never saves or prints it.
- By default the report holds only uiprobe's own words and numbers it counted: the reader's verdict (reason, rule, line number), whether it took a list as display 0's and how many windows it read there, and for a few lines their kind (as the reader classified them) and length. No field name, value, flag, row or display number, orientation, sign or other character of `dumpsys input` is in it. Tests fill the captures with a serial, IMEI-like numbers, MAC and IP addresses, accounts, phone numbers, package names, window titles (also with field-like text or line breaks), quoted values, display ids and input device names, change them to other letters, digits, Unicode digits, signs, quotes and delimiters, mutate the outputs further, and check that the text, the JSON and the Python object hold only uiprobe's fixed words and numbers it counted.
- Errors are reported by their error code alone, never with the error's message, which can name the device or hold text it printed. A usage error of `diagnose` does not repeat the command line, which can hold a serial.
- `--package PKG` is not echoed: the report does not name it. Whether a `samsungFlags=0x1` window was accepted as its own, and a note that its uid could not be read, still tell something about that app on the device to anyone who knows which package was given.
- The lengths still say something about the device (how long a window title's line is), and so do the counts and the kinds the reader gave lines (how many windows it read; a window name with line breaks can change them). `--show-device-text` adds the indents and shapes of the lines, with field names, values, flag names and numbers from the device: window names and app text can appear there, with or without line breaks, and can hold a serial or personal data. The report's first line says so in that mode; read it before you share it. Details: [Diagnosing the tap window check](commands.md#diagnosing-the-tap-window-check).
