# Safety

**`uiprobe crawl --press` presses the device for real, and so does `uiprobe crawl` when the settings file says `press = true`.** A settings file can therefore start a pressing run without `--press` (with `--out DIR`, or a `runs_dir` in the file); `--dry-run` always previews. Its limits are the settings file's `[limits]` (300 actions, depth 5, 30 minutes in the file `uiprobe init` writes) unless `--actions`, `--depth` or `--minutes` say otherwise, and the plan printed before the first action says why the run presses and where each limit came from. It presses on a real device only when `--allow-real-device` is given, on every run: the settings file cannot hold that permission. Without `--press` and without `press = true`, `crawl` only previews and presses nothing. A file written by an older `uiprobe init` says `press = false`, so it does not start pressing. A run folder that comes from `runs_dir` is created only inside an existing folder that the file names, under a new name; uiprobe never creates that folder itself, and refuses it when its last part is a link or junction (links and junctions in the parts above it are followed, as for `--out`); nothing is reused or overwritten. Accepted limit: another program running as the same user can replace the `runs_dir` folder, or the new run folder, with a link between uiprobe's check and its use, so the records can land somewhere else; the same holds for `--out` today. Making the folder and writing its files through an open handle of the folder (`dir_fd`) would close that gap and is a possible later change.

uiprobe is alpha software, and `tap`, `swipe`, `key`, `type` and `crawl --press` send real input to a device. This page gathers the safety notes. Most notes below restate the other pages in short form; the links lead to the full rules.

## What is sent

- `tap`, `swipe` and `key` send real input to whatever screen is showing, in any app, and they press what you name, also a button called "Delete" or "Buy". `type` sends text to the focused field, whatever it is; it presses no button.
- They act on the screen showing now. The foreground app is not checked, and there is no deny-word guard. A swipe that starts at a screen edge can trigger a system gesture.
- With `tap --xy` and with `swipe --from ... --to ...` there is no dump and no check: the point is pressed, or the swipe sent, as given, because you named the points.
- Each press is sent once and never resent, not even after a lost connection, because a resend could press twice. Exit 14 (`input_failed`) does not prove that nothing was pressed: `input` may have acted before it failed. Look at the screen before you repeat the command.
- `type` sends the text to whatever field has focus, in any app; the text is not written to the output, and errors while it is typed hold only fixed words and numbers. Two exceptions: a refused character is named in the usage error (by code point and position), and an error that comes before any text is sent (no adb server, no device) is reported as for any other command. Device options (`-s`, `--adb`, `--adb-server`) go before `type` and are refused after it, so no word of the text is used as one. When the text is not quoted as one argument, part of it can still be read as arguments and appear in an error; uiprobe hides what it can (see [Typing text](commands.md#typing-text)), but quote the text, or use `Device.type_text` from Python. The text is visible in the process list and shell history of this computer, and may be visible in the device's process list while it is typed. A long text, or one with `%s`, goes out in several commands, so an error part way can leave part of it typed: look at the screen before you repeat the command.
- `launch` starts the app on whatever device is selected; `--restart` stops it first (`am force-stop`), which can lose unsaved state in that app; without it the app is not stopped. A pressing crawl does the opposite by default (see below).
- Apps are started with `am start -W` of the app's launcher activity, read with `cmd package resolve-activity` right before each start, never with `monkey`. The previous version started apps with `monkey -p PACKAGE -c android.intent.category.LAUNCHER 1`, which turned the device's auto-rotate setting on (`accelerometer_rotation` 0 to 1), seen on API 24 and API 36 emulators and a Samsung API 36 phone. `am start` does not change it: on an API 36 emulator no system, global or secure setting changed its value across `launch`, `launch --restart` and a short crawl. This holds for `launch` and for the first launch and every relaunch of `crawl --press`. When the launcher activity cannot be read in the expected shape, with its exit status 0, nothing is started (exit 15, `launcher_unreadable`; a crawl stops before its run folder is made). A crawl whose start gets no reply in time stops at once (`start_timeout`), because whether the app started is unknown. See [Launching an app](commands.md#launching-an-app).
- Between the crawl's last check and a request that changes the device (a tap, a scroll, BACK, force-stop or start), no code you passed to `crawl_run()` runs (not `clock`, `stop` or `sleep`; this holds for uiprobe's own `Device`: a subclass that overrides `stop_app`, `tap`, `key` or `_launch_component` runs its override there, see L1 below), and the time limit is checked once more by uiprobe's own clock on the request's connection, right before it is written. Accepted limit L1 (as in the previous version): before a tap, BACK or force-stop the crawl calls your `clock` once more after its reads of the screen and before its last check of the pin, so a `clock` that changes the device's screen there (opens a window, for example) is not caught by those reads; a change of the device itself is still caught by the pin check. The same holds before a start: the crawl calls your `clock` after its read of the launcher activity and before its last check of the pin, so a `clock` that changes or removes the launcher activity there is not caught, and the start uses the component read just before. The Policy is copied when the crawl starts; changes to it during the run are not seen. The crawl calls methods of the `Device` object you pass: its reads, and for the requests that change the device `stop_app`, `tap`, `key` and the internal start `_launch_component`, handing each the pin epoch the crawl approved and the time limit, which the device checks right before the request is written. Also part of L1: a `Device` subclass that overrides these methods and drops those arguments can send after the crawl's checks; this is the same as in the previous version for taps, BACK and relaunches. Accepted limit: a stop asked while the checks before a tap or BACK read the screen takes effect after that one request; `stop` and the time limit are asked again when the next observation begins, and a read in progress can run until it finishes after them.
- Accepted limit for `crawl_run()` from Python: the crawl copies the values you pass into plain data when it starts (the policy and its words, the limits) and turns every clock value into a built-in float at once, so a subclass or an object with hooks cannot run code while it decides. Code you supply that still runs earlier (your `clock`, `stop` and `sleep`, a method of the `Device` object you pass) can change the device; the crawl checks the pin and reads the screen again after them, but an object made to defeat those checks (a `Device` subclass, for example) is not caught.
- `uiprobe launch` selects the device by its serial for each request; it never starts an adb server, and once its first request went out, any failed request ends it at once, so it never goes on through a server that was started again. Accepted limit: if the device behind the serial is replaced between the launcher read and the start, the start uses the component read just before (it fails, or opens that component of the same package on the new device). Use `crawl --press`, which pins the device, where this matters. Limit: the `LaunchState:` values seen and accepted in the reply of `am start` are `COLD`, `WARM`, `HOT` and `UNKNOWN (0)`; with any other value the start is not taken as a success (the launch fails, and a crawl ends with `error`).
- From Python, do not use a `Device` from another thread while its `launch()` runs: a request from that thread can start the adb server again between the launch's steps, and the stop and start can then reach a replacement device (accepted limit). The previous version's monkey-based `launch(restart=True)` had the same exposure.
- Deny words are used by the crawl preview (what `crawl` does by default), which presses nothing, and by the pressing crawl (`crawl --press`, and `crawl_run()` from Python), which judges every screen with the same guards before it taps. Both also refuse every element of a screen that says it cannot be undone, buttons such as "Cancel" included. They recognize the configured irreversibility phrases (for example "You can't undo this" or 元に戻せません, see [Previewing a crawl](crawl.md)), not every possible wording: a warning phrased in another way is not caught, so the screen is then judged like any other.
- The pressing crawl, `uiprobe crawl PACKAGE --press --out DIR` (or `uiprobe crawl PACKAGE --out DIR` with `press = true` in the settings file) or `crawl_run()` from Python (alpha), presses on the selected device: it force-stops the app at its start, taps what the guards allow, presses BACK and relaunches the app. The force-stop at the start (`am force-stop`, then the start of the launcher activity; which screen the app then shows is up to the app) loses what the app had not saved; it goes through the same pin and time checks as a relaunch's force-stop, and `--no-restart` (`crawl_run(..., restart=False)`) turns it off, so the crawl starts from the screen the app shows now. By default it sends nothing to a screen of another app: it relaunches the target app instead (`am force-stop`, then `am start -W`), which can lose unsaved state. `back_on_other_screens = true` under `[rules]` in the settings file, or `--back-on-other-screens` for one run (`Policy(back_on_other_screens=True)` from Python), makes it press BACK there, and that BACK reaches the owner of the focused window, whichever app that is; `--no-back-on-other-screens` turns it off for one run. When it is on, a system permission dialog gets that BACK too, whether its package is listed under `also_target` or not. Right before each tap it reads which window takes a touch at the tap's point and sends the tap only when the topmost window that takes touches there belongs to the app (its owner uid is the app's for Android user 0; for an app with a system uid or a uid shared with other packages, its title must also name the app); `--no-tap-window-check` (`Policy(check_tap_window=False)`) turns that off (text an app sets, such as an unusual window name, can make the check refuse taps on that app's screens; see the limits under [Crawling from Python](python.md#crawling-from-python-alpha)), and then an overlay of another app over the point gets the tap. Windows that only watch touches (such as the system's gesture monitors, which are spy windows) and copies of a touch sent to the wallpaper are not checked. When the window cannot be read, nothing is sent (`cover_unknown`); on a rotated display every tap is refused that way (`rotation`, when the gate's own screen dump or the display orientation in `dumpsys input` says it is rotated), so an app in landscape cannot be crawled yet, and so is every tap while the focused window belongs to another Android user than user 0 (`target_user`). The check trusts that the output of `dumpsys` arrives as the Android system wrote it, and does not trust text an app can set (window names, `applicationInfo.name`). If a window of another app is the lowest in the list, no window above it takes the point, and its name fakes a complete window line, the check cannot tell; the tap then goes where it would go without the check. Output of the system that is damaged in ways that contradict themselves is an accepted limit; a contradiction the check notices makes it refuse. Windows of another package that shares the app's uid (a package of the same developer, signed with the same key, or a system package) are told apart only by their name. The tap is a 10 ms swipe from the point to itself: if Android sends a move event during it and the window at the point is marked `SLIPPERY`, a window of another app that appears there during those 10 ms can receive the rest of the press. It refuses a device that is not an emulator unless `--allow-real-device` (`allow_real_device=True`) is given, keeps every request on the device it checked (and checks before every action and screen read that the device behind its connection is still the same one), and right before each action reads the device again and sends nothing when anything it needs cannot be read or has changed, ending the run when that happens to a BACK or relaunch; see [Pressing crawl](crawl.md#pressing-crawl---press) and [Crawling from Python](python.md#crawling-from-python-alpha). The command stops at the settings file's `[limits]` (after 300 sent actions or 30 minutes, and at most 5 screens deep on one path, in the file `uiprobe init` writes), unless `--actions`, `--minutes` or `--depth` say otherwise; `crawl_run()` takes its `limits` from the caller.

- The pressing crawl can also scroll lists with a mouse wheel turn, but only when you ask: `[rules] scroll_lists = true` in the settings file, or `--scroll` for one run (`--no-scroll` turns it off for one run; the default is off). It sends `input mouse scroll X Y --axis VSCROLL,-N` at one point, on a screen with nothing left to press, at most `[limits] scrolls_per_screen` (10) times per screen. It is a new kind of input beside the tap and BACK, it is not a touch, it only runs on a device whose own `input` usage lists the wheel scroll (API 35 and later on the emulator images tested), and every run prints a plan line that says whether it scrolls, from where that came and the limits. What protects it, and the limits that stay, are listed under [A wheel scroll from the crawl](#a-wheel-scroll-from-the-crawl). With it off (the default) the run reads no usage and sends no wheel input, and behaves as a run without the feature.

Details: [Commands](commands.md).

## A wheel scroll from the crawl

Scrolling is an opt-in: it is off unless `[rules] scroll_lists = true` is in the settings file or `--scroll` is given (`--no-scroll` wins over the file for one run; both options together are a usage error). The plan line says which, for example `scroll lists with the mouse wheel: yes (--scroll), at most 10 per screen, wheel amount 3; an app's own view, or a window that appears just before the wheel, can react to it (see docs/safety.md)`; `no (this device's input does not list the wheel scroll)` when the device cannot do it; `no` otherwise.

A tap-like swipe can act as a tap or a long press (a swipe with 1 px of travel inside a refused button is read by an app as a tap), so the crawl does not swipe. It turns a mouse wheel instead, and a wheel event is not a touch: it goes to the window under the pointer, not to the focused window, and it does what a wheel does to the view there. A wheel scroll is sent only when all of this holds:

- The device's own `input` usage is read by blocks. Its sources list includes `mouse`, and its `scroll` command block (from the command line to the next line at the same or a lower indentation; the API 36 and 37 emulators print `scroll (Default: rotaryencoder). Has the following syntax:` with the syntax lines and `Axis options: SCROLL, HSCROLL, VSCROLL` indented under it) has a pointer-based syntax line, `scroll <x> <y> ...`, that is the mouse's (`(for pointer-based sources)`, which the mouse is one of, a source word before the command, or its own `(Default: ...)`; a line for another source, or naming none, does not count). In that block only, `VSCROLL` must be among the axes: the names of its `Axis options:` lines (which must hold nothing but names) and every `--axis NAME` of its bracket groups (as a word of its own with its value placeholder). Any `unsupported`, `not supported`, `unavailable`, `not available` or `disabled` in the block means no support, and nothing outside the block (another command's text, another source's options line) is read for the axes. Only the driver reads the usage, once per run, after the device check and before anything is sent; the plan line is printed from that read (the command is told the answer by a callback), so the plan and the run use one answer and no caller can claim support. Otherwise the run does not scroll. Both real usages (API 36 and API 37) are kept as test fixtures, `tests/data/input_usage_api36.txt` and `input_usage_api37.txt`, and are read as support.
- It is turned one way only (`VSCROLL,-N`, N from `[limits] scroll_amount`, 1 to 10), nothing else is sent, and it cannot be built with another direction.
- Only on a screen of the app (or of a package listed under `also_target`, when that package is on target under the same rules), with the keyboard hidden, that is not a dialog and not judged irreversible, and only when no row is left to press on it or it is at the depth limit.
- The list that is scrolled (the container) is chosen in two steps. First, the largest visible scrollable element must have exactly one of four classes: `android.widget.ListView`, `android.widget.ScrollView`, `androidx.recyclerview.widget.RecyclerView`, `androidx.core.widget.NestedScrollView` (a larger scrollable of any other class, such as a ViewPager or a HorizontalScrollView, means no scroll). Second, when scrollable elements of those four classes lie inside it, the container is the largest of the innermost ones: on the Settings screens the page is a ScrollView and the list a RecyclerView inside it, and the RecyclerView is chosen. The point (the center, then a 3 by 3 grid) qualifies only when every element whose rectangle holds it, whether or not it has a label or is clickable and whatever its size (siblings of the list included), is the container, an element inside it or one of its ancestors, and passes the rule of its place. Inside the container: exactly one of `android.widget.LinearLayout`, `FrameLayout`, `RelativeLayout`, `androidx.constraintlayout.widget.ConstraintLayout`, `android.view.View`, `android.view.ViewGroup`, `android.widget.TextView`, `android.widget.ImageView` (or one of the four list classes when it is not scrollable, a view that cannot scroll, as the RecyclerView inside the scrolling ScrollView of the Settings first page), and nothing scrollable. Above the container (the page the list lies in): one of the four list classes, scrollable or not, or one of the plain classes that is not scrollable; an ancestor of any other class (a ViewPager, a HorizontalScrollView), or a plain one flagged scrollable, refuses the point. In every place none may be long-clickable, checkable, editable (`editable` flag), a password field, a text field or refused by judge. These are allow lists fixed in the code, not settings; exact class names, no substring matching. A Spinner, dropdown, custom view, second scrollable inside the list, pager, WebView, picker, slider or map at the point disqualifies it, and if no point qualifies the screen is not scrolled. A point that lies in a screen-edge area of the judge (the areas that give a tap `screen_edge`) never qualifies. Every element there is also checked for what it is and says, clickable or not (the judge decides only clickable ones): one of a package other than the screen's target (a listed `also_target` package when it is on target), or with a deny word or an irreversibility phrase in its own text, description or hint (the judge's own matcher, its exception words included; the resource id does not count here), disqualifies the point.
- It passes the gate of a tap: the device is the pinned one, the app is in front and owns the focused window, the keyboard is known to be hidden, the screen is read again and the engine's re-check on it gives exactly the planned container and point and finds the whole screen identical (every element's id, parent, class, package, text, description, hint, flags and bounds); and the window that takes a touch at the point is read and must belong to the app (`covered_by_other`, `cover_unknown`, unless `--no-tap-window-check`). For a scroll it must also be the focused app window that supplied the dump, told by its title (`covered_by_other` for another title, `cover_unknown` when the focused title is not known): a popup of the app's own uid that is visible but not part of the dumped hierarchy would otherwise get the wheel. Two windows with the same title cannot be told apart. A tap keeps the uid-only test: a window of the app's own uid at the tap's point takes the tap whether or not it is the window that was dumped, which is a limit of the tap side. The window is read because the wheel goes to the window under the pointer, **not to the focused window**; the focus check stays because that is the tap's rule. Nothing the caller supplied runs between the last comparison and the request, which carries the time limit and the approved pin epoch like a tap's.
- The number of scrolls is bounded per container, per family of screen ids, per screen's set of lists and per activity (`scrolls_per_screen` for each): the container's key does not change with a header, the family follows a list whose id changed as it scrolled, the set of lists is the activity and every scrollable element's class, resource id and ancestors' classes (so a header that changes the id together with another list becoming the largest does not start a new count), and the activity count holds even when a list is added on return and every other key changes. Coverage cost: the activity count is shared by all the pages of one activity, so an app whose pages are all one activity (a single-activity app) gets `scrolls_per_screen` scrolls in total, not per page; raise `[limits] scrolls_per_screen` for such an app. Scrolls count as actions. A screen is left as soon as a scroll shows no new element (clickable or not). A scroll is an incident, which blocks that container and counts toward `[limits] scroll_incidents` (2; after that nothing more is scrolled in the run), when it changed a checked state or a text outside the scrolled list, or landed on another activity or package (a listed `also_target` package counts as the target's own), on a dialog (also one with the same screen id, found by its top-level element being smaller than the display), or on a page whose scrolled container is gone (no scrollable element with its key and overlapping bounds, so also a page that reuses the list's key elsewhere, and a page with the same classes and resource ids but no scrollable list). The last three are navigation (the depth is one more, as for a tap). An unreadable foreground on the screen that was scrolled is an incident without a depth change. Only what is below the scrolled container element itself is left out of the change comparison, by text and checked state, because its rows move as it scrolls; a sibling list with the same key is compared, and identical rows outside the list that are fewer or more after the scroll are not paired.
- A mouse pointer may stay on the screen after a wheel turn and show in screenshots.

Limits that stay, which the dump cannot close (this is why it is opt-in):

- An app's own view of an allowed class (or a class derived from a plain layout, reported by the dump as the plain one) can react to the wheel: change a value, zoom, change a page. The dump does not show which view handles a wheel event or what an app does with it.
- A list view inside the chosen list that the dump does not flag as scrollable is allowed at the point (the Settings first page has one). If it does take wheel events at run time, for example an app's own list class reported as a RecyclerView, it can receive the wheel.
- If the inner list is at its end, the wheel can scroll the outer page instead: the page above the list is an allowed container, and the dump does not show which of the two takes the event.
- A RecyclerView's orientation is not visible in the dump: a horizontal list of the allowed class gets a vertical wheel turn.
- Changes after the gate's last read pass any action, a tap included: the gate reads the screen and the window, and the request goes out right after, but what happens on the device between the last read and the event is not seen.
- With `--no-tap-window-check` (`Policy(check_tap_window=False)`) the window at the point is not read, so an overlay of another app over the point gets the wheel as it gets a tap.
- A clock, a counter or another text that changes outside the list between the two reads is taken as a change and costs a scroll, and a change inside the scrolled list (a value of a row) is not looked at by text.
- A non-clickable label whose deny word is only in its resource id is not matched: resource ids are not matched at the wheel point (the judge does match them for a tap, on the element it presses).
- Calling the private `Device._wheel_scroll` directly sends the wheel event without a usage read; only the crawl's driver reads the usage first, and the method is not part of the API.
- Two display cases of `uiprobe tree` after scrolling, when parent ids are reused by the dump: a child's destination can be shown under two rows, and with text recording off (`record_text = false`) a skip reason can be attached to two rows. They change what the tree shows, not what the crawl sent. A few rarer display cases of a scrolled screen remain, found with made-up run folders: a tap made after a row moved to the exact place of another read's row can be shown on that row; with text recording off, a skip reason can be lost when two reads of one screen share a row's fingerprint; when a read between two scrolls exists only as a scroll snapshot of another activity, two screens can be shown as one; and a read of more than 2,000 elements can leave the skip reasons of the other reads of the same screen unmatched. These too change only what the tree shows.
- An element that appears between the gate's dump and its final window read (a new window or view at the point) can receive the wheel, and a value can change; this is rare, and a short form of it is in the plan line.
- A replacement `Device` subclass can claim wheel support: the driver trusts the `Device` object it is given, including one whose `_wheel_supported` is overridden (subclasses are trusted, as for the other checks the crawl asks of the device).

## Real devices and test accounts

- Use an emulator, or a test device with test accounts. Do not run uiprobe on a phone that holds your own accounts, payment methods or messages.
- uiprobe uses the device given with `-s`, else the one named in `ANDROID_SERIAL`, else the only ready device. Run `uiprobe devices` first.
- The guards have been checked only on Android emulators; real devices and other Android versions may behave differently.
- Known point: a pressing crawl, by `--press` or by `press = true` in the settings file, pins the device before it checks whether it is an emulator. The pin reads the device's identity (`ro.serialno`, the build fingerprint and the boot id), so a real device without `--allow-real-device` gets those reads before the refusal; nothing is written, started or pressed. This was so for `--press` before; `press = true` is a new way into it.
- When `dumpsys window` shows several displays (a foldable with a cover screen) or an unusual focused-display line, the foreground app and the focused window are read only while display 0 is the focused display: the foreground from the device-wide resumed activity, the focused window only when exactly one display has a focused window and that window is on display 0. Otherwise they are unknown, so `launch` fails with `not_in_front` and the crawl presses nothing. That the resumed activity is printed once for the whole device was seen on one capture only (SM-F776B, Android 17, phone open). The focus reading is best effort against forged window titles, so on such a device the tap window check is the guard and cannot be turned off: with `--no-tap-window-check` the pressing crawl sends no tap or BACK. Once any read in a run has shown several displays (also window blocks on more than one display), this holds for the rest of the run; a new run starts without it. Accepted limits, where an app's window title can mislead the focus reading: while no display has a focused window, a title that forges a display header and a focus line together is read as the focus; if `dumpsys activity activities` has no genuine resumed line, a title can supply agreeing resumed lines, and the foreground becomes that package (on one display, the same holds without a genuine `mFocusedApp` line, as before); and a focused window whose title changes between the focus read and the owner read can have its title text taken as owner lines, so the focus is given to another package and uid. While a foldable is being opened or closed, the foreground can be misread if the focus moves between the window read and the activity read; taps stay guarded by the tap-window check, the next read notices it, and the same gap is in the earlier commits of this change. Taps stay guarded by the uid check of the window at the tap point, which cannot be turned off on several displays; a BACK relies on the focus reading, so it can go to the window that really has the focus. Further accepted limits (L1, code you pass to the crawl): the note of several displays is cleared when a crawl starts, so a `clock`, `stop` or `sleep` of yours that starts another crawl on the same `Device` clears it; reads that your callbacks make (such as `device.foreground()` in your `clock`) count toward the note, and only those before the gate's last check of it are seen in time; `Device.diagnose_tap_window()` does not count toward it, so a `dumpsys input` that only it reads does not set the note. Window titles can also move the reading the other way: a line break in a title can split a window block's header from its `mDisplayId=` line (that window then counts on no display), and a title that imitates a second window block, or a second `Display:` section in `dumpsys input`, on a single display makes uiprobe take the device for one with several displays, which only refuses more. `dumpsys input` is read only for the tap window check, so its `Display:` sections count only while that check is on.

## What deny words cannot see

- Deny words see only the text, description, hint and resource id that uiautomator reports. An icon-only button without them (a trash can, a send arrow) has no words to match.
- `--tap-unlabeled` allows pressing elements that have no text, description or hint. This also allows icon-only buttons that deny words cannot see, such as a trash can.
- Deny words include the state-changing verbs of Settings pages (`forget`, `disconnect`, `unpair`, `turn off`, `eject` and others, see [Crawling an app](crawl.md)), so an element whose judged scope (its own texts and its descendants, and the other places the guard looks, see [Crawling an app](crawl.md)) holds one of them is not pressed: the `Forget` and `Disconnect` buttons of a saved network, for example. Separate buttons in the same bar whose own scope holds no deny word (`Edit`, `Cancel`) stay pressable. Refusing more rows can change which other rows a run with a small action budget reaches, because a skipped row frees budget for others; this is expected. Substring matching also over-blocks (`Posture` contains `post`); a miss is worse than an over-block. The known limits are listed in [Crawling an app](crawl.md).
- There are no exception words by default. A word you list under `[deny] except` in the settings file stops a deny word found inside it from counting where the word stands whole inside one element's text with real separators around it, so an element whose only hit was there is pressed: with `automatically` listed, `Bill my card automatically` is pressed by `crawl --press`. You take that on when you add the word. A label split across child elements (`Turn on` + `automatically`) or text that normalization changes may still be refused; the exact condition and its limits are in [Crawling an app](crawl.md). Exception words never weaken the screen-wide check behind `confirm_button`.
- There are no exception phrases by default. A phrase you list under `[deny] except_phrases` lets one plain row through, not a word. A phrase lets a row through only when all of this holds: the row is a plain button (it is not long-clickable, checkable, scrollable, editable or a text or password field, nothing inside it is clickable or any of those, it has at most 500 elements, and no clickable element contains it); the tap lands on the row or on something inside it; the row must have only its name as text: exactly one element inside it has any text, description or hint, that is the name, and its description and hint, if any, say the same as the text (so there is nothing in the row for a deny word to be made with); the name equals the phrase exactly, ignoring case, extra spaces and full-width letters, it has some area on the display and its middle lies inside the row; the last element drawn at the tap point and at the middle of the name (an element with no text counts too, and so does one nobody can see) is the row or inside it, except Samsung's empty `round_corner` decoration view (a `View` with no flag, text or child whose id is `<package>:id/round_corner`, where `<package>` is `android` or a package name of two or more dot-separated segments of ASCII letters, digits and underscores that start with a letter), which is passed over; no other button or control (a clickable, long-clickable, checkable, scrollable or editable element, a field) is drawn on top of the row there (a scrolling list that holds the row is fine); the deny words found in the row are exactly the ones found in the name text alone; the only reason the row is refused is a deny word; and the row is not pressable-but-refused again when that name text is taken out and the same screen is judged once more (the check uses the normal deny matching, with its exception words). So `Quick Share` is pressed when its only problem is the `share` of its own name; any other deny word anywhere that reaches the row (its summary, its id, an element on top of it) still refuses it, and so does text that only forms a deny word next to the name once the name is out (`De` + `Quick Share` + `lete` reads `delete`: refused, an accepted over-refusal; but a row with a second text is not given a phrase at all). If a screen has more than 8 rows that fit all this except the last two points (counted before the reasons are looked at, so a disabled row counts), no phrase applies on that screen. You take on that the row does what its name says: an app can name any button `Quick Share`. The press is marked `except_phrase` in `transitions.jsonl`, so you can find it afterwards.

## Listing more apps (`also_target`)

By default a pressing crawl presses only inside the app it was given: a screen of any other package gets no tap, and the app is restarted instead. `[rules] also_target = ["com.example.helper"]` in the settings file widens that to the packages listed, and only to them; there is no command-line option for it, so the file shows what a run was allowed to do (`run-start.json` records the list when it is not empty).

What listing a package allows: a screen is the listed package's when the dump and the foreground app both name it, and it is then judged exactly like the crawled app's screens. Every guard still applies to it: deny and confirm words, irreversible screens, toggles and switch rows, sliders, text and password fields, screen edges, the window check (the window at the tap must belong to the listed package's own uid, read once at the start; a package whose uid cannot be read, for example one that is not installed, is refused then), the keyboard and focus checks, the pin, the emulator-only default and the depth, action and time limits. Elements of any other package on that screen, and a listed package's windows over a tap point of the crawled app, are still refused.

What stays refused whatever is listed:

- `com.android.systemui` (the lock screen and the notification shade), the home apps `com.android.launcher3`, `com.google.android.apps.nexuslauncher` and `com.sec.android.app.launcher`, the home app the device itself names, and the crawled app itself are refused when the run starts, as a usage error (exit 2) before anything is sent. The device's home app is read once, at the start, when the list is not empty; if that read fails, or does not name exactly one `PACKAGE/CLASS` (no component, `No activity found`, the system's `android/...ResolverActivity` answer, an error, a non-zero exit), the run is refused with `also_target: could not read this device's home app, which also_target needs in order to refuse it; nothing was pressed`. The fixed list is an extra check, not a replacement. A read that fails at the transport level (`AdbError`, a gone or offline device and the like) stops before any input with that error's own exit code (10 for `AdbError`); the exit-2 message above is for an answer that cannot be read. The home app is checked at the start only: a home app that changes during the run is not noticed.
- Permission screens (the permission controller and the package installer) are never pressed: the guard that refuses their elements does not look at the list, and their screens stay off target whether or not their package is listed, so listing one of those packages has no effect (a permission package chosen as the primary target is out of scope: it is handled as before). They are handled as today: the app is restarted, or, with `back_on_other_screens = true` in the settings file or `--back-on-other-screens`, such a dialog gets BACK (listed or not), and that BACK answers the dialog.
- Any package that is not listed, including every app a listed package opens.

Two limits of the window check predate this setting and now apply to a listed package's screens too: with `--no-tap-window-check` overlays are not checked at all, and two packages that share one uid (`sharedUser`) cannot be told apart by their windows (a window of the listed package's uid with a title that does not name it is refused only when the package has a shared or system uid).

Listing an app still lets the crawl press inside it for real, with the test-account caution of [Real devices and test accounts](#real-devices-and-test-accounts): a listed package is never started by uiprobe, but whatever its rows do on the device is up to that app. Settings, the shell and other system apps are not refused apart from the names above, so list them knowingly.

## Dialog buttons that change a device setting

A popup that asks to turn something on (Bluetooth, for example) has a positive button labeled "ON", "Turn on" or "Enable", and pressing it changes the device. Two guards cover it, both only on a screen judged a dialog (its first top-level element is smaller than the display) and both switched off by `[rules] refuse_dialog_confirm = false`:

- The platform dialog's positive button, the element whose resource id is `button1` under the `android` package (`android:id/button1`) or the screen's own package (`com.android.settings:id/button1` on a Settings screen), and anything inside it, is refused whatever its label (`dialog_confirm_button`, with a detail that says it is the dialog's positive button). So is a candidate whose press point lands on it or on something inside it, such as a dialog container whose center falls on the button's label; a screen whose parent links are missing is covered by checking whether the button's visible part holds the press point. Other names (`button1x`, `button10`) and other packages' ids do not match. The negative and neutral buttons (`button2`, `button3`) are not refused by this.
- `turn on`, `enable`, `オンにする` and `有効にする` are dialog-only confirm words: a button with one of them, or starting with one followed by a non-letter (`Enable Bluetooth`), is refused on a dialog even when it does not carry that id (an app's own dialog). A word ending in a letter of the Japanese script needs no boundary, like the other Japanese confirm words, so `有効にする場合` counts. They never give the screen-wide `confirm_button` reason (a full-screen `Enable` row next to a deny word is not refused for it). A bare `ON` is not a confirm word: it is refused only through the id.

Outside dialogs nothing changes: a full-screen row labeled `Turn on` is still judged by the deny words (`turn off` is one) and the other guards.

## Device-wide keys are refused

`key` refuses device-wide keys with a usage error (exit 2) before the adb server is contacted, whether the key is given as an alias or as a name. Ten keys are refused whatever any file says: the power, sleep, lock and call keys (`KEYCODE_POWER`, `KEYCODE_SLEEP`, `KEYCODE_SOFT_SLEEP`, `KEYCODE_LOCK`, `KEYCODE_CALL`, `KEYCODE_ENDCALL`, `KEYCODE_HEADSETHOOK`, `KEYCODE_TV_POWER`, `KEYCODE_AVR_POWER`, `KEYCODE_STB_POWER`). The other groups (more power and wake keys, sound and media playback, brightness, screenshots, assistants, system UI and keys that open other apps) are defaults: without a settings file they are refused, and with one, the file's `[keys]` table decides. The file can remove any of them and can add keys to refuse, for example `KEYCODE_HOME`. Any key that no list refuses is sent, including `home` and `recents`, which can leave the current app. `key` uses `--config PATH` when given (the file must then exist), else `./uiprobe.toml` when that file exists, else the built-in lists. Like `tap` and `swipe`, `key` sends to whatever screen is showing, in any app. The groups are listed in [Pressing keys](commands.md#pressing-keys) and the file in [Settings file](settings.md).

## What the guards cannot see

- The preview judges one screen as it is. It cannot see what a press would lead to, and it does not look at the pixels, only at what `uiautomator` reports.
- The screen-edge areas use the sizes measured on an API 36 emulator for every device for now, in pixels, not scaled to the device's density.
- The foreground app is not checked by `tap`, `swipe` or `key`.

## Texts in run folders

A run folder holds screen text, which may be personal. Two protections exist; the rest is up to you.

- A field with the `password` flag is always written without its text (`"text": ""` and `"hidden": ["text"]`), and `summary.txt` shows `[password field]`. It applies to text in the records only: a screenshot (`--screenshots`) holds pixels, so a password field whose characters the app shows on screen has them in the PNG; `record_text` off refuses screenshots. Only the flag decides: an app that shows a code or password in a plain field (a one-time code, a PIN on a custom keypad) is not covered by this.
- `record_text = false` (or `--no-record-text`) keeps `text`, `content_desc` and `hint` of every element, and the title of a window that covers a tap, out of the records. Use it when screens may show a code in a plain field. It cannot be used with `--screenshots`, because a picture shows the text.
- Limit: fingerprints in `skipped.jsonl` and in the records are hashes over an element's texts. A short code (4 to 6 digits) could be recovered from its fingerprint by trying all values, with `record_text` off too. Do not share a run folder of a screen that showed such a code.
- `uiprobe dump` and the text a dry run prints are not run folders and keep the texts; the same care as for [dumps](#personal-data-in-dumps) applies.
- PIN and fingerprint prompts of the system are screens of another app; uiprobe does not write them, but it notes their ids and, for an action decided there, the package.

## Terms of service

Automating an app you do not own may break its terms of service. Read them first, and prefer your own builds and test environments.

## Personal data in dumps

- A dump holds the text on the screen, which may include personal data such as names, addresses and messages. Check saved screens before you share them, also in an issue.
- A screenshot (`uiprobe screenshot`, `Device.screenshot`) can contain personal data too, like a dump, and an image can show what no text names, so look at it before you share it.
- Android lets an app forbid screenshots of a screen (`FLAG_SECURE`), but `uiautomator` still returns that screen's structure and text. So a dump of such a screen, and any copy of it you save, contains that text, which may include personal data. For example, on Android emulators at API 24 and API 36, Chrome's Incognito tab had `FLAG_SECURE`: Android's screenshot command, `screencap`, gave empty output on API 24 and an almost entirely black image on API 36, while `uiautomator dump` and `uiprobe dump` returned the full tree with its text.

## Sharing a tap window diagnosis

- `uiprobe diagnose tap-window` sends one command to the device, `dumpsys input`, which only reads; it presses nothing and changes nothing on the device. With `--package PKG` it first reads `dumpsys package PKG` (the app's uid, as the crawl reads it), which only reads too.
- `dumpsys input` holds device values: window titles and app names, the uids and pids of apps, screen coordinates, display ids such as `uniqueId=local:...`, the names of input devices, and on some devices more. uiprobe reads it in memory and never saves or prints it.
- By default the report holds only uiprobe's own words and numbers it counted: the reader's verdict (reason, rule, line number), whether it took a list as display 0's and how many windows it read there, and for a few lines their kind (as the reader classified them) and length. No field name, value, flag, row or display number, orientation, sign or other character of `dumpsys input` is in it. Tests fill the captures with a serial, IMEI-like numbers, MAC and IP addresses, accounts, phone numbers, package names, window titles (also with field-like text or line breaks), quoted values, display ids and input device names, change them to other letters, digits, Unicode digits, signs, quotes and delimiters, mutate the outputs further, and check that the text, the JSON and the Python object hold only uiprobe's fixed words and numbers it counted.
- Errors are reported by their error code alone, never with the error's message, which can name the device or hold text it printed. A usage error of `diagnose` does not repeat the command line, which can hold a serial.
- `--package PKG` is not echoed: the report does not name it. Whether a `samsungFlags=0x1` window was accepted as its own, and a note that its uid could not be read, still tell something about that app on the device to anyone who knows which package was given.
- The lengths still say something about the device (how long a window title's line is), and so do the counts and the kinds the reader gave lines (how many windows it read; a window name with line breaks can change them). `--show-device-text` adds the indents and shapes of the lines, with field names, values, flag names and numbers from the device: window names and app text can appear there, with or without line breaks, and can hold a serial or personal data. The report's first line says so in that mode; read it before you share it. Details: [Diagnosing the tap window check](commands.md#diagnosing-the-tap-window-check).
